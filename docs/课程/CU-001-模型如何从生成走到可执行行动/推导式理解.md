# CU-001：模型如何从生成走到可执行行动 - 推导式理解

> CU 状态：未开始
> 生成依据：当前主干知识全部未开始，优先补齐阻塞 Agent Loop 的模型生成、真实请求和工具协议
> 覆盖知识点：10 个

## 选课依据与覆盖知识点

当前目标不是先记住十个术语，而是回答一个完整问题：

```text
一个只会继续生成文本的模型，
为什么经过 API、结构约束和工具执行器后，
可以参与真实系统行动？
```

本 CU 从[学习总纲](../../学习总纲.md)和[学习进度](../../学习进度.md)动态选择下面 `10` 个主知识点：

| 序号 | 知识点 | 总纲主归属 | 当前状态 | 本 CU 中的作用 |
|---|---|---|---|---|
| 1 | Token、Tokenizer 与上下文窗口 | 模型与表示基础 | 未开始 | 解释模型真正接收的输入和容量边界 |
| 2 | Transformer、自注意力与位置编码直觉 | 模型与表示基础 | 未开始 | 解释模型如何组合上下文中的信息 |
| 3 | 自回归生成与下一 Token 预测 | 模型与表示基础 | 未开始 | 解释输出为什么是逐步生成的候选 |
| 4 | 解码参数与非确定性 | 模型与表示基础 | 未开始 | 解释相同请求为什么可能得到不同输出 |
| 5 | 幻觉、知识截止与上下文依赖 | 模型与表示基础 | 未开始 | 解释为什么不能把流畅文本当成事实 |
| 6 | 消息角色与请求结构 | 模型交互原语 | 未开始 | 把任务、约束和运行数据放进真实协议 |
| 7 | Structured Output 与 Schema | 模型交互原语 | 未开始 | 约束模型输出形状，便于程序消费 |
| 8 | Function Calling 与 Tool Calling | 模型交互原语 | 未开始 | 让模型表达行动意图，而不是伪造行动结果 |
| 9 | Usage、Finish Reason 与错误响应 | 模型交互原语 | 未开始 | 区分模型停止、请求失败和任务完成 |
| 10 | 工具选择、参数校验与结果回填 | Agent Loop 与决策 | 未开始 | 把行动意图变成受控执行并将事实送回模型 |

选择它们的原因是：前三个机制解释模型能做什么，第四和第五个机制解释它为什么不可靠，第六到第九个机制把模型接入真实程序，第十个机制完成一次最小行动闭环。

本 CU 暂不展开循环、规划、记忆和验证器；这些问题会由最后一个阶段自然引出。

## 核心推导链

```text
自然语言进入模型
  ↓ Tokenizer 将输入变成 Token
Transformer 根据上下文关系计算下一 Token 分布
  ↓ 自回归和解码逐步生成
得到“听起来合理”的候选文本
  ↓ 但它可能非确定、过期或幻觉
API 用消息角色、请求和响应承载一次真实调用
  ↓ 但自由文本难以被程序稳定消费
Structured Output 用 Schema 约束结果形状
  ↓ 但结构正确仍不等于真实行动
Tool Calling 让模型表达工具和参数意图
  ↓ 但模型输出仍是不可信输入
程序完成参数、业务、权限校验并执行工具
  ↓
真实结果回填给模型
  ↓
留下下一问题：谁决定继续、验证还是停止？
```

整条链只有一个核心判断：

> 模型始终负责生成候选，确定性程序始终负责约束、执行和验证真实世界的副作用。

## 贯穿案例与初始状态

我们使用一个研发 Agent 调查发布失败：

```text
用户目标：
  调查 release-20260810-1427 为什么失败；
  如果满足回滚条件，给出回滚建议；
  未经确认不得真正回滚。

已有输入：
  发布编号、用户问题。

初始状态：
  尚未读取发布记录、日志和监控。

可用能力：
  模型调用；
  get_release；
  query_logs；
  query_metrics；
  rollback_release。

权限边界：
  查询工具只读；
  rollback_release 会产生真实副作用，必须审批。

成功标准：
  根因结论能回链真实证据；
  不把建议误写成已执行；
  不发生越权或重复回滚。
```

这一个案例会从“直接问模型”逐步演进成“受控工具行动”。发布编号、用户目标和权限边界始终不变。

## 阶段一：模型为什么只能先生成一个候选答案

### 已有能力

最小版本只有一次模型调用：

```text
用户问题
  ↓
模型
  ↓
“可能是配置错误，建议回滚”
```

这句话可能非常流畅，但系统还没有读取任何发布记录。

### 输入怎样进入模型

模型不直接读取“汉字”或“单词”，而是由 Tokenizer(文本切分器)将内容切成 Token(模型处理文本的基本单位)。上下文窗口限制一次调用能够容纳的输入和输出总量。

可以先建立最简直觉：

```text
文本
  ↓ Tokenizer
Token 序列
  ↓ Embedding 与位置
带语义和顺序的表示
  ↓ Transformer
下一个 Token 的概率分布
```

Transformer 中的 Self-Attention(自注意力机制)让当前位置能够根据上下文中其他位置的信息计算表示；位置编码补充顺序信息，否则“服务导致数据库超时”和“数据库超时导致服务失败”会失去方向差异。

第一轮不需要手推矩阵，但要抓住三点：

1. 模型看到的是有限 Token 序列，不是无限知识库。
2. 自注意力组合的是当前上下文和模型参数中的模式，不会自动查询真实发布系统。
3. 位置和上下文会影响哪些信息被使用。

### 输出怎样产生

模型按自回归方式逐步预测：

```text
P(token_1 | context)
  ↓ 选出 token_1
P(token_2 | context, token_1)
  ↓ 选出 token_2
...
```

每一步都在已有上下文上预测下一个 Token。最终答案是多次局部选择累积出来的，不是先在内部得到一个完整事实对象再打印。

Temperature、Top-p 等解码参数改变候选分布的选择方式。较低随机性可以让输出更稳定，但不能把错误知识变成正确事实。

### 暴露的问题

```text
生成概率高
  ≠
事实为真
```

模型可能：

- 根据常见发布故障模式补出不存在的配置错误。
- 使用训练截止前的旧知识回答当前系统问题。
- 因为上下文缺少发布记录而猜测。
- 在不同采样参数下给出不同根因。
- 在低随机性下稳定地重复同一个错误。

因此 V0 只能得到“候选分析”，不能得到“发布事实”。

### 下一问题

要让程序稳定地传入任务、约束和运行数据，并识别模型本轮返回了什么，我们需要真实请求协议。

## 阶段二：真实 API 怎样把生成能力接入程序

### 从一段字符串升级为有角色的消息

程序需要区分：

```text
System / Developer
  系统级目标、运行规则和边界

User
  当前用户任务和输入

Assistant
  模型已经生成的内容或行动意图

Tool
  外部工具返回的真实结果
```

不同供应商的角色名和优先级细节可能不同，但通用目标一致：把长期约束、当前任务、模型输出和环境反馈分开，不把所有内容拼成一段不可追踪文本。

本案例的请求结构可以表达：

```json
{
  "instructions": "先调查证据；未经用户确认不得回滚",
  "input": [
    {
      "role": "user",
      "content": "调查 release-20260810-1427 为什么失败"
    }
  ]
}
```

### 响应不只有正文

一次模型调用至少要观察：

| 观察项 | 能回答的问题 | 不能证明什么 |
|---|---|---|
| 输出内容或输出项 | 模型本轮生成了什么 | 内容一定真实 |
| Usage | 消耗了多少输入和输出 Token | 任务质量好坏 |
| Finish Reason 或响应状态 | 本轮为何停止或是否完整 | Agent 任务已经完成 |
| 错误响应 | 请求在哪一层失败 | 业务目标为何失败 |
| Trace ID | 怎样关联日志和重试 | 根因已经定位 |

`Finish Reason`是部分模型 API 使用的字段；其他 API 可能使用响应状态、输出项类型或不完整原因表达相同类别的信息。学习时应理解“停止语义”，不要把某个供应商字段名当成唯一标准。

### 暴露的问题

请求和响应让程序能看见一次调用，但如果模型返回：

```text
先查发布记录，再查错误日志，然后看监控。
```

程序仍然需要从自由文本中猜测步骤。格式稍变，解析器就可能失效。

### 下一问题

怎样让模型输出稳定的数据形状，供程序读取？

## 阶段三：Structured Output 先解决“长得对”

### 引入 Schema

我们先让模型只生成调查计划：

```json
{
  "hypotheses": [
    {
      "name": "发布配置错误",
      "required_evidence": ["release_record", "error_log"]
    }
  ],
  "next_action": "get_release"
}
```

Schema 可以约束：

- 必须有哪些字段。
- 字段是什么类型。
- 枚举允许哪些值。
- 数组元素是什么结构。
- 是否允许额外字段。

结构化输出解决的是：

```text
自由文本难解析
  ↓
输出形状可预测
  ↓
程序可以稳定读取
```

### 它没有解决什么

下面的数据可以完全符合 Schema，但仍然是错的：

```json
{
  "hypotheses": [],
  "next_action": "rollback_release"
}
```

Schema 只能证明“长得对”，不能证明：

- 发布编号存在。
- 根因结论有证据。
- 当前用户有回滚权限。
- 业务状态允许回滚。
- 这个动作不会重复执行。

### 下一问题

我们还需要一种协议，让模型明确表达“想调用哪个工具、参数是什么”，并把执行控制权留给程序。

## 阶段四：Tool Calling 怎样表达行动意图

### 工具定义进入上下文

程序向模型声明工具名称、描述和参数结构：

```json
{
  "name": "get_release",
  "description": "读取指定发布的状态、变更和失败阶段",
  "parameters": {
    "type": "object",
    "properties": {
      "release_id": {"type": "string"}
    },
    "required": ["release_id"],
    "additionalProperties": false
  }
}
```

模型可能返回一个工具调用意图：

```json
{
  "tool": "get_release",
  "arguments": {
    "release_id": "release-20260810-1427"
  }
}
```

关键边界是：

```text
模型选择工具并生成参数
  ≠
模型已经执行工具
```

Function Calling(函数式工具调用)和 Tool Calling(广义工具调用)常被用于描述这一类协议。前者强调模型生成函数式调用参数，后者还可以包含搜索、文件、浏览器或其他环境能力。

### 程序重新获得控制权

```text
模型
  ↓ 工具调用意图
编排程序
  ↓ 决定是否允许执行
工具
  ↓ 返回真实结果
编排程序
  ↓ 结果回填
模型
  ↓ 基于新事实继续生成
```

Tool Calling 把“生成”和“执行”切开，程序因此可以插入日志、审批、权限和失败处理。

### 下一问题

工具参数来自模型输出。即使它满足 Schema，也仍然属于不可信输入。执行前必须经过哪些校验？

## 阶段五：校验、执行和结果回填怎样形成最小行动闭环

### 四层校验

以回滚工具为例：

| 层次 | 检查内容 | 失败示例 |
|---|---|---|
| 结构校验 | 字段、类型、枚举和必填项 | `release_id`缺失 |
| 业务校验 | 发布是否存在、状态是否允许回滚 | 发布仍在进行中 |
| 权限校验 | 当前用户和任务是否允许写操作 | 用户只有只读权限 |
| 副作用校验 | 审批、幂等、环境和影响范围 | 同一发布重复回滚 |

模型不能给自己授权，也不能用一句“已经确认”代替真实审批状态。

### 真实结果必须回填

查询工具返回：

```json
{
  "release_id": "release-20260810-1427",
  "status": "failed",
  "failed_stage": "health_check",
  "change": "PAYMENT_TIMEOUT_MS: 800 -> 80"
}
```

程序应将这个工具结果和调用关联标识一起回填。模型下一轮才能把假设更新为“健康检查失败，且超时配置发生十倍变化”，再决定查询日志或监控。

工具失败也要回填明确语义：

```json
{
  "error_type": "permission_denied",
  "retryable": false,
  "message": "当前用户无回滚权限"
}
```

不要只回填“失败了”，否则模型无法判断应该改参数、换工具、申请审批还是停止。

### 当前闭环

```text
用户任务
  ↓
模型生成工具意图
  ↓
程序校验
  ↓
真实工具执行
  ↓
结构化结果回填
  ↓
模型基于新事实继续分析
```

到这里，我们完成的是“一次可控行动”，还没有完成完整 Agent。

## 正常链路与失败链路

### 正常链路

```text
用户：调查发布失败
  ↓
模型：请求 get_release
  ↓
程序：结构、业务和权限校验通过
  ↓
工具：返回失败阶段和配置变更
  ↓
模型：请求 query_logs
  ↓
工具：返回 timeout 错误
  ↓
模型：形成带证据的根因和回滚建议
  ↓
程序：等待用户审批，不执行回滚
```

### 失败链路

```text
模型：直接请求 rollback_release
  ↓
Schema：参数格式合法
  ↓
业务校验：缺少根因证据
权限校验：当前任务未获审批
  ↓
程序拒绝执行
  ↓
回填 permission_denied / approval_required
  ↓
模型改为输出调查计划和审批请求
```

失败链路证明：Schema、Tool Calling 和模型自述都不能替代确定性业务控制。

## 最小实验

这些实验是本 CU 的学习任务，不是已经完成的证据。

### 实验一：观察生成和解码

```text
假设：
  相同上下文下，解码设置会影响输出稳定性，但不能保证事实正确。

输入：
  不提供发布记录，只询问失败原因。

操作：
  重复调用，并比较低随机性和较高随机性设置。

观察点：
  根因是否变化；错误答案是否仍然流畅。

结论标准：
  能区分稳定性和正确性。
```

### 实验二：比较自由文本和 Structured Output

让模型分别输出自由文本计划和 Schema 约束计划，再故意提供一个结构合法但业务错误的`next_action`。

断言：

- 结构化输出减少解析歧义。
- Schema 无法证明动作合理、真实或有权限。

### 实验三：手写一次 Tool Calling

不使用 Agent 框架，记录：

```text
原始请求
模型工具调用意图
参数校验结果
工具真实返回
结果回填
模型后续响应
Usage、停止状态和 Trace ID
```

### 实验四：制造合法但越权的请求

让模型生成格式完全合法的`rollback_release`参数，但不给审批。

通过标准：

- 工具没有执行。
- 错误类型可区分权限、业务和结构问题。
- 回填结果能让模型选择申请审批或停止。
- 审计日志能证明没有真实副作用。

## 边界、代价与下一问题

当前机制已经解决：

- 模型输入和输出有真实协议。
- 结果形状可被程序稳定读取。
- 行动意图与真实执行分离。
- 程序能够校验、拒绝和回填工具结果。

当前机制仍未解决：

- 模型何时继续调用工具，何时回答用户。
- 一次调查最多执行多少步、花多少 Token 和时间。
- 工具失败后应该重试、换工具还是停止。
- 模型声称“已完成”时怎样验证业务目标。
- 多轮状态怎样持久化和恢复。

这自然引出下一 CU 的中心问题：

```text
一次受控工具调用
  ↓
怎样演进成可继续、可验证、可停止的 Agent Loop？
```

## 自测问题

1. 为什么 Temperature 降到最低也不能保证事实正确？
2. Transformer 的自注意力解决了什么，它为什么不会自动读取发布系统？
3. 模型 API 的停止状态为什么不等于 Agent 任务完成？
4. Structured Output 能证明什么，不能证明什么？
5. Function Calling 与真实函数执行之间隔着哪些程序步骤？
6. 为什么工具参数通过 Schema 后仍要做业务和权限校验？
7. 工具结果为什么必须回填，而不是只记录在程序日志中？
8. 如果删除“程序校验”这一步，整条链最先出现什么风险？
9. 本 CU 为什么把工具选择与结果回填放在一起学习？
10. 下一 CU 为什么应该学习 Agent Loop，而不是立刻学习 Memory？
