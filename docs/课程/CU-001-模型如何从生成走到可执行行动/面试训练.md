## 1. 语言模型为什么能生成合理答案，却不能直接保证事实正确？

题型：原理型

一句话核心判断：语言模型优化的是上下文条件下的下一 Token 生成，不是对外部事实数据库做强一致查询。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 会把流畅度、概率和事实正确性混为一谈 |
| 最小机制是什么 | Token 化、上下文表示、下一 Token 概率和逐步解码 |
| 工程收益 | 能判断何时需要检索、工具和确定性验证 |
| 边界和代价 | 即使降低随机性，模型仍可能稳定地产生错误答案 |

30 秒回答：

> 语言模型先把输入切成 Token，再通过 Transformer 根据当前上下文计算下一 Token 的概率，并自回归地逐步生成。它擅长生成符合上下文和训练分布的候选，但不会自动查询当前发布系统，所以流畅和高概率不等于事实正确。真实 Agent 必须用工具读取外部状态，再用程序验证结果。

完整回答：

模型生成可以拆成四步：Tokenizer 将文本变成 Token；位置和自注意力让模型组合上下文关系；模型计算下一个 Token 的概率分布；解码策略选出 Token 并继续生成。这个目标决定了模型优先产生“在当前上下文中像合理续写”的内容。

事实错误主要来自三类边界：模型参数中的知识可能过期，当前上下文可能缺少关键事实，解码过程还具有非确定性。即使把随机性降得很低，也只能提高输出稳定性，不能把缺失证据补成真实证据。

因此工程上要分层：模型负责提出假设和行动意图，工具负责读取真实世界，确定性程序负责校验权限、副作用和成功条件。

ASCII 图或关键表：

```text
上下文 → 下一 Token 概率 → 逐步生成 → 候选答案
                                  ↓
                           不自动等于真实事实
```

追问：

- 原理追问：自注意力和位置编码分别解决什么问题？
- 工程追问：怎样判断错误来自模型能力、上下文缺失还是工具结果错误？
- 项目追问：你如何在发布调查 Agent 中阻止模型编造根因？

证据：

使用相同问题重复采样，并对比“无工具直接回答”和“读取真实发布记录后回答”的 Trace。

## 2. Temperature、Top-p 和上下文窗口如何影响 Agent 行为？

题型：原理与调参型

一句话核心判断：Temperature 和 Top-p 影响候选 Token 的选择分布，上下文窗口限制模型本轮能看到的信息；三者都不能单独保证任务正确。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 会把采样稳定性、信息容量和事实正确性混成一个参数问题 |
| 最小机制是什么 | 调整候选分布，限制输入输出 Token 总量 |
| 工程收益 | 可以按创意、稳定性、延迟和上下文需求配置调用 |
| 边界和代价 | 参数过度收紧可能降低探索，窗口变大也可能增加噪声和成本 |

30 秒回答：

> Temperature 和 Top-p 控制模型从下一 Token 候选分布中怎样选，主要影响多样性和稳定性；上下文窗口限制本轮输入和输出能放多少 Token。低 Temperature 不等于事实正确，大窗口也不等于模型一定使用了关键信息，所以 Agent 还需要上下文选择、工具和验证。

完整回答：

Temperature 通常改变概率分布的平滑程度，Top-p 将采样限制在累计概率达到阈值的候选集合中。它们影响“怎样从候选中选”，并不改变外部事实是否已经进入上下文。

上下文窗口解决容量上限，但窗口更大仍有三个问题：信息可能根本没有被放入，关键信息可能被噪声淹没，输入 Token、延迟和成本会上升。

Agent 调参时要先定位问题层：输出风格不稳定可以看解码；证据缺失要看检索或工具；上下文冲突要看选择和压缩；业务错误要看校验和验证，不能先用参数掩盖系统问题。

ASCII 图或关键表：

| 变量 | 主要影响 | 不直接保证 |
|---|---|---|
| Temperature | 分布随机性 | 事实正确 |
| Top-p | 候选集合范围 | 证据完整 |
| 上下文窗口 | 本轮容量 | 信息一定被使用 |

追问：

- 原理追问：为什么低 Temperature 仍可能稳定输出错误？
- 工程追问：长上下文退化时先检查哪些证据？
- 项目追问：发布调查场景为什么不能只把所有日志塞进窗口？

证据：

同一输入的多次采样结果、上下文长度对比和关键证据位置实验。

对应推导章节：

阶段一的输出生成、解码参数和幻觉边界。

## 3. 一次模型调用的输入、输出和停止条件分别是什么？

题型：协议型

一句话核心判断：一次调用接收有角色的消息、指令和运行参数，返回文本或结构化输出项、用量、状态和错误；本轮停止不等于 Agent 任务完成。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 程序无法区分任务输入、模型输出、工具结果和调用状态 |
| 最小机制是什么 | 消息角色、请求参数、响应项、Usage、停止或错误语义 |
| 工程收益 | 可以追踪、重试、计费并接入执行循环 |
| 边界和代价 | 不同供应商字段不同，需要抽象但不能抹平语义差异 |

30 秒回答：

> 输入通常包括 System 或 Developer 约束、User 任务、历史 Assistant 内容和 Tool 结果，再加模型与解码参数。输出可能是文本、结构化数据或工具调用，同时带 Usage、响应状态、停止原因或错误。停止只说明这一次模型生成结束，Agent 是否完成还要看业务验收和后续工具结果。

完整回答：

输入层要区分长期规则、当前用户任务、模型历史输出和环境反馈，因为它们拥有不同来源和信任级别。请求还可能包含模型选择、输出约束、工具定义、超时和追踪信息。

输出层不能只读取一段正文。程序还要识别输出项类型、工具调用参数、Token 用量、本轮是否完整以及错误发生在哪一层。部分 API 使用`finish_reason`，其他 API 使用状态、不完整原因或事件类型表达停止语义。

最重要的边界是：模型本轮停止可能因为自然结束、长度限制、工具调用或错误；即使自然结束，也不能证明发布调查的业务目标已经完成。

ASCII 图或关键表：

```text
角色消息 + 运行参数
        ↓
      模型 API
        ↓
内容 / 工具调用 / Usage / 状态 / 错误
```

追问：

- 原理追问：Tool 消息为什么不能和 User 消息混在一起？
- 工程追问：请求超时后怎样避免盲目重复副作用？
- 项目追问：你会记录哪些字段把模型调用和工具调用串成 Trace？

证据：

打印一次完整请求、输出项、Usage、停止状态、错误响应和 Trace ID。

对应推导章节：

阶段二：真实 API 怎样把生成能力接入程序。

## 4. Structured Output 和 Function Calling 有什么区别？

题型：概念边界型

一句话核心判断：Structured Output(结构化输出)约束返回的数据形状，Function Calling(函数式工具调用)表达调用外部能力的意图；两者都不代表真实动作已经成功。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 会把“返回结构化数据”和“请求执行工具”误认为同一件事 |
| 最小机制是什么 | 前者用 Schema 约束输出，后者返回工具名、参数和调用关联 |
| 工程收益 | 分别解决稳定解析和外部能力编排 |
| 边界和代价 | Schema 只验证形状，工具调用仍需执行器和结果回填 |

30 秒回答：

> Structured Output 的目标是让模型返回符合 Schema 的数据，适合分类、抽取和计划；Function Calling 的目标是让模型选择工具并生成参数，程序随后校验、执行并回填结果。结构合法不等于事实正确，工具调用出现也不等于工具已经执行。

完整回答：

如果任务是“输出一份调查计划”，Structured Output 可以约束`hypotheses`和`next_action`字段，程序因此不必解析自然语言。

如果任务是“读取真实发布记录”，需要 Function Calling 或更广义的 Tool Calling。模型根据工具描述产生调用意图，执行控制权回到程序。程序完成结构、业务、权限和副作用校验，再调用真实工具。

两者可以组合：工具参数本身受 Schema 约束，工具结果也可以结构化；但它们解决的层次不同，一个解决数据契约，一个解决行动协议。

ASCII 图或关键表：

| 机制 | 解决的问题 | 下一步 |
|---|---|---|
| Structured Output | 输出怎样稳定解析 | 程序消费数据 |
| Function Calling | 模型想调用什么能力 | 程序校验并执行 |

追问：

- 原理追问：合法 JSON、符合 Schema 和业务正确分别是什么关系？
- 工程追问：工具结果是否也应该有 Schema？
- 项目追问：发布调查计划和读取发布记录分别选哪一种机制？

证据：

对比自由文本计划、Schema 约束计划和一次真实工具调用的三段响应。

对应推导章节：

阶段三和阶段四。

## 5. Function Calling 从模型产生请求到真实工具执行，完整链路是什么？

题型：链路型

一句话核心判断：工具调用是一段“模型提出意图、程序恢复控制、工具真实执行、结果再次回填”的协议闭环。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 模型只能描述动作，或系统会误把描述当成执行结果 |
| 最小机制是什么 | 工具定义、工具选择、参数生成、校验、执行、结果回填 |
| 工程收益 | 可以引入权限、审批、重试、审计和真实环境反馈 |
| 边界和代价 | 工具描述和错误语义需要设计，副作用工具还要处理幂等与补偿 |

30 秒回答：

> 程序先把工具名称、描述和参数 Schema 提供给模型；模型返回工具和参数意图；程序验证结构、业务、权限和副作用后执行真实工具；再把带调用关联的结果回填给模型，让它基于新事实继续生成。模型负责选择和参数候选，程序负责执行控制。

完整回答：

完整链路有六步。第一，程序注册工具契约。第二，模型根据任务选择工具并生成参数。第三，程序把模型输出视为不可信输入。第四，执行器校验参数和权限，必要时等待人工审批。第五，工具访问真实系统并返回成功或分类错误。第六，程序将结果回填，模型再决定继续调用工具还是形成答案。

工程上还要记录调用关联、Trace ID、超时、重试语义和幂等键。只记录模型“想调用什么”无法证明工具执行成功；只记录工具成功也无法证明业务目标完成。

ASCII 图或关键表：

```text
工具定义
  ↓
模型选择 + 参数
  ↓
结构 / 业务 / 权限 / 副作用校验
  ↓
真实执行
  ↓
结果或分类错误回填
  ↓
模型继续
```

追问：

- 原理追问：模型如何知道有哪些工具可用？
- 工程追问：工具超时后什么时候可以安全重试？
- 项目追问：你怎样证明回滚工具没有被重复执行？

证据：

保存原始请求、工具调用项、校验日志、工具返回、回填项和下一轮模型输出。

对应推导章节：

阶段四和阶段五。

## 6. 工具参数通过 Schema 校验后，为什么还需要业务校验和权限校验？

题型：安全与工程型

一句话核心判断：Schema 只证明参数形状合法，业务校验判断动作是否有意义，权限校验判断当前主体是否被允许执行。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 格式正确的模型输出也可能触发越权、重复或错误副作用 |
| 最小机制是什么 | 结构、业务、权限和副作用四层校验 |
| 工程收益 | 将模型错误限制在执行边界之前，并留下可审计拒绝原因 |
| 边界和代价 | 校验规则需要与真实业务状态和权限系统保持一致 |

30 秒回答：

> Schema 只能保证字段、类型和枚举正确，不能证明发布存在、当前状态允许回滚、用户有权限或操作不会重复。模型参数必须被当成不可信输入，执行器还要做业务、权限、审批和幂等校验，失败时返回明确错误，而不是让模型自己判断自己是否有权执行。

完整回答：

四层校验分别解决不同风险。结构校验拦截缺字段和类型错误；业务校验读取真实状态，判断动作在当前阶段是否成立；权限校验结合用户、任务和环境决定是否允许；副作用校验处理审批、幂等、影响范围和补偿。

把这些判断交给模型有两个问题：模型看不到完整权限事实，而且它的输出本身就是待校验输入。正确做法是让确定性程序拥有最终控制权，并把`permission_denied`、`approval_required`或`invalid_state`等分类错误回填给模型。

ASCII 图或关键表：

```text
模型参数
  ↓
Schema
  ↓
业务状态
  ↓
用户与任务权限
  ↓
审批 / 幂等 / 影响范围
  ↓
执行或拒绝
```

追问：

- 原理追问：为什么模型不能通过 Prompt 获得真实权限？
- 工程追问：业务校验失败和权限失败应该使用同一种重试策略吗？
- 项目追问：发布回滚审批通过后，你如何防止旧调用被重放？

证据：

构造一个参数格式完全合法但缺少审批的回滚请求，证明工具未执行、错误可分类、审计记录完整。

对应推导章节：

阶段五和失败链路。
