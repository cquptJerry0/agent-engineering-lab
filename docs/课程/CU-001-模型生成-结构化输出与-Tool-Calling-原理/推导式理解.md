```text
知识点群 A：模型怎样生成候选
  ↓ 暴露“候选不等于事实”
知识点群 B：API 怎样承载一次调用
  ↓ 暴露“自由文本难解析”
知识点群 C：结构化输出怎样约束形状
  ↓ 暴露“形状正确不等于行动”
知识点群 D：工具调用怎样表达行动意图
  ↓ 暴露“意图仍是不可信输入”
知识点群 E：程序怎样校验、执行和回填
  ↓ 暴露“单次行动还没有形成循环”
```

## 核心推导链

```text
[用户任务]
    │ 被切分为
    ▼
[Token 序列]
    │ 经过上下文关系计算和逐步解码
    ▼
[候选文本]
    │ 可能非确定、过期或幻觉
    ▼
[消息与请求协议]
    │ 能传输，但自由文本难以稳定解析
    ▼
[结构化输出]
    │ 形状稳定，但不代表真实行动
    ▼
[工具调用意图]
    │ 交还程序控制权
    ▼
[结构 / 业务 / 权限 / 副作用校验]
    │ 通过后才允许
    ▼
[真实工具执行]
    │ 将结果或分类错误
    ▼
[回填给模型]
    │ 形成下一轮的新事实
    ▼
下一问题：怎样继续、验证和停止？
```

核心判断：

> 模型负责产生候选内容和行动意图；确定性程序负责真实状态、权限、副作用和验收。

## 贯穿案例与初始状态

使用同一个研发 Agent 调查发布失败：

| 项目 | 内容 |
|---|---|
| 用户目标 | 调查`release-20260810-1427`为什么失败，并给出有证据的处理建议 |
| 初始输入 | 发布编号和用户问题 |
| 初始状态 | 尚未读取发布记录、日志和监控 |
| 可用工具 | `get_release`、`query_logs`、`query_metrics`、`rollback_release` |
| 权限边界 | 查询工具只读；回滚必须经过审批 |
| 真实副作用 | `rollback_release`会改变线上发布状态 |
| 成功标准 | 根因可回链证据，不把建议写成已执行，不发生越权和重复回滚 |

系统会从`V0：直接问模型`演进到`V4：受控工具行动`。发布编号、用户目标和权限边界始终保持不变。

## 阶段一：语言模型生成原理

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与后续阶段的关系 |
|---|---|---|
| Token、Tokenizer 与上下文窗口 | 模型到底接收什么 | 决定请求能放入多少信息 |
| Transformer、自注意力与位置编码直觉 | 模型怎样组合上下文 | 决定候选生成依赖哪些输入 |
| 自回归生成与下一 Token 预测 | 输出怎样逐步产生 | 解释为什么输出是候选 |
| 解码参数与非确定性 | 候选怎样被选择 | 解释稳定性和正确性的区别 |
| 幻觉、知识截止与上下文依赖 | 候选为什么可能错误 | 推导出必须读取外部事实 |

### 当前问题

V0 只有一次模型调用：

```text
用户：调查 release-20260810-1427 为什么失败
  ↓
模型：可能是配置错误，建议回滚
```

模型没有读取发布系统，却给出了看似完整的根因和建议。我们需要先理解：这段文字究竟是怎样产生的？

### 推导过程

1. 模型不能直接处理无限长自然语言，需要先把文本变成有限 Token 序列。
2. 模型需要结合 Token 内容和位置，计算当前上下文中哪些信息相关。
3. 模型逐个选择下一 Token，形成完整输出。
4. 解码策略可以改变候选选择，却不能补出缺失的真实发布数据。
5. 所以 V0 的输出只能是候选分析，不能成为发布事实。

### 机制全解

#### 1. Token、Tokenizer 与上下文窗口

Tokenizer(文本切分器)把文本转换成 Token(模型处理文本的基本单位)。Token 可能是完整词、词的一部分、标点或其他编码片段。

```text
文本
  └─ Tokenizer 切分 → Token ID 序列
                         └─ 进入模型
```

上下文窗口限制一次调用中输入 Token 和输出 Token 的总容量。窗口是容量边界，不是记忆能力保证：

- 信息没放入窗口，模型本轮看不到。
- 信息放入窗口，不代表模型一定正确使用。
- 信息越多，成本、延迟和噪声可能越高。

#### 2. Transformer、自注意力与位置编码

Transformer 负责把 Token 序列转换成上下文相关表示。Self-Attention(自注意力机制)让一个位置根据其他位置的信息更新自己；位置编码补充顺序。

以两句话为例：

```text
服务异常导致数据库超时
数据库超时导致服务异常
```

Token 大体相同，但顺序和因果方向不同。位置编码保留顺序，自注意力组合“谁和谁相关”。

自注意力只处理当前输入和模型参数中的模式，不会自动访问发布数据库。

#### 3. 自回归生成

模型按下面的条件概率逐步生成：

```text
P(token_1 | 当前上下文)
P(token_2 | 当前上下文, token_1)
P(token_3 | 当前上下文, token_1, token_2)
...
```

每一步选择都会进入下一步上下文。早期错误可能继续影响后续内容，因此一段长答案可能从一个错误假设逐步扩展得越来越完整。

#### 4. 解码参数与非确定性

Temperature 和 Top-p 等参数影响怎样从候选 Token 分布中选择：

| 参数或因素 | 主要影响 | 不直接保证 |
|---|---|---|
| Temperature | 分布的随机性和集中程度 | 事实正确 |
| Top-p | 参与采样的候选范围 | 证据完整 |
| Stop | 在指定模式下停止生成 | 任务完成 |
| 随机采样 | 同一输入的输出差异 | 工程可验证性 |

降低随机性可以让回答更稳定，但模型可能稳定地重复同一个错误。

#### 5. 幻觉、知识截止与上下文依赖

三者是不同故障来源：

| 问题 | 含义 | 发布案例 |
|---|---|---|
| 幻觉 | 生成了没有证据支持的内容 | 编造不存在的配置变更 |
| 知识截止 | 模型参数没有当前事实 | 不知道今天的发布记录 |
| 上下文依赖 | 本轮答案依赖提供的信息 | 没有日志就只能根据模式猜测 |

### 状态变化

| 维度 | 进入阶段前 | 完成理解后 |
|---|---|---|
| 输入认知 | 模型直接读懂自然语言 | 文本先变成有限 Token 序列 |
| 输出认知 | 模型给出答案 | 模型逐步生成候选 |
| 事实来源 | 默认相信模型 | 外部事实必须额外读取 |
| 控制权 | 模型看似拥有结论权 | 程序必须区分候选和事实 |
| 仍未解决 | 不知道模型为何会错 | 还没有真实调用协议 |

### 阶段结论

模型擅长根据上下文生成候选，但它不拥有当前发布事实。解码稳定性不能替代外部证据。

## 阶段二：模型 API 请求响应协议

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与前后阶段的关系 |
|---|---|---|
| 消息角色与请求结构 | 不同来源的信息怎样分层传输 | 承接阶段一的上下文输入 |
| Usage、Finish Reason 与错误响应 | 一次调用怎样被观察 | 为后续循环、预算和错误处理提供数据 |

### 当前问题

如果程序只是拼接一段长字符串，就无法区分系统规则、用户输入、模型历史和工具事实，也无法判断本轮是正常结束、长度耗尽还是调用失败。

### 推导过程

1. 不同信息拥有不同来源、优先级和信任级别。
2. 程序需要结构化请求，而不是无法追踪的字符串拼接。
3. 程序不仅要读取正文，还要读取用量、停止状态和错误。
4. 有了真实协议，模型才能成为可观察的软件组件。

### 机制全解

#### 1. 消息角色

通用角色职责：

| 角色 | 主要内容 | 信任和边界 |
|---|---|---|
| System / Developer | 系统级规则、工具边界和运行约束 | 不应被普通用户输入覆盖 |
| User | 当前用户目标和数据 | 属于任务输入，不自动可信 |
| Assistant | 模型历史输出和行动意图 | 是候选，不是环境事实 |
| Tool | 工具真实返回或分类错误 | 来自外部执行器，仍需检查来源 |

供应商的具体角色名称和优先级可能不同，但“规则、用户任务、模型输出、环境反馈分离”的设计目标稳定。

#### 2. 请求结构

本案例最小请求：

```json
{
  "instructions": "先调查证据；未经审批不得回滚",
  "input": [
    {
      "role": "user",
      "content": "调查 release-20260810-1427 为什么失败"
    }
  ]
}
```

真实请求通常还包含模型、解码参数、工具定义、输出约束、超时和追踪信息。

#### 3. 响应观察

| 观察项 | 回答的问题 | 不代表 |
|---|---|---|
| 内容或输出项 | 本轮生成了什么 | 内容正确 |
| Usage | 消耗了多少 Token | 任务高质量 |
| Finish Reason 或响应状态 | 本轮为何停止 | Agent 已完成 |
| 错误响应 | 请求在哪一层失败 | 业务根因已找到 |
| Trace ID | 怎样关联调用和日志 | 调用一定成功 |

不同 API 可能使用`finish_reason`、响应状态、不完整原因或事件类型表达停止语义。应该抽象“本轮为什么结束”，不要只记字段名。

### 状态变化

| 维度 | 进入阶段前 | 引入协议后 |
|---|---|---|
| 输入 | 一段混合字符串 | 有角色和字段的请求 |
| 状态 | 只有聊天文本 | 可记录请求、响应、用量和错误 |
| 控制权 | 难以区分模型与程序 | 程序能够检查响应类型 |
| 输出 | 只读取正文 | 同时读取内容、状态和错误 |
| 仍未解决 | 无法稳定接入模型 | 自由文本仍难被程序消费 |

### 阶段结论

API 把模型变成可调用、可观察的软件组件，但自由文本仍然没有稳定数据契约。

### 下一问题

怎样让模型输出的字段和类型稳定，避免程序解析自然语言？

## 阶段三：Structured Output 与 Schema 约束

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与前后阶段的关系 |
|---|---|---|
| Structured Output 与 Schema | 模型输出怎样被程序稳定解析 | 承接请求协议，引出工具行动 |

### 当前问题

模型返回：

```text
先查发布记录，再看日志，如果确认配置错误再考虑回滚。
```

人能理解，但程序要从句式中猜步骤。模型稍微换个表达，解析器就可能失效。

### 推导过程

1. 程序需要字段、类型和枚举，而不是依赖自然语言句式。
2. Schema 可以定义输出的数据契约。
3. 结构化输出减少解析歧义。
4. 但字段满足 Schema 仍不能证明内容真实或动作允许。

### 机制全解

Structured Output(结构化输出)让模型按照 Schema(字段约束)产生结果。

调查计划示例：

```json
{
  "hypotheses": [
    {
      "name": "发布配置错误",
      "required_evidence": ["release_record", "error_log"]
    }
  ],
  "next_action": "get_release"
}
```

Schema 可以约束：

- 必填字段。
- 字段类型。
- 枚举取值。
- 数组元素结构。
- 是否允许额外字段。

需要区分四层正确性：

```text
JSON 可解析
  ↓
符合 Schema
  ↓
业务语义合理
  ↓
事实和权限真实
```

前一层成立不自动推出后一层。下面的数据可以符合 Schema，但业务上仍然错误：

```json
{
  "hypotheses": [],
  "next_action": "rollback_release"
}
```

### 状态变化

| 维度 | 进入阶段前 | 引入结构化输出后 |
|---|---|---|
| 输入 | 消息和请求 | 消息、请求和输出 Schema |
| 状态 | 保存自由文本 | 保存可验证字段 |
| 控制权 | 程序猜测模型意图 | 程序先校验输出形状 |
| 输出 | 句式不稳定 | 字段和类型稳定 |
| 仍未解决 | 难解析 | 没有表达真实工具执行 |

### 阶段结论

Structured Output 解决的是“数据长什么样”，不解决“外部动作是否已经执行”。

### 下一问题

怎样让模型明确表达“要调用哪个工具、参数是什么”，同时把执行权留给程序？

## 阶段四：Tool Calling 协议与行动意图

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与前后阶段的关系 |
|---|---|---|
| Function Calling 与 Tool Calling | 模型怎样请求外部能力 | 承接结构化数据，引出程序执行边界 |

### 当前问题

结构化计划中的`next_action: get_release`只是一段数据。系统还需要定义工具、识别调用、关联执行结果。

### 推导过程

1. 程序把可用工具和参数契约提供给模型。
2. 模型根据任务生成工具名和参数候选。
3. 模型返回调用意图后暂停本轮生成。
4. 程序恢复控制权，决定是否执行。
5. 工具结果必须关联原调用并回填。

### 机制全解

工具定义示例：

```json
{
  "name": "get_release",
  "description": "读取指定发布的状态、变更和失败阶段",
  "parameters": {
    "type": "object",
    "properties": {
      "release_id": {"type": "string"}
    },
    "required": ["release_id"],
    "additionalProperties": false
  }
}
```

模型调用意图：

```json
{
  "tool": "get_release",
  "arguments": {
    "release_id": "release-20260810-1427"
  }
}
```

Function Calling(函数式工具调用)通常强调函数名和参数；Tool Calling(广义工具调用)还可以包含搜索、文件、浏览器和其他环境能力。

完整边界：

```text
模型选择工具并生成参数
  ≠
程序批准执行
  ≠
工具执行成功
  ≠
业务目标完成
```

### 状态变化

| 维度 | 进入阶段前 | 引入工具调用后 |
|---|---|---|
| 输入 | 输出 Schema | 工具定义和参数 Schema |
| 状态 | 保存计划字段 | 保存工具调用 ID、名称和参数 |
| 控制权 | 模型输出计划 | 调用意图后程序恢复控制 |
| 输出 | 结构化计划 | 明确工具调用请求 |
| 仍未解决 | 没有行动协议 | 参数仍是不可信输入 |

### 阶段结论

Tool Calling 只让模型表达行动意图。它最重要的价值是把真实执行控制权交还给程序。

### 下一问题

模型给出的参数可能格式正确但越权、无意义或具有重复副作用。程序怎样把意图变成安全执行？

## 阶段五：工具执行控制与结果回填

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与前后阶段的关系 |
|---|---|---|
| 工具选择、参数校验与结果回填 | 行动意图怎样变成真实、可观察的结果 | 完成 CU-001，作为 Agent Loop 的单步基础 |

这一知识点本身包含三个连续子机制：

```text
工具选择
  ↓
参数与权限校验
  ↓
执行结果回填
```

### 当前问题

模型已经请求`rollback_release`，参数也符合 Schema。系统能否直接执行？

不能。模型输出始终是不可信输入，Schema 只能验证形状。

### 推导过程

1. 工具选择必须来自当前允许的工具集合。
2. 参数先做结构校验，再做业务状态和权限校验。
3. 有副作用的工具还需要审批、幂等和影响范围控制。
4. 工具执行后，程序不能只写日志，还要把结果回填给模型。
5. 模型下一轮才能基于新事实继续判断。

### 机制全解

#### 1. 工具选择

工具选择不是“模型想用什么就用什么”。程序先根据用户、任务和环境过滤可见工具，模型只能在允许集合中提出候选。

工具定义需要清晰区分：

- 工具解决什么问题。
- 什么情况下不应该调用。
- 参数的业务含义。
- 成功和失败返回什么。
- 是否产生副作用。

#### 2. 四层校验

| 层次 | 检查内容 | 发布案例 |
|---|---|---|
| 结构校验 | 字段、类型、枚举和必填项 | `release_id`是否缺失 |
| 业务校验 | 真实状态是否允许动作 | 发布是否处于可回滚状态 |
| 权限校验 | 当前主体是否允许执行 | 用户是否拥有回滚权限 |
| 副作用校验 | 审批、幂等和影响范围 | 是否已审批、是否重复回滚 |

模型不能给自己授权，也不能用一句“用户已确认”代替真实审批记录。

#### 3. 执行

只有校验全部通过，执行器才调用真实工具。执行器负责：

- 设置超时和取消。
- 记录调用关联和审计信息。
- 对写操作使用幂等键。
- 区分成功、可重试失败和永久失败。

#### 4. 结果回填

成功结果：

```json
{
  "release_id": "release-20260810-1427",
  "status": "failed",
  "failed_stage": "health_check",
  "change": "PAYMENT_TIMEOUT_MS: 800 -> 80"
}
```

失败结果：

```json
{
  "error_type": "approval_required",
  "retryable": false,
  "message": "回滚需要用户审批"
}
```

回填需要包含调用关联、结果数据和失败语义。只回填“失败了”，模型无法判断应该改参数、申请审批、换工具还是停止。

#### 5. 最小行动闭环

```text
模型提出工具候选
  ↓
程序校验工具和参数
  ↓
执行器访问真实环境
  ↓
真实结果或分类错误
  ↓
回填为下一轮上下文
```

这叫“最小行动闭环”，因为系统已经完成一次`意图 → 执行 → 反馈`，但还没有定义多轮循环和任务完成条件。

### 状态变化

| 维度 | 进入阶段前 | 形成最小行动闭环后 |
|---|---|---|
| 输入 | 工具调用意图 | 意图、身份、业务状态和审批状态 |
| 状态 | 待执行参数 | 校验结果、执行结果和调用关联 |
| 控制权 | 模型提出动作 | 程序决定执行、拒绝或等待审批 |
| 输出 | 工具请求 | 真实结果或分类错误 |
| 副作用 | 尚未发生 | 仅在校验通过后发生 |
| 仍未解决 | 参数不可信 | 多轮怎样继续、验证和停止 |

### 阶段结论

最小行动闭环包含工具选择、分层校验、真实执行和结果回填。模型拥有候选权，程序拥有执行权。

### 下一问题

一次受控行动完成后，系统怎样决定下一步、限制循环、验证完成并安全停止？

## 正常链路与失败链路

### 正常链路

```text
用户任务
  └─ 模型请求 get_release
       └─ 程序校验通过
            └─ 工具返回发布状态
                 └─ 结果回填
                      └─ 模型请求 query_logs
                           └─ 工具返回 timeout 证据
                                └─ 模型形成有证据的建议
```

### 失败链路

```text
模型请求 rollback_release
  └─ Schema 校验：通过
       └─ 业务校验：缺少根因证据
            └─ 权限校验：没有审批
                 └─ 程序拒绝执行
                      └─ 回填 approval_required
                           └─ 模型改为请求审批或停止
```

对照结论：

| 机制 | 正常链路中的作用 | 失败链路中的作用 |
|---|---|---|
| Schema | 保证参数形状 | 不能阻止越权 |
| 业务校验 | 确认动作当前有意义 | 拒绝错误状态 |
| 权限校验 | 确认主体被允许 | 拒绝越权 |
| 结果回填 | 提供下一轮事实 | 提供可恢复的失败语义 |

## 实验任务卡

以下实验是学习任务，不是已经完成的证据。

### 实验任务一：观察解码稳定性和事实正确性的区别

实验目标：证明“输出更稳定”不等于“事实更正确”。

覆盖知识点：自回归生成、解码参数与非确定性、幻觉与上下文依赖。

为什么做：如果不亲自比较多次输出，很容易把低随机性误解成可靠性保证。

准备条件：

- 任意可设置采样参数的模型 API 或本地模型。
- 一个不存在于模型上下文中的发布编号。

输入与初始状态：

```text
请判断 release-20260810-1427 失败的根因。
不要调用工具。
```

操作步骤：

1. 使用较低随机性设置调用 3 次。
2. 使用较高随机性设置调用 3 次。
3. 记录每次根因、证据来源和措辞。
4. 检查回答是否引用了真实发布记录。

预期现象：

- 较低随机性下输出通常更相似。
- 较高随机性下假设可能更多样。
- 两组回答都无法提供真实发布证据。

程序断言或人工检查：

```text
稳定性：多次输出是否相似
正确性：结论是否能回链真实数据
```

失败时先看什么：确认两组调用是否真的使用了不同解码设置，输入是否完全相同。

通过标准：能够用实验结果解释“稳定性”和“事实正确性”是两个维度。

产出证据：六次请求响应、参数配置和一张结论对比表。

这个实验没有证明什么：不能证明某个特定模型在所有任务上的幻觉率。

### 实验任务二：证明 Schema 只保证形状

实验目标：构造一个符合 Schema 但业务错误的调查计划。

覆盖知识点：Structured Output 与 Schema。

为什么做：直接看到“校验通过但业务错误”，才能真正理解结构正确性的边界。

准备条件：Python 3；不需要真实模型。

输入与初始状态：

```python
plan = {
    "hypotheses": [],
    "next_action": "rollback_release",
}
allowed_actions = {"get_release", "query_logs", "query_metrics", "rollback_release"}
```

操作步骤：

1. 检查`plan`是否包含`hypotheses`和`next_action`。
2. 检查`next_action`是否在枚举中。
3. 再增加业务规则：没有证据时禁止回滚。
4. 比较结构校验和业务校验结果。

预期现象：

```text
结构校验：通过
业务校验：失败，原因是缺少根因证据
```

程序断言或人工检查：

```python
assert set(plan) == {"hypotheses", "next_action"}
assert plan["next_action"] in allowed_actions
assert not (plan["next_action"] == "rollback_release" and not plan["hypotheses"])
```

失败时先看什么：检查是否把业务规则错误地写进了“字段存在”判断。

通过标准：能够分别说清 JSON 可解析、符合 Schema、业务正确和权限允许。

产出证据：脚本输出和四层正确性说明。

这个实验没有证明什么：没有证明真实模型一定遵守 Schema。

### 实验任务三：手写一次完整 Tool Calling

实验目标：不依赖 Agent 框架，走通`工具意图 → 校验 → 执行 → 回填`。

覆盖知识点：Function Calling 与 Tool Calling、工具选择、参数校验与结果回填。

为什么做：框架会隐藏控制权切换，手写一次才能看清模型没有直接执行工具。

准备条件：Python 3；使用本地模拟的`get_release`工具。

输入与初始状态：

```python
tool_call = {
    "id": "call_001",
    "name": "get_release",
    "arguments": {"release_id": "release-20260810-1427"},
}
```

操作步骤：

1. 校验工具名是否在允许集合。
2. 校验`release_id`字段和类型。
3. 调用本地函数返回模拟发布记录。
4. 生成带`call_001`关联的工具结果。
5. 将工具结果加入下一轮模型输入。

预期现象：

```text
模型输出：工具调用意图
程序输出：校验通过
工具输出：真实或模拟发布记录
回填输出：带调用关联的结果
```

程序断言或人工检查：

```python
assert tool_call["name"] == "get_release"
assert isinstance(tool_call["arguments"]["release_id"], str)
assert tool_result["call_id"] == tool_call["id"]
```

失败时先看什么：先检查调用 ID、工具名和参数，再检查工具函数本身。

通过标准：Trace 中能明确指出哪一步由模型决定，哪一步由程序决定。

产出证据：原始请求、工具调用意图、校验日志、工具结果、回填消息和下一轮输入。

这个实验没有证明什么：没有形成自动继续和停止的 Agent Loop。

### 实验任务四：制造合法但越权的回滚请求

实验目标：证明 Schema 通过后仍必须做业务、权限和副作用校验。

覆盖知识点：工具选择、参数校验与结果回填。

为什么做：这是最容易产生真实事故的边界。

准备条件：

- 一个模拟`rollback_release`工具。
- 当前身份只有只读权限。
- 审批状态为`not_approved`。

输入与初始状态：

```json
{
  "release_id": "release-20260810-1427",
  "reason": "health check failed"
}
```

操作步骤：

1. 运行结构校验，确认字段和类型合法。
2. 运行业务校验，确认发布存在。
3. 运行权限和审批校验。
4. 确认真实回滚函数没有被调用。
5. 回填`approval_required`分类错误。

预期现象：

```text
结构校验：通过
业务校验：通过
权限或审批校验：失败
真实副作用：0
回填结果：approval_required
```

程序断言或人工检查：

```python
assert schema_valid is True
assert rollback_called is False
assert tool_result["error_type"] == "approval_required"
```

失败时先看什么：检查回滚函数是否在所有校验完成前被调用。

通过标准：工具没有执行，错误可分类，模型能据此申请审批或停止。

产出证据：拒绝日志、`rollback_called=False`断言和回填消息。

这个实验没有证明什么：没有覆盖审批通过后的幂等和补偿。

## 边界、代价与下一问题

当前机制已经解决：

| 已解决 | 对应机制 |
|---|---|
| 模型输入和输出可观察 | 消息、请求、响应状态和错误 |
| 程序可以稳定读取结果 | Structured Output 与 Schema |
| 行动意图与执行分离 | Tool Calling |
| 越权和错误动作可以被阻止 | 业务、权限和副作用校验 |
| 模型能获得新事实 | 结果回填 |

当前机制仍未解决：

| 未解决 | 为什么属于下一 CU |
|---|---|
| 何时继续调用工具 | 需要循环决策 |
| 何时回答用户 | 需要停止条件 |
| 最多执行多少步和成本 | 需要预算控制 |
| 工具失败后怎样恢复 | 需要重试和重新规划 |
| 模型声称完成是否可信 | 需要 Verification |
| 重复调用和无进展怎样阻断 | 需要循环状态与故障检测 |

下一 CU：

```text
一次受控工具行动
  └─ 演进为 → 可继续、可验证、可停止的 Agent Loop
```

## 自测题与答案

### 题目一：为什么降低 Temperature 不能保证事实正确？

参考答案：Temperature 主要影响怎样从候选 Token 分布中选择，降低它可以让输出更集中、更稳定，但不会把缺失的发布事实放入上下文，也不会让模型自动查询真实系统。

判分点：

- 1 分：说明 Temperature 影响采样稳定性。
- 1 分：说明事实正确依赖真实证据或外部工具。

常见误区：把“每次说法一样”当成“每次都正确”。

### 题目二：自注意力解决了什么，为什么不会自动读取发布系统？

参考答案：自注意力计算当前 Token 与上下文其他 Token 的关系，用于构造上下文相关表示；它的输入仍然是当前 Token 序列和模型参数，不包含对发布数据库的自动访问。

判分点：

- 1 分：说明上下文内关系计算。
- 1 分：说明外部系统需要显式工具。

常见误区：把 Attention 理解成全局互联网搜索。

### 题目三：模型 API 的停止状态为什么不等于 Agent 任务完成？

参考答案：停止状态只解释本次模型生成为什么结束，例如自然结束、长度限制、工具调用或错误；Agent 完成还要满足业务验收、工具结果和终止条件。

判分点：

- 1 分：区分单次模型调用和完整任务。
- 1 分：指出业务验收或工具结果。

常见误区：看到模型输出“完成了”就结束循环。

### 题目四：Structured Output 能证明什么，不能证明什么？

参考答案：它可以证明结果满足字段、类型和枚举等 Schema 约束；不能证明字段内容真实、业务动作合理、当前用户有权限或副作用已经成功。

判分点：

- 1 分：说明结构约束。
- 1 分：说明事实、业务或权限边界。

常见误区：把合法 JSON 当成可信业务参数。

### 题目五：Function Calling 与真实工具执行之间有哪些步骤？

参考答案：程序提供工具定义，模型生成工具和参数意图，程序恢复控制权并完成结构、业务、权限和副作用校验，然后执行工具，再把结果或错误关联原调用回填。

判分点：

- 1 分：说明模型只生成调用意图。
- 1 分：说明程序校验和执行。
- 1 分：说明结果回填。

常见误区：认为模型返回工具调用项后工具已经运行。

### 题目六：为什么 Schema 校验后仍需要业务和权限校验？

参考答案：Schema 只检查参数形状；业务校验读取真实状态判断动作是否成立；权限校验判断当前主体是否允许执行。三者解决不同问题。

判分点：

- 1 分：区分结构和业务。
- 1 分：区分业务和权限。

常见误区：把权限字段写进 Prompt 就认为权限已验证。

### 题目七：工具结果为什么必须回填给模型？

参考答案：工具结果是模型下一轮决策需要的新事实。只写程序日志，模型上下文仍然不知道真实状态，也无法根据成功或分类错误决定下一步。

判分点：

- 1 分：说明下一轮上下文。
- 1 分：说明成功和失败语义都会改变决策。

常见误区：认为程序知道结果就等于模型知道。

### 题目八：删除程序校验后最先出现什么风险？

参考答案：模型生成的格式合法但业务错误或越权参数会直接产生真实副作用，例如未经审批回滚。最先失去的是确定性执行边界。

判分点：

- 1 分：指出模型参数不可信。
- 1 分：指出真实副作用风险。

常见误区：只讨论解析报错，不讨论越权和事故。

### 题目九：为什么把工具选择、校验和结果回填放在同一知识点群？

参考答案：它们共同完成一次行动的闭环。只有选择没有执行，只有执行没有校验会失控，只有执行没有回填则模型无法继续基于事实决策。

判分点：

- 1 分：说明三者共享同一行动状态。
- 1 分：说明删除任一环节闭环都会断裂。

常见误区：按 API 方法数量机械拆课。

### 题目十：为什么下一步学习 Agent Loop，而不是 Memory？

参考答案：当前系统只有一次受控行动，还不知道怎样继续、验证和停止。Agent Loop 是多轮行动的最小控制结构；Memory 是跨轮或跨任务的信息管理，需要先有运行循环。

判分点：

- 1 分：指出当前缺口是控制流。
- 1 分：说明 Memory 依赖运行过程。

常见误区：把所有多轮问题都归因于记忆不足。

## 知识关系图

```text
一、模型内部：产生候选

[文本]
  └─ 被切分为 → [Token 序列]
                       └─ 经过上下文关系计算 → [上下文表示]
                                                   └─ 逐步预测 → [候选输出]
                                                                      │
                                      解码参数影响选择，不保证事实 ───┘

二、模型与程序边界：约束候选

[系统规则 / 用户任务 / 历史 / 工具结果]
  └─ 按来源组织为 → [消息与请求]
                         ├─ 产生 → [内容 / 用量 / 停止状态 / 错误]
                         └─ 使用 Schema 约束 → [结构化输出]
                                                    └─ 表达 → [工具调用意图]

三、程序与真实环境边界：控制行动

[工具调用意图]
  └─ 交给程序 → [工具选择]
                    └─ 依次通过 → [结构校验]
                                      └─ [业务校验]
                                           └─ [权限与副作用校验]
                                                └─ 允许后 → [真实执行]
                                                               └─ 产生 → [结果或分类错误]
                                                                            └─ 回填给 → [下一轮模型输入]
```

### 如何读图

1. 先读第一层：模型怎样把输入变成候选，理解为什么候选不等于事实。
2. 再读第二层：程序怎样用请求和 Schema 约束候选的表达形式。
3. 最后读第三层：程序怎样接管控制权，让候选行动经过校验后才接触真实环境。
4. 箭头上的动词就是机制关系：`切分`、`预测`、`约束`、`校验`、`执行`、`回填`。

关键结论：

- Token 到候选输出属于模型内部生成链。
- 消息、响应状态和 Schema 属于模型与程序的协议边界。
- 工具校验、执行和回填属于程序与真实环境的控制边界。
- `结果回填`把一次行动的终点变成下一轮模型调用的输入。
