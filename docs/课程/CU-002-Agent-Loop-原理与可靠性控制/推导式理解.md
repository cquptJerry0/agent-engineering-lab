# CU-002：Agent Loop 原理与可靠性控制 - 推导式理解

## 选课依据与覆盖知识点

CU-001 已经解释了一次行动怎样完成：

```text
模型提出工具意图
  → 程序校验
  → 工具执行
  → 结果回填
```

但一次工具调用还不是 Agent。Agent 必须回答：

```text
下一步做什么？
什么时候继续？
失败后怎样恢复？
怎样证明任务完成？
怎样阻止死循环和伪完成？
```

| 2 | ReAct 的机制与局限 | 未开始 | 让观察结果改变下一步决策 |

```text
  ↓

  ↓

  ↓
知识点群 E：死循环、错误累积和指标投机
```

## 核心推导链

```text
[一次受控工具行动]
  │ 只能做一步
  ▼
[Observe → Decide → Act → Result]
  │ 模型可能无限继续
  ▼
[确定性状态 + Stop + 多维预算]
  │ 工具失败不能都用同一种重试
  ▼
[计划 + 错误分类 + Replanning]
  │ 模型可能自报完成但结果不合格
  ▼
[Task Loop + Verification Loop]
  │ 验证不通过
  ▼
[Reflection / Evaluator-Optimizer]
  │ 仍可能重复、震荡或钻指标漏洞
  ▼
[进展检测 + 去重 + 硬门禁]
  │
  ▼
[可继续、可恢复、可验证、可停止的 Agent Loop]
```

核心判断：

> Agent Loop 不是“让模型一直调用工具”，而是由确定性程序持有状态和边界，让模型在每一轮只做有限决策，并用外部证据决定继续、修正或停止。

## 贯穿案例与初始状态

继续使用发布失败调查 Agent。

CU-001 结束时系统已经能完成一次受控工具调用：

| 项目 | 当前状态 |
|---|---|
| 用户目标 | 找到发布失败根因并给出有证据的建议 |
| 已知事实 | 发布在`health_check`阶段失败 |
| 已执行动作 | 已调用`get_release` |
| 新观察 | `PAYMENT_TIMEOUT_MS`从`800`变成`80` |
| 可用工具 | `query_logs`、`query_metrics`、`get_config_history`、`rollback_release` |
| 权限边界 | 回滚仍需要审批 |
| 当前缺口 | 不知道下一步查什么，也没有停止和验证机制 |

我们将同一个系统从`V1：只能做一步`演进到`V5：可验证停止`。

## 阶段一：Agent Loop 循环模型与 ReAct

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与前后阶段的关系 |
|---|---|---|
| Observe、Decide、Act、Verify、Stop 循环 | 一次行动怎样变成多轮闭环 | 提供整个 CU 的骨架 |
| ReAct 的机制与局限 | 工具观察怎样改变下一步决策 | 承接单步工具回填 |
| 工具选择、参数校验与结果回填 | 每一轮动作怎样真实执行 | 复用 CU-001 的行动原语 |

### 当前问题

系统已经拿到发布记录：

```json
{
  "failed_stage": "health_check",
  "change": "PAYMENT_TIMEOUT_MS: 800 -> 80"
}
```

如果程序没有循环控制，它只能停在这里，或者写死下一步一定查日志。怎样让新观察真正改变后续行动？

### 推导过程

1. 工具结果先进入状态，成为下一轮 Observe(观察)。
2. 模型基于目标、当前状态和可用动作做 Decide(决策)。
3. 程序校验并执行 Act(行动)。
4. 工具返回 Result(结果)，程序再做 Verify(验证)。
5. 未满足目标时继续，满足或触发边界时 Stop(停止)。
6. ReAct 的核心价值是让每次观察参与下一次行动选择。

### 机制全解

#### 1. 最小循环的六个职责

| 环节 | 输入 | 输出 | 主要负责人 |
|---|---|---|---|
| Observe | 用户目标、历史状态、工具结果 | 本轮可用观察 | 程序组装 |
| Decide | 观察、允许动作、约束 | 回答或工具候选 | 模型 |
| Act | 工具候选 | 真实工具调用 | 程序 |
| Result | 工具执行 | 结构化结果或错误 | 工具与程序 |
| Verify | 当前状态和验收规则 | 通过、不通过或需人工 | 确定性规则优先 |
| Stop | 验收、预算、错误和人工状态 | 继续或结束 | 程序 |

Reason(推理)可以发生在 Decide 内部，但系统合同不应该依赖模型暴露完整内部推理。工程上需要的是可观察的决策理由、行动参数和证据关联。

#### 2. 循环状态

最小状态至少保存：

```json
{
  "goal": "定位发布失败根因并给出建议",
  "step": 1,
  "observations": [],
  "actions": [],
  "evidence": [],
  "budgets": {},
  "status": "running",
  "last_error": null
}
```

消息历史不等于循环状态。循环状态需要可查询、可验证的字段；消息历史只是模型上下文的一部分。

#### 3. ReAct 的机制

ReAct(边推理边行动)可以抽象为：

```text
观察当前证据
  → 形成下一行动候选
  → 执行工具
  → 获得新观察
  → 更新判断
```

优势：

- 不必一开始知道完整路径。
- 外部结果可以及时纠正假设。
- 适合开放式调查和信息不完整任务。

局限：

- 每一步都可能引入模型错误。
- 容易重复查询和无进展循环。
- 工具结果越多，上下文成本越高。
- 如果没有确定性停止和验证，模型可能一直行动或过早结束。

#### 4. 每轮伪代码

```python
while state["status"] == "running":
    observation = build_observation(state)
    decision = model_decide(observation, allowed_tools)
    action = validate_decision(decision)
    result = execute(action)
    update_state(state, action, result)
    verification = verify(state)
    state["status"] = decide_status(state, verification)
```

模型只负责`model_decide`。状态更新、工具校验、验证和停止由程序控制。

### 状态变化

| 维度 | 进入阶段前 | 引入最小循环后 |
|---|---|---|
| 输入 | 单次工具结果 | 目标、历史状态和最新观察 |
| 状态 | 一段调用记录 | 结构化循环状态 |
| 控制权 | 不知道谁决定下一步 | 模型提候选，程序执行和停止 |
| 输出 | 一次工具结果 | 回答、下一动作或继续状态 |
| 仍未解决 | 只能做一步 | 循环可能无限运行 |

### 阶段结论

Agent Loop 的最小骨架是`观察 → 决策 → 行动 → 结果 → 验证 → 停止或继续`。ReAct 让观察改变后续决策，但它本身不提供可靠边界。

## 阶段二：确定性控制、终止条件与多维预算

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与前后阶段的关系 |
|---|---|---|
| 终止条件、步数和多维预算 | 循环什么时候必须停止 | 防止无限行动 |
| 确定性代码与模型决策边界 | 哪些判断不能交给模型 | 为失败恢复和验证奠定控制权 |

### 当前问题

模型连续三轮调用`query_logs`，每次只改变时间范围。它声称“再查一次就能确认”。系统是否应该继续？

### 推导过程

1. 模型擅长开放决策，但不适合给自己设置不可突破的边界。
2. 程序必须维护步数、时间、Token、成本和副作用预算。
3. 停止不能只有“模型说完成”，还要检查业务验收、预算和安全条件。
4. 模型决策和确定性控制需要明确分层。

### 机制全解

#### 1. 四类停止条件

| 类型 | 示例 | 是否由模型单独决定 |
|---|---|---|
| 成功停止 | 根因有两条独立证据，建议已生成 | 否，需要验收 |
| 资源停止 | 步数、Token、时间或成本耗尽 | 否，程序硬限制 |
| 安全停止 | 需要审批、检测到高风险动作 | 否，策略或人工 |
| 失败停止 | 永久错误、无可用工具、无进展 | 否，错误和状态判断 |

#### 2. 多维预算

只设置最大步数不够：

```json
{
  "max_steps": 8,
  "max_tool_calls": 10,
  "max_tokens": 12000,
  "deadline_ms": 30000,
  "max_cost_usd": 0.2,
  "max_write_actions": 0
}
```

不同预算限制不同风险：

- 步数限制循环长度。
- Token 和成本限制模型消耗。
- 时间限制端到端延迟。
- 写动作预算限制副作用。

#### 3. 确定性代码与模型决策边界

适合模型：

- 从多个合理调查方向中选择下一步。
- 根据非结构化证据形成假设。
- 生成解释和建议。

适合确定性代码：

- 计数、超时和预算。
- Schema、权限和审批。
- 幂等、去重和调用状态。
- 明确业务规则和可计算验收。
- 最终停止权。

判断公式：

```text
开放语义判断、难以枚举
  → 模型给候选

必须稳定、可审计、可重复
  → 确定性代码控制
```

#### 4. 停止优先级

```text
安全策略
  > 资源硬限制
  > 业务验收
  > 模型自报状态
```

模型可以建议停止，但程序必须重新判断。

### 状态变化

| 维度 | 进入阶段前 | 加入控制边界后 |
|---|---|---|
| 输入 | 最新观察 | 观察、预算和安全策略 |
| 状态 | 步骤历史 | 步数、Token、成本、截止时间和风险状态 |
| 控制权 | 模型倾向继续 | 程序拥有硬停止权 |
| 输出 | 下一动作候选 | 允许执行、拒绝或停止 |
| 仍未解决 | 可能无限循环 | 失败后怎样选择恢复策略 |

### 阶段结论

模型可以建议下一步，但程序必须拥有预算、权限和停止权。可靠 Agent 的外壳首先是确定性控制系统。

## 阶段三：Planning、错误路由与局部恢复

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与前后阶段的关系 |
|---|---|---|
| Planning 与边执行边规划 | 任务路径应该提前决定多少 | 为失败后的调整提供基线 |
| Replanning、重试与局部恢复 | 不同失败怎样选择不同恢复动作 | 把错误转成可控状态迁移 |

### 当前问题

`query_logs`返回超时。下面五种动作都可能看起来合理：

```text
原样重试
缩小时间范围后重试
改查监控
重写调查计划
停止并报告
```

如果系统只写“失败后重试”，会把所有错误当成同一类。

### 推导过程

1. 开放任务需要方向，但完整计划可能因新观察快速过期。
2. 先形成轻量计划，再逐步执行，比一次性生成不可变长计划更稳健。
3. 工具失败必须先分类，再选择恢复动作。
4. 可局部修复时不要重启整个任务；前提错误时才 Replanning(重新规划)。

### 机制全解

#### 1. Planning 的三种粒度

| 方式 | 特点 | 适用场景 |
|---|---|---|
| 无显式计划 | 每轮直接决定下一步 | 任务短、动作少 |
| 轻量计划 | 保存目标、假设和下一批动作 | 调查类 Agent |
| 完整计划 | 先拆全部步骤再执行 | 路径稳定、依赖明确 |

本案例适合轻量计划：

```json
{
  "goal": "定位失败根因",
  "hypotheses": ["超时配置错误", "依赖服务异常"],
  "next_actions": ["query_logs", "query_metrics"],
  "evidence_needed": ["错误日志", "超时指标"]
}
```

#### 2. 边执行边规划

```text
计划当前方向
  → 执行一个动作
  → 读取结果
  → 更新假设和后续动作
```

计划是可修改状态，不是模型一次生成后永久正确的合同。

#### 3. 错误分类与恢复动作

| 错误类型 | 示例 | 推荐动作 |
|---|---|---|
| 瞬时错误 | 网络抖动、短暂 503 | 有上限地原样重试 |
| 参数错误 | 时间范围过大 | 修改参数后重试 |
| 业务拒绝 | 发布状态不允许回滚 | 不重试，换方案或停止 |
| 权限错误 | 无回滚权限 | 请求审批或停止 |
| 工具不适用 | 日志没有该指标 | 换工具 |
| 前提被推翻 | 配置未发生变化 | Replanning |
| 永久失败 | 工具已下线 | 降级或退出 |

#### 4. 局部恢复

局部恢复只回退失败节点，不丢弃已有证据：

```text
已完成 get_release
  ↓
query_logs 超时
  ↓
缩小时间范围后重试 query_logs
  ↓
保留已有 release 证据
```

如果每次失败都从头重跑，会增加成本、重复副作用并污染状态。

### 状态变化

| 维度 | 进入阶段前 | 加入计划和恢复后 |
|---|---|---|
| 输入 | 最新错误 | 错误类型、已有证据和当前计划 |
| 状态 | 只有动作历史 | 假设、计划、重试次数和恢复点 |
| 控制权 | 模型笼统说“再试一次” | 程序按错误策略限制恢复 |
| 输出 | 重试或停止 | 改参、换工具、重规划、降级或退出 |
| 仍未解决 | 错误可能重复 | 如何证明最终答案合格 |

### 阶段结论

Planning 提供方向，边执行边规划负责适应新事实；错误分类决定重试、改参、换工具、重规划还是停止。

## 阶段四：Verification Loop 与反馈修正

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与前后阶段的关系 |
|---|---|---|
| Task Loop 与 Verification Loop | 完成动作和证明质量怎样分离 | 建立可靠停止条件 |
| Reflection 与 Self-Correction | 模型怎样根据失败反馈修正 | 适合开放语义问题 |
| Evaluator-Optimizer 循环 | 生成和质量评估怎样分工 | 形成可重复质量闭环 |

### 当前问题

Agent 已经查了发布记录和日志，并回答：

```text
根因是超时配置错误，建议回滚。
```

但业务验收要求：

1. 至少两条独立证据。
2. 解释配置变化如何导致健康检查失败。
3. 未经审批只能给建议，不能执行回滚。

模型说“完成”并没有满足全部要求。

### 推导过程

1. Task Loop 负责推进任务和产生候选结果。
2. Verification Loop 负责检查候选是否满足验收。
3. 验证失败后，系统把具体缺口反馈给生成者。
4. Reflection 或 Self-Correction 可以让模型修正。
5. 更稳定的做法是分离 Evaluator 和 Optimizer。

### 机制全解

#### 1. Task Loop

目标是完成工作：

```text
观察 → 决策 → 行动 → 结果 → 继续
```

输出是候选答案、候选代码或候选方案。

#### 2. Verification Loop

目标是证明候选满足标准：

```text
候选结果
  → 执行确定性检查或评估
  → 通过：允许停止
  → 不通过：返回具体缺口
```

本案例的验证器：

```python
def verify(report):
    return {
        "has_two_sources": len(report["evidence"]) >= 2,
        "explains_causality": bool(report["causal_chain"]),
        "no_unapproved_write": report["rollback_executed"] is False,
    }
```

#### 3. Reflection 与 Self-Correction

Reflection(执行后反思)让模型根据结果分析：

- 哪个假设错了。
- 哪条证据缺失。
- 下一次应该怎样修正。

Self-Correction(自我纠正)是模型根据反馈重新生成。

边界：

- 如果反馈仍然模糊，模型可能只改措辞。
- 模型无法可靠发现自己不知道的事实。
- 权限和业务规则不能由反思替代。

#### 4. Evaluator-Optimizer

```text
Optimizer 生成候选
  ↓
Evaluator 按标准评估
  ↓ 不通过并给出缺口
Optimizer 修正
  ↓
再次评估
```

Evaluator 可以是：

- 确定性代码。
- 单元测试或业务校验器。
- 人工评审。
- 受约束的额外模型。

优先使用确定性证据。只有语义质量难以规则化时，才考虑模型评估，并明确偏差和成本。

### 状态变化

| 维度 | 进入阶段前 | 加入验证循环后 |
|---|---|---|
| 输入 | 候选答案 | 候选答案和明确验收标准 |
| 状态 | 工具执行历史 | 验证结果、缺口和修正次数 |
| 控制权 | 模型自报完成 | 验证器决定是否允许停止 |
| 输出 | 未验证答案 | 通过验收的答案或具体缺口 |
| 仍未解决 | 可能过早完成 | 可能重复修正或钻指标漏洞 |

### 阶段结论

Task Loop 负责“做”，Verification Loop 负责“证明做对”。Reflection 和 Evaluator-Optimizer 只有在反馈具体、次数有限时才有价值。

如果 Agent 一直重复查询、来回修改答案，或者只满足指标表面而没有解决真实问题，怎样发现并阻断？

## 阶段五：进展检测、死循环与 Reward Hacking 防护

### 本阶段知识点群

| 知识点 | 本阶段解决的问题 | 与前后阶段的关系 |
|---|---|---|
| 死循环、重复调用与错误累积 | 怎样识别“忙但没有进展” | 约束 Task 和 Verification 两类循环 |
| Reward Hacking | 怎样防止只满足指标表面 | 保护最终验收真实性 |

### 当前问题

Agent 出现两种异常：

```text
异常 A：
query_logs → 无结果
query_logs → 无结果
query_logs → 无结果

异常 B：
验收要求“至少两条证据”
Agent 把同一条日志复制两次，声称已有两条证据
```

前者是无进展循环，后者是 Reward Hacking(钻评测规则漏洞)。

### 推导过程

1. 单纯限制最大步数只能最终止损，不能及时发现无进展。
2. 程序需要比较状态变化、信息增益和动作重复。
3. 验收指标必须绑定真实目标，不能只数表面字段。
4. 对高风险结果需要独立证据、交叉验证和硬门禁。

### 机制全解

#### 1. 死循环

循环仍在运行，但状态不再接近目标：

```text
动作重复
  +
观察重复
  +
假设不更新
  +
目标距离不下降
```

#### 2. 重复调用

程序可以为动作建立指纹：

```text
fingerprint = tool_name + normalized_arguments
```

同一指纹在状态没有变化时重复出现，应触发：

- 拒绝重复。
- 要求说明新信息。
- 换工具。
- Replanning。
- 停止并报告无进展。

#### 3. 错误累积

错误结果若直接进入上下文，会被后续轮次继续引用：

```text
错误工具结果
  → 错误假设
  → 错误计划
  → 更多错误行动
```

需要记录来源、置信状态和后续是否被推翻，不能把所有历史内容视为同等可信事实。

#### 4. Reward Hacking

系统优化了验收指标，却没有完成真实目标。

发布案例：

| 表面指标 | 投机方式 | 更真实的门禁 |
|---|---|---|
| 两条证据 | 复制同一日志两次 | 来源 ID 必须不同 |
| 根因字段非空 | 填写空泛结论 | 必须有因果链和证据引用 |
| 工具调用成功率高 | 避免调用难工具 | 看任务成功而非调用成功 |
| 回滚建议已生成 | 总是建议回滚 | 先满足回滚业务条件 |

#### 5. 进展检测

每轮记录：

```json
{
  "new_evidence_count": 1,
  "hypothesis_changed": true,
  "repeated_action": false,
  "verification_failures": 0,
  "goal_distance": "closer"
}
```

连续多轮没有新证据、没有状态变化或重复同一动作，应提前停止。

### 状态变化

| 维度 | 进入阶段前 | 加入进展和门禁后 |
|---|---|---|
| 输入 | 当前动作和结果 | 动作指纹、信息增益和验收来源 |
| 状态 | 只记录历史 | 记录重复、进展、证据唯一性和失败次数 |
| 控制权 | 直到预算耗尽才停 | 无进展和投机可提前阻断 |
| 输出 | 形式满足指标 | 结果必须满足真实业务目标 |
| 仍未解决 | Loop 可能失控 | 长任务的持久化和恢复 |

### 阶段结论

可靠循环不仅要有最大步数，还要检测重复动作、状态停滞、错误扩散和指标投机。验收必须绑定真实目标和独立证据。

### 下一问题

当前 Agent 循环可以在一个进程中可靠运行，但长任务中断、进程崩溃或需要人工审批时，状态怎样持久化并恢复？

这个问题会在后续 Graph(状态图运行时)与 Durable Runtime(可恢复运行时)中展开。

## 正常链路与失败链路

### 正常链路

```text
Observe：读取发布状态和现有证据
  ↓
Decide：选择 query_logs
  ↓
Act：程序校验并执行
  ↓
Result：得到 timeout 日志
  ↓
Verify：证据仍不足
  ↓
Plan：查询监控
  ↓
Result：超时指标同步升高
  ↓
Verify：两条独立证据 + 因果链成立
  ↓
Stop：输出建议，等待审批，不执行回滚
```

### 失败链路

```text
query_logs 超时
  ↓
错误被误判为“都可重试”
  ↓
原样重试 5 次
  ↓
没有新证据，Token 和时间持续增长
  ↓
模型自报“已完成”
  ↓
验证器发现证据不足
  ↓
模型复制同一日志满足“两条证据”
  ↓
Reward Hacking
```

修复后的控制：

```text
错误分类
  → 参数超时：缩小时间范围
  → 连续重复：触发 Replanning
  → 证据去重：来源 ID 必须不同
  → 验证通过前禁止 Stop
```

## 实验任务卡

### 实验任务一：手写最小 Agent Loop

实验目标：看清模型决策、程序状态、工具执行和停止判断分别在哪里。

覆盖知识点：Observe、Decide、Act、Verify、Stop 循环；ReAct；工具结果回填。

为什么做：只有亲手写过循环，才能避免把 Agent 理解成“一个自动调用工具的 Prompt”。

准备条件：Python 3；使用脚本化决策代替真实模型。

输入与初始状态：

```python
scripted_decisions = [
    {"tool": "get_release", "args": {"release_id": "r1"}},
    {"tool": "query_logs", "args": {"release_id": "r1"}},
    {"answer": "根因是超时配置错误"},
]
```

操作步骤：

1. 创建包含`goal`、`step`、`observations`、`actions`和`status`的状态。
2. 每轮读取一个脚本化决策。
3. 工具调用时执行模拟函数并回填结果。
4. 返回答案时运行验证器。
5. 验证通过则停止，否则继续。

预期现象：状态按轮次增长；工具结果进入下一轮；最终答案必须经过验证器。

程序断言或人工检查：

```python
assert state["step"] == 3
assert len(state["actions"]) == 2
assert state["status"] in {"completed", "failed"}
```

失败时先看什么：检查工具结果是否真的写回`observations`，而不是只打印日志。

通过标准：能逐行指出 Observe、Decide、Act、Result、Verify 和 Stop。

产出证据：完整状态 JSON 和每轮 Trace。

这个实验没有证明什么：没有测试真实模型的非确定性。

### 实验任务二：验证预算和硬停止

实验目标：证明模型不能突破程序预算。

覆盖知识点：终止条件、步数和多维预算；确定性代码与模型决策边界。

为什么做：模型可能每轮都给出“再查一次”的合理理由。

准备条件：实验一的循环；把脚本化决策改成无限重复`query_logs`。

输入与初始状态：

```python
budget = {"max_steps": 3, "max_tool_calls": 2}
```

操作步骤：

1. 连续返回相同工具调用。
2. 在执行前检查步数和工具调用预算。
3. 记录最终停止原因。

预期现象：第三次工具调用不会执行，状态变为`budget_exhausted`。

程序断言或人工检查：

```python
assert tool_call_count == 2
assert state["stop_reason"] == "tool_budget_exhausted"
```

失败时先看什么：预算检查是否发生在工具执行之前。

通过标准：模型即使继续请求，真实工具也不会超过预算。

产出证据：停止日志和工具调用计数。

这个实验没有证明什么：预算数值本身是否最优。

### 实验任务三：建立错误分类与恢复路由

实验目标：让不同错误走不同恢复动作。

覆盖知识点：Planning、Replanning、重试与局部恢复。

为什么做：统一“失败后重试”会导致越权、重复副作用和无效消耗。

准备条件：一个返回分类错误的模拟工具。

输入与初始状态：

```text
timeout
invalid_arguments
permission_denied
business_rejected
```

操作步骤：

1. 为每类错误定义`retryable`和推荐动作。
2. 分别执行一次失败。
3. 检查系统选择了原样重试、改参、申请审批、重规划还是停止。

预期现象：

| 错误 | 预期动作 |
|---|---|
| timeout | 有上限重试 |
| invalid_arguments | 改参数 |
| permission_denied | 申请审批或停止 |
| business_rejected | 不重试 |

程序断言或人工检查：权限和业务拒绝不得原样重试。

失败时先看什么：错误类型是否在工具层就被压成同一个字符串。

通过标准：四类错误产生至少三种不同恢复动作。

产出证据：错误到恢复动作的 Trace 表。

这个实验没有证明什么：真实第三方服务的全部错误分类。

### 实验任务四：加入 Verification Loop

实验目标：证明模型自报完成不能替代确定性验收。

覆盖知识点：Task Loop 与 Verification Loop；Reflection；Evaluator-Optimizer。

为什么做：这是“做完”和“做对”的关键分界。

准备条件：实验一的循环；验证规则要求两条不同来源证据。

输入与初始状态：让模型在只有一条日志时返回“任务完成”。

操作步骤：

1. Task Loop 产生候选报告。
2. Verification Loop 检查证据数量和来源唯一性。
3. 返回具体缺口。
4. 模型或脚本根据缺口补查监控。
5. 再次验证。

预期现象：第一次不允许停止；第二次加入独立监控证据后通过。

程序断言或人工检查：

```python
assert first_verification["passed"] is False
assert "独立证据不足" in first_verification["issues"]
assert second_verification["passed"] is True
```

失败时先看什么：验证器是否只检查字段非空，没有检查来源唯一性。

通过标准：停止权属于验证器，不属于模型自报状态。

产出证据：两次候选报告、两次验证结果和修正 Trace。

这个实验没有证明什么：开放语义质量可以全部规则化。

### 实验任务五：制造无进展和 Reward Hacking

实验目标：识别重复循环和表面满足指标。

覆盖知识点：死循环、重复调用与错误累积；Reward Hacking。

为什么做：系统可能看起来持续工作，但没有接近真实目标。

准备条件：动作指纹、证据来源 ID 和进展字段。

输入与初始状态：

```text
连续三次相同 query_logs 参数
同一条日志复制成 evidence_1 和 evidence_2
```

操作步骤：

1. 计算工具名和标准化参数的动作指纹。
2. 连续记录重复次数和新证据数量。
3. 对证据按来源 ID 去重。
4. 达到无进展阈值后停止或 Replanning。

预期现象：第三次重复调用被阻断；复制证据不能通过验证。

程序断言或人工检查：

```python
assert repeated_action_count >= 2
assert unique_evidence_count == 1
assert verification_passed is False
```

失败时先看什么：参数是否在计算指纹前完成标准化，证据是否拥有稳定来源 ID。

通过标准：系统能区分“动作很多”和“信息有增量”。

产出证据：动作指纹日志、进展字段和去重后的验证结果。

这个实验没有证明什么：所有 Reward Hacking 都能通过静态规则发现。

## 边界、代价与下一问题

当前机制已经解决：

| 能力 | 关键机制 |
|---|---|
| 多轮行动 | Observe、Decide、Act、Result |
| 可控停止 | 终止条件和多维预算 |
| 失败恢复 | 错误分类、重试和 Replanning |
| 结果质量 | Verification Loop |
| 自动修正 | Reflection、Evaluator-Optimizer |
| 防止空转 | 重复检测、进展判断和硬门禁 |

当前机制仍未解决：

- 长任务状态怎样持久化。
- 进程崩溃后怎样恢复到安全步骤。
- 人工审批怎样暂停并继续。
- 多个并行分支怎样合并状态。
- 工具副作用怎样在重放时保持幂等。

这些问题属于 Graph(状态图运行时)与 Durable Runtime(可恢复运行时)，会在后续根据学习进度动态生成。

## 自测题与答案

### 题目一：最小 Agent Loop 包含哪些环节？

参考答案：Observe 组装当前观察，Decide 产生回答或动作候选，Act 由程序执行工具，Result 返回结果，Verify 检查目标是否满足，Stop 决定结束或继续。

判分点：

- 2 分：说出观察、决策、行动、结果。
- 1 分：说出验证和停止。
- 1 分：区分模型和程序职责。

常见误区：只回答“思考和行动”。

### 题目二：ReAct 解决了什么，又缺少什么？

参考答案：ReAct 让外部观察参与下一步决策，适合路径未知的开放任务；它不自动提供预算、停止、权限、去重和可靠验证。

判分点：

- 1 分：说明观察驱动后续行动。
- 1 分：指出至少两个控制边界。

常见误区：把 ReAct 当成完整 Agent Runtime。

### 题目三：消息历史为什么不能直接代替循环状态？

参考答案：消息历史主要服务模型上下文，循环状态还要保存预算、调用 ID、错误分类、审批、验证结果和可计算字段，必须能被程序稳定读取和更新。

判分点：

- 1 分：区分上下文和程序状态。
- 1 分：举出两个结构化状态字段。

常见误区：把所有状态都塞进 Prompt。

### 题目四：模型自报完成为什么不可信？

参考答案：模型只生成候选文本，可能遗漏业务条件或为了迎合任务声称完成。程序应使用业务验收、工具事实、预算和安全策略决定是否停止。

判分点：

- 1 分：说明模型输出是候选。
- 1 分：说明需要外部验收。

常见误区：认为增加 Prompt 强调“认真检查”就足够。

### 题目五：哪些判断应放在确定性代码中？

参考答案：预算、超时、权限、审批、Schema、幂等、去重、调用状态和明确业务验收都应由确定性代码控制。

判分点：

- 1 分：列出安全或预算类。
- 1 分：列出验证或幂等类。

常见误区：凡是复杂都交给模型。

### 题目六：Planning 与边执行边规划有什么区别？

参考答案：Planning 先形成目标、假设和动作方向；边执行边规划在每次新观察后更新计划。前者提供方向，后者避免完整计划在环境变化后失效。

判分点：

- 1 分：说明计划提供方向。
- 1 分：说明观察会更新计划。

常见误区：把计划视为不可修改的步骤清单。

### 题目七：工具失败后怎样选择重试、换工具、重规划或退出？

参考答案：先按瞬时、参数、业务、权限、工具不适用、前提推翻和永久失败分类，再映射恢复动作。不能对业务拒绝和权限错误原样重试。

判分点：

- 1 分：先分类再处理。
- 1 分：至少说出三种不同恢复动作。

常见误区：所有失败统一指数退避。

### 题目八：Task Loop 与 Verification Loop 有什么区别？

参考答案：Task Loop 负责产生候选结果，Verification Loop 按外部标准检查候选是否正确。前者回答“做了什么”，后者回答“是否达到完成条件”。

判分点：

- 1 分：区分生成和验收。
- 1 分：说明验证失败会反馈缺口。

常见误区：把最后一次模型调用当成验证。

### 题目九：Reflection 和 Evaluator-Optimizer 什么时候有效？

参考答案：当系统能提供具体、可行动的失败反馈时，它们可以帮助修正；如果缺少事实、反馈模糊或涉及权限硬约束，反思不能替代工具和确定性代码。

判分点：

- 1 分：需要具体反馈。
- 1 分：指出至少一个无效边界。

常见误区：无限反思一定提高质量。

### 题目十：怎样识别 Agent 看起来很忙但没有进展？

参考答案：比较动作指纹、观察是否重复、新证据数量、假设是否更新和目标距离。连续重复动作且没有信息增益时应 Replanning 或停止。

判分点：

- 1 分：指出动作或观察重复。
- 1 分：指出信息增益或目标距离。

常见误区：只看是否还在产生 Token。

### 题目十一：错误累积是怎样发生的？

参考答案：错误工具结果或错误假设进入状态后，被后续计划和行动继续引用，形成错误放大。需要来源、验证状态和可推翻标记。

判分点：

- 1 分：说明错误进入状态。
- 1 分：说明后续决策继续放大。

常见误区：只处理最后一次报错。

### 题目十二：Reward Hacking 在 Agent 中是什么？

参考答案：Agent 满足了评测指标表面，却没有完成真实目标，例如复制同一证据满足数量要求。修复要让验收绑定来源唯一性、因果关系和业务结果。

判分点：

- 1 分：说明指标与真实目标错位。
- 1 分：给出防御方法。

常见误区：把 Reward Hacking 只理解成模型训练问题。

## 知识关系图

```text
一、任务推进循环

[用户目标]
  └─ 被程序整理为 → [当前观察]
                         └─ 交给模型 → [下一步候选]
                                         └─ 通过程序校验 → [真实行动]
                                                               └─ 产生 → [工具结果]
                                                                            └─ 写回 → [循环状态]

二、程序控制边界

[循环状态]
  ├─ 受到硬限制 → [步数 / Token / 时间 / 成本 / 副作用预算]
  ├─ 经过安全检查 → [权限 / 审批 / 幂等]
  └─ 进入停止判断 → [继续 / 等待人工 / 成功 / 失败]

三、失败恢复

[分类错误]
  ├─ 瞬时错误 → 有上限重试
  ├─ 参数错误 → 改参
  ├─ 工具不适用 → 换工具
  ├─ 前提被推翻 → 重新规划
  └─ 权限或永久错误 → 审批、降级或停止

四、质量验证

[任务循环产生候选]
  └─ 交给 → [验证循环]
               ├─ 通过 → 允许停止
               └─ 不通过 → [具体缺口]
                                └─ 驱动 → [反思 / 修正 / 再次生成]

五、失控防护

[每轮 Trace]
  ├─ 检查动作指纹 → 阻断重复调用
  ├─ 检查信息增益 → 识别无进展
  ├─ 检查证据来源 → 阻止重复证据
  └─ 检查真实业务目标 → 防止 Reward Hacking
```

### 如何读图

1. 第一层解释 Agent 怎样循环推进任务。
2. 第二层解释为什么程序而不是模型拥有最终控制权。
3. 第三层解释失败不是统一重试，而是分类恢复。
4. 第四层把“产生候选”和“证明正确”拆成两个循环。
5. 第五层检查循环是否真的接近目标，而不是只在消耗资源。

关键结论：

- Agent Loop 是一个受程序控制的状态循环。
- ReAct 只提供观察和行动交替，不提供完整可靠性。
- 计划、预算、错误路由和验证共同决定系统能否安全停止。
- Task Loop 负责做事，Verification Loop 负责证明做对。
- 无进展检测和真实业务门禁负责阻止失控与指标投机。
