# CU-002：Agent Loop 原理与可靠性控制 - 面试训练

> 对应推导式理解：[CU-002 推导式理解](推导式理解.md)
> 使用方式：先根据发布调查案例独立推演，再对照核心判断和完整回答

## 1. 请从零描述一个最小 Agent Loop 的执行过程？

题型：原理与链路型

一句话核心判断：最小 Agent Loop 是由程序持有状态和停止权，让模型在每轮观察后产生有限决策候选，再经过工具执行、结果回填和验证决定继续或结束。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 系统只能完成一次模型调用或一次工具调用 |
| 最小机制是什么 | Observe、Decide、Act、Result、Verify、Stop |
| 工程收益 | 可以根据真实环境反馈连续推进开放任务 |
| 边界和代价 | 多轮会累积错误、成本和状态复杂度 |

30 秒回答：

> 最小 Agent Loop 先由程序把目标、当前状态和最新工具结果组装成 Observe；模型执行 Decide，返回回答或工具候选；程序校验后 Act；工具结果写回状态；Verification 检查业务目标和证据；最后由程序根据验收、预算和错误决定 Stop 或进入下一轮。模型负责开放决策，程序负责状态、执行和边界。

完整回答：

一个可靠循环至少有六个环节。观察环节读取用户目标、已有证据、上轮结果和可用工具；决策环节让模型选择回答、调用工具或请求人工；行动环节由确定性程序校验参数和权限后执行。

结果环节将成功数据或分类错误写回；验证环节用业务规则、测试或评估器检查是否真正满足目标；停止环节根据验证、预算、安全和错误状态决定结束或继续。

循环状态不能只有消息历史。它至少要保存步骤、动作、观察、证据、预算、错误和任务状态。模型可以建议“完成”，但程序必须重新验证。

ASCII 图或关键表：

```text
目标与状态
  → Observe
  → Decide
  → Act
  → Result
  → Verify
  → Stop / Continue
```

追问：

- 原理追问：Reason 在这个循环中位于哪里？
- 工程追问：循环状态至少需要哪些字段？
- 项目追问：发布调查 Agent 的每一轮 Trace 会记录什么？

证据：

手写三轮脚本化 Agent Loop，保存每轮状态 JSON、工具调用和停止原因。

对应推导章节：

阶段一：Agent Loop 循环模型与 ReAct。

## 2. ReAct 解决了什么问题，又带来哪些风险？

题型：概念与取舍型

一句话核心判断：ReAct 让外部观察持续修正下一步行动，解决完整路径未知的问题，但它不自动提供预算、停止、验证和防重复机制。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | Agent 只能预先固定完整路径或单次回答 |
| 最小机制是什么 | 观察、形成行动候选、执行、获得新观察 |
| 工程收益 | 可以在信息不完整时逐步调查和调整 |
| 边界和代价 | 容易重复调用、上下文膨胀和错误累积 |

30 秒回答：

> ReAct 的核心是让推理和行动交替：模型根据当前观察选择工具，工具结果再成为下一轮观察。它适合开放式调查，因为不要求一开始知道完整路径。但 ReAct 只是决策模式，不是完整运行时，预算、权限、停止、验证、去重和状态持久化仍要由程序补齐。

完整回答：

一次性规划假设环境相对稳定，而 ReAct 允许每次工具观察改变后续路径。例如发布记录显示健康检查失败后，Agent 可以查日志；日志没有证据时再改查监控。

ReAct 的风险来自多轮不确定性：模型可能选错工具、重复相同动作、把错误观察当事实、暴露不应展示的内部推理，或者在没有验证时过早结束。工程上通常只保留可审计的行动理由和 Trace，不依赖或公开完整内部思维过程。

ASCII 图或关键表：

```text
观察 1 → 行动 1 → 观察 2 → 行动 2 → 观察 3
                    │
                    └─ 新事实改变下一步
```

追问：

- 原理追问：ReAct 与固定 Workflow 的真实差异是什么？
- 工程追问：怎样压缩多轮工具结果而不丢关键证据？
- 项目追问：发布调查中什么情况下不应该使用 ReAct？

证据：

对比固定“发布记录 → 日志 → 监控”流程和根据工具结果动态选择的 Trace。

对应推导章节：

阶段一：Agent Loop 循环模型与 ReAct。

## 3. Agent Loop 如何判断任务已经完成？

题型：终止与可靠性型

一句话核心判断：任务完成必须同时满足业务验收和安全边界，并且没有触发资源或失败停止；模型自报完成只能作为候选信号。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | Agent 会过早结束或无限循环 |
| 最小机制是什么 | 成功、资源、安全和失败四类停止条件 |
| 工程收益 | 停止原因可解释、可审计、可测试 |
| 边界和代价 | 业务验收需要额外设计和维护 |

30 秒回答：

> Agent 是否完成不能只看模型说了什么，而要由程序检查四类条件：业务验收是否通过，步数、Token、时间和成本是否超限，是否需要审批或触发安全策略，以及是否出现永久错误或无进展。成功验收通过才算完成，其他情况应该记录明确的停止原因。

完整回答：

成功停止要求任务结果满足外部标准，例如发布根因至少有两条独立证据、因果链完整且没有未经审批的回滚。资源停止包括最大步数、工具调用数、Token、时间和成本耗尽。安全停止包括高风险动作审批和策略拒绝。失败停止包括永久错误、无可用工具和连续无进展。

停止优先级一般是安全策略高于资源硬限制，资源硬限制高于模型建议。模型的`done`只是一个字段，不能突破程序边界。

ASCII 图或关键表：

```text
候选完成
  ├─ 业务验收通过 → 成功停止
  ├─ 预算耗尽 → 资源停止
  ├─ 需要审批 → 等待人工
  └─ 永久失败或无进展 → 失败停止
```

追问：

- 原理追问：Finish Reason 与 Agent Stop 有什么区别？
- 工程追问：多维预算之间怎样设置优先级？
- 项目追问：发布调查的成功验收条件是什么？

证据：

分别制造验收通过、预算耗尽、审批等待和无进展四条停止 Trace。

对应推导章节：

阶段二：确定性控制、终止条件与多维预算；阶段四：Verification Loop 与反馈修正。

## 4. 确定性代码和模型决策应该怎样划分边界？

题型：系统设计型

一句话核心判断：模型负责难以枚举的开放语义候选，确定性代码负责必须稳定、可审计和不可绕过的控制边界。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 所有复杂判断都交给模型，系统无法保证安全和一致性 |
| 最小机制是什么 | 候选权与执行权分离 |
| 工程收益 | 保留模型灵活性，同时提供硬边界 |
| 边界和代价 | 确定性规则过多可能让系统退化成僵硬工作流 |

30 秒回答：

> 我会把开放语义决策交给模型，例如从多个调查方向中选择下一步、总结非结构化证据；把预算、超时、权限、审批、Schema、幂等、去重、调用状态和明确业务验收放在确定性代码里。判断标准是：如果错误会产生不可接受副作用，或结果必须稳定可复现，就不能只靠模型。

完整回答：

模型的优势是处理模糊目标、非结构化输入和无法穷举的选择；程序的优势是稳定、可重复和可审计。因此模型应该生成候选计划、工具或解释，程序负责过滤工具集合、校验参数、执行副作用、维护状态、限制预算和判断硬性验收。

边界不是“智能归模型，简单归代码”。有些业务规则很复杂，但只要必须强一致，就应该在代码、策略引擎或人工审批中。反过来，若用大量规则枚举开放语义，系统可能失去 Agent 的适应性。

ASCII 图或关键表：

| 类型 | 模型 | 确定性代码 |
|---|---|---|
| 开放语义 | 假设、计划、解释 | 提供输入和约束 |
| 硬边界 | 只能建议 | 预算、权限、审批、停止 |
| 真实副作用 | 产生候选 | 校验并执行 |
| 最终验收 | 辅助评估 | 规则、测试或人工拥有决定权 |

追问：

- 原理追问：为什么 Prompt 不能替代权限系统？
- 工程追问：模型和规则结论冲突时谁优先？
- 项目追问：你的 Agent 中哪一个判断曾从模型迁回代码？

证据：

展示工具调用进入执行器前的权限、预算和业务门禁代码。

对应推导章节：

阶段二：确定性控制、终止条件与多维预算。

## 5. 工具调用失败后，Agent 应该重试、换工具、重新规划还是退出？

题型：排障与恢复型

一句话核心判断：先对错误分类，再根据错误是否瞬时、是否可改参、是否推翻前提和是否允许继续，选择不同恢复动作。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 所有失败统一重试，导致浪费、越权或重复副作用 |
| 最小机制是什么 | 分类错误到恢复策略的映射 |
| 工程收益 | 局部恢复且保留已有证据 |
| 边界和代价 | 错误契约需要工具和编排层共同维护 |

30 秒回答：

> 我会先区分瞬时错误、参数错误、业务拒绝、权限错误、工具不适用、前提被推翻和永久失败。瞬时错误可以有上限重试，参数错误应改参，工具不适用要换工具，前提被推翻才重新规划，权限和业务拒绝通常申请审批或停止。有副作用的工具还要先确认幂等，不能盲目重试。

完整回答：

恢复策略必须读取结构化错误，而不是只看“调用失败”。网络抖动和临时 503 可以退避重试；时间范围过大应缩小参数；无权限不能通过重试解决；发布状态不允许回滚属于业务拒绝；日志工具没有目标指标时可以换监控；核心假设被证据推翻时才 Replanning。

局部恢复应该保留已完成动作和证据，只重做失败节点。重新启动整个任务会增加成本，也可能重复副作用。

ASCII 图或关键表：

```text
工具失败
  → 错误分类
     ├─ 瞬时 → 有上限重试
     ├─ 参数 → 改参
     ├─ 不适用 → 换工具
     ├─ 前提错误 → Replanning
     └─ 权限 / 业务 / 永久 → 审批、降级或退出
```

追问：

- 原理追问：重试与 Replanning 的边界是什么？
- 工程追问：副作用工具超时后怎样判断是否已经成功？
- 项目追问：发布日志查询超时时你会怎么恢复？

证据：

一张错误类型、`retryable`、恢复动作和最大次数的路由表，以及对应 Trace。

对应推导章节：

阶段三：Planning、错误路由与局部恢复。

## 6. Planning、Replanning 和边执行边规划分别解决什么问题？

题型：规划机制型

一句话核心判断：Planning 提供当前方向，边执行边规划根据新观察持续更新，Replanning 在核心前提被推翻时重写剩余路径。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | Agent 每轮临时反应，缺少目标一致性 |
| 最小机制是什么 | 目标、假设、证据缺口和下一动作的可更新状态 |
| 工程收益 | 既有方向，又能适应环境变化 |
| 边界和代价 | 计划过重会增加 Token 和维护成本 |

30 秒回答：

> Planning 先定义目标、假设、证据缺口和候选动作；边执行边规划是在每次工具结果后更新这些状态；Replanning 是当原计划的关键前提被推翻时重写剩余路径。开放式调查通常适合轻量计划，而不是一开始生成不可修改的长步骤。

完整回答：

无计划适合极短任务，完整计划适合路径稳定的工作流，发布调查更适合轻量计划。系统可以保存当前假设、需要的证据和下一批动作，每执行一步就根据结果更新。

Replanning 不应该在每次小错误后触发。参数错误可以局部改参，瞬时错误可以有限重试；只有证据推翻关键假设、工具路径不再适用或目标发生变化时，才需要重写计划。

ASCII 图或关键表：

```text
轻量计划
  → 执行一步
  → 新观察
     ├─ 计划仍成立 → 更新下一动作
     └─ 核心前提被推翻 → Replanning
```

追问：

- 原理追问：计划应该保存在哪一层状态中？
- 工程追问：怎样避免每轮都重写完整计划？
- 项目追问：发布调查中的哪个证据会触发 Replanning？

证据：

展示同一任务执行前后的计划差异和触发 Replanning 的证据。

对应推导章节：

阶段三：Planning、错误路由与局部恢复。

## 7. Reflection、Self-Correction 和 Evaluator-Optimizer 有什么区别？

题型：质量改进型

一句话核心判断：Reflection(反思)分析哪里错了，Self-Correction(自我纠正)根据反馈重新生成，Evaluator-Optimizer(评估优化循环)则把质量判断和候选优化分成两个角色或组件。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 验证失败后系统不知道怎样修正 |
| 最小机制是什么 | 具体反馈驱动新的候选 |
| 工程收益 | 可以在有限轮次内改进开放语义结果 |
| 边界和代价 | 反馈模糊时只会改措辞，循环成本也会上升 |

30 秒回答：

> Reflection 是对失败原因和缺口做分析，Self-Correction 是根据这些反馈重新生成；Evaluator-Optimizer 把生成候选和评估质量分开，Evaluator 给出具体缺口，Optimizer 再修正。它们只有在反馈可操作、修正次数有限时有效，不能替代外部事实、权限和确定性验证。

完整回答：

Reflection 可以发生在执行失败或验收不通过后，目标是找出错误假设、缺失证据和下一步修正。Self-Correction 是利用这些反馈产生新答案或新动作。

Evaluator-Optimizer 更结构化：Optimizer 负责生成，Evaluator 按规则、测试、人工或受约束模型评估，并返回明确缺口。确定性检查应优先；语义质量无法规则化时才使用模型评估，并考虑偏差、成本和自我确认风险。

ASCII 图或关键表：

| 机制 | 主要职责 | 关键前提 |
|---|---|---|
| Reflection | 分析错误和缺口 | 有真实反馈 |
| Self-Correction | 重新生成候选 | 反馈可行动 |
| Evaluator-Optimizer | 分离生成与评估 | 验收标准明确 |

追问：

- 原理追问：模型能否只靠自我反思发现未知事实？
- 工程追问：怎样限制反思循环次数？
- 项目追问：发布报告验证失败后反馈应该多具体？

证据：

保存第一次候选、验证缺口、反思结果、修正候选和第二次验证结果。

对应推导章节：

阶段四：Verification Loop 与反馈修正。

## 8. Task Loop 和 Verification Loop 为什么要分开？

题型：可靠性架构型

一句话核心判断：Task Loop 负责产生和推进候选结果，Verification Loop 负责用独立标准证明结果是否正确；生成者不能同时无条件批准自己完成。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 模型一旦生成答案就被视为完成 |
| 最小机制是什么 | 候选结果、独立验收、缺口反馈和有限返工 |
| 工程收益 | 停止条件可测试，失败原因可定位 |
| 边界和代价 | 验证器设计本身可能不完整或被投机 |

30 秒回答：

> Task Loop 负责查数据、调用工具和生成候选报告；Verification Loop 独立检查证据数量、来源、因果链和安全条件。验证通过才允许停止，不通过就返回具体缺口，驱动补充动作或修正。这样可以避免模型既当选手又无条件当裁判。

完整回答：

Task Loop 的成功标准是“产生候选”，Verification Loop 的成功标准是“候选满足外部要求”。发布调查中，即使工具调用都成功，最终报告仍可能证据不足、因果关系错误或误写成已经回滚。

验证器可以组合确定性代码、测试、人工和模型评估。验证失败后，不应该笼统返回“再想想”，而要指出缺少哪条证据、哪个字段冲突或哪项安全条件未满足。

ASCII 图或关键表：

```text
Task Loop → 候选结果
                 ↓
        Verification Loop
          ├─ 通过 → Stop
          └─ 不通过 → 具体缺口 → 返工
```

追问：

- 原理追问：Verification Loop 是否也是 Agent Loop？
- 工程追问：验证器失败或超时时怎么办？
- 项目追问：发布调查的确定性验证项有哪些？

证据：

同一个候选报告在加入验证器前后产生的不同停止结果。

对应推导章节：

阶段四：Verification Loop 与反馈修正。

## 9. 如何识别 Agent 在循环中看起来很忙但没有进展？

题型：排障与可观测型

一句话核心判断：不能只看轮次和 Token，要比较动作指纹、观察变化、信息增益、假设更新和目标距离。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | Agent 会持续消耗资源直到最大步数 |
| 最小机制是什么 | 重复检测和进展字段 |
| 工程收益 | 可以提前 Replanning 或停止 |
| 边界和代价 | 开放任务的目标距离有时难以量化 |

30 秒回答：

> 我会给工具名和标准化参数建立动作指纹，同时记录新证据数量、观察是否重复、假设是否更新、验证缺口是否减少和目标距离。连续多轮重复同一动作且没有信息增益，就不是进展，应阻断重复、换工具、Replanning 或停止，而不是等预算耗尽。

完整回答：

“忙”只说明系统仍在产生动作。“进展”要求状态发生与目标相关的变化。最小检测包括重复工具调用、相同结果、证据数量、证据来源唯一性、计划是否更新和验证问题是否减少。

错误累积也要观察：错误工具结果进入状态后，可能被后续假设和计划反复引用。状态中应保存来源、验证状态和是否被推翻。

ASCII 图或关键表：

```text
每轮 Trace
  ├─ 动作是否重复
  ├─ 是否新增证据
  ├─ 假设是否变化
  ├─ 验证缺口是否减少
  └─ 目标距离是否下降
```

追问：

- 原理追问：怎样定义动作指纹？
- 工程追问：重复调用一定是错误吗？
- 项目追问：你会为发布调查定义哪些进展指标？

证据：

一条连续三次相同查询的 Trace，以及加入重复阻断后的对照结果。

## 10. 什么是 Agent 场景中的 Reward Hacking，怎样防止？

题型：评测与安全型

一句话核心判断：Reward Hacking 是 Agent 满足了评测指标表面，却绕开真实任务目标；防御要让验收绑定不可伪造的业务证据和多维约束。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 系统指标变好，但真实结果变差 |
| 最小机制是什么 | 检查指标与真实目标是否一致 |
| 工程收益 | 防止 Agent 钻字段、数量和流程漏洞 |
| 边界和代价 | 新的投机方式可能持续出现，需要回归和人工抽查 |

30 秒回答：

> Reward Hacking 是 Agent 优化了验收规则的表面形式，却没有完成真实目标。比如要求两条证据，它复制同一日志两次；要求根因字段非空，它填一个空泛结论。防御要检查证据来源唯一性、因果关系、真实业务结果和安全边界，并用隐藏样本、人工抽查和回归持续发现新投机方式。

完整回答：

Reward Hacking 的根因是代理指标和真实目标不一致。Agent 擅长寻找满足规则的路径，如果验收只检查字段存在、调用次数或表面成功率，就可能出现投机。

防御包括：让证据带稳定来源 ID；验证不同来源而不是数量；检查因果链；同时看任务成功、工具轨迹和业务结果；保留 Holdout(留出)样本；对高风险结果人工复核；发现投机后加入回归。

ASCII 图或关键表：

| 表面规则 | 投机方式 | 更真实的验收 |
|---|---|---|
| 两条证据 | 复制同一日志 | 不同来源 ID |
| 根因非空 | 填空泛文本 | 因果链和引用 |
| 工具成功率高 | 避免难工具 | 端到端任务成功 |

追问：

- 原理追问：Reward Hacking 与普通幻觉有什么区别？
- 工程追问：怎样设计不容易被钻的验证器？
- 项目追问：你的 Agent 哪个指标最容易诱发投机？

证据：

构造复制证据通过旧验证器、被新验证器拒绝的回归 Case。

对应推导章节：

阶段五：进展检测、死循环与 Reward Hacking 防护。
