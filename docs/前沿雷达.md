# Agent 工程前沿雷达

## 1. 文档定位

这份文档跟踪尚在快速变化、证据不足或工程边界未稳定的新方向。

它不是第二份学习总纲。进入这里不等于第一轮必须学习，只有通过证据和实验门槛的内容才会晋级到[学习总纲](学习总纲.md)。

最后核对日期：`2026-07-30`。

## 2. 状态定义

| 状态 | 含义 |
|---|---|
| 线索 | 只有观点、演讲或少量项目描述 |
| 已核实 | 找到官方资料、源码或论文，确认概念真实存在 |
| 实验中 | 已设计或完成最小实验，但结论还不稳定 |
| 主干候选 | 多个独立来源和实验说明它解决稳定问题 |
| 已进入主干 | 已写入学习总纲，并定义实验和掌握要求 |
| 已归档 | 价值不足、概念被吸收或长期没有可靠证据 |

## 3. 当前雷达总览

| 方向 | 当前状态 | 在主干中的位置 | 当前判断 |
|---|---|---|---|
| Harness Engineering | 已进入主干 | 构造 Agent Harness | 已成为理解高能力 Agent 系统的关键视角 |
| Loop Engineering | 已进入主干 | 评测并持续改进 | 需要继续观察术语是否稳定，但问题分类已经有价值 |
| Memory 与 Skill 自演进 | 已进入主干 | 持续改进闭环 | 工程价值较高，必须同时学习测试、版本和回滚 |
| Harness 自动优化 | 主干候选 | 持续改进闭环 | 已有研究和系统样本，生产治理仍不成熟 |
| Agent 修改自身代码 | 实验中 | 持续改进闭环 | 研究价值高，默认不作为普通应用 Agent 的生产能力 |
| 模型权重自进化 | 实验中 | 模型训练支线 | 与 Agent Harness 改进不同，第一轮低投入 |
| Agent2Agent Protocol | 主干候选 | 编排模式与跨系统协作 | 正式协议已经形成，是否深入取决于项目是否跨系统 |

## 4. Loop Engineering

### 已确认的价值

单个 Agent Loop 只能解释一次任务如何运行，无法完整解释：

- 验证不通过后如何返工。
- 事件到来后如何持续运行。
- 如何根据历史 Trace 改进系统。

当前采用四层模型：

```text
Task Loop
Verification Loop
Event-driven Loop
Improvement Loop
```

### 仍需观察

- 不同团队是否对“Loop Engineering”形成一致定义。
- 它最终是独立学科，还是 Eval、Harness 和运行时工程的组合名称。
- 外层循环的自动化程度如何分级。

### 晋级条件

已经进入主干，但每季度需要检查术语和分层是否仍有解释力，避免为了保留热点名词制造重复章节。

## 5. 自进化 Agent

### 必须先拆成五类

```text
Memory Evolution
更新事实、经验和用户偏好

Skill Evolution
发现、生成、测试和维护可复用方法

Harness Evolution
调整 Prompt、Context、Tool、Workflow、权限和验证器

Code Self-Modification
Agent 修改自身实现代码

Model Adaptation
通过训练或参数更新改变模型本身
```

把这五类都叫“自进化”会掩盖完全不同的成本和风险。

### 当前工程判断

- Memory 更新最容易落地，也最容易积累错误事实。
- Skill 演进具有较高工程价值，但必须拥有测试、版本、检索、冲突处理和淘汰机制。
- Harness 优化比模型训练更贴近应用开发，应成为主线重点。
- 代码自修改需要 Sandbox、独立 Eval、候选归档、审批和回滚。
- 模型权重自进化属于训练与研究支线，不应吞噬第一轮 Agent 工程投入。

### 当前样本

- [Hermes Agent](https://github.com/NousResearch/hermes-agent)：Memory、Skill、后台执行和持续改进。
- [DeerFlow](https://github.com/bytedance/deer-flow)：长任务 Harness、Subagent、Sandbox、Memory 和 Skills。
- [Darwin Gödel Machine](https://arxiv.org/abs/2505.22954)：代码自修改、候选归档和基准验证。
- [SkillWeaver](https://arxiv.org/abs/2504.07079)：从环境探索中形成可复用 Skill。
- [MUSE-Autoskill](https://arxiv.org/abs/2605.27366)：Skill 的创建、记忆、管理、评测和迭代。

### 尚未解决的问题

- 如何证明一条经验可以跨任务泛化。
- 如何避免 Agent 针对固定 Eval 过拟合。
- 如何发现 Skill 重复、冲突和过期。
- 如何控制长期记忆和 Skill 库的检索成本。
- 如何定义自动修改的权限上限。
- 如何证明回滚恢复了状态和外部副作用。

## 6. 现代 Agent Harness 样本

### DeerFlow

研究问题：

- 长任务如何规划和持续执行。
- Subagent 如何隔离上下文。
- Sandbox、Workspace 和 Artifact 如何组织。
- Memory、Skill 和工具如何按需加载。
- Skill 自演进是否具备真实的生成、验证和治理闭环。

不能直接推出：

- DeerFlow 的目录结构就是通用最佳实践。
- README 中的每个概念都已经达到生产成熟度。
- 使用更多 Subagent 一定优于单 Agent。

### Hermes Agent

研究问题：

- 经验如何进入 Memory 或 Skill。
- 后台复盘如何触发。
- Skill 写入是否需要审批。
- 如何整理、归档和恢复长期知识。

不能直接推出：

- Agent 自动写出的 Skill 一定可靠。
- 有长期记忆就等于能够持续学习。
- 单一项目中的改进结果能迁移到其他 Agent。

### Claude Code

研究问题：

- 项目指令如何进入 Context。
- Hook、Skill、Subagent、MCP 和插件如何分工。
- Compaction、权限和工具反馈如何支撑长任务。
- Coding Agent 如何使用测试、日志和编译器建立 Verification Loop。

资料边界：

- 优先使用官方文档、SDK、插件和可观察实验。
- 来源不明的“泄漏源码”只可提出假设，不能成为知识主干依据。
- 反编译结果不能证明设计意图和当前版本行为。

## 7. Agent 互操作协议

### MCP

MCP 主要解决 AI 应用如何接入工具、资源和交互能力。

主干已经覆盖其 Host、Client、Server、Transport 和 Capability，需要持续跟踪规范版本和安全建议。

### A2A

A2A 主要解决独立 Agent 系统如何发现彼此、描述能力、通信和协作。

需要研究的边界：

- A2A 与框架内部 Handoff 的区别。
- A2A 与普通 REST、消息队列的成本差异。
- Agent Card(智能体能力说明卡)的发现、身份和信任。
- 跨组织任务的认证、授权、状态和审计。
- Remote Agent(远程智能体)失败后的恢复责任。

当前只要求知道定位。除非贯穿项目涉及跨系统 Agent 协作，否则不立即投入完整协议实现。

## 8. Coding Agent 带来的新工程视角

Coding Agent 不只是一个应用场景，它集中暴露了现代 Harness 的关键问题：

- 仓库是否对 Agent 可理解。
- 能否自己启动目标系统并得到真实环境反馈。
- 测试、编译器和日志能否形成可靠验证。
- 长任务进度能否跨会话恢复。
- 工具和规则长期堆积后是否需要清理。
- Agent 是否有权限修改 Harness 本身。

这些结论可以迁移到数据分析、办公自动化、运维和研究 Agent，但需要重新定义各领域的环境反馈和验证器。

## 9. GUI 与 Computer-use Agent

需要观察：

- 视觉定位与 DOM(网页结构树)操作的边界。
- 环境变化后的重新观察和恢复。
- 不可重复界面操作的幂等问题。
- 截图、视频和交互轨迹的上下文成本。
- 登录态、隐私和高风险点击审批。
- Skill 如何适应界面版本变化。

只有当贯穿项目需要真实操作网页、桌面或设备时，才从已核实提升为主干候选。

## 10. 长期自治后台 Agent

长期运行不等于一个无限 while 循环，需要额外机制：

- Event Source(事件来源)和触发规则。
- Job Lease(任务租约)与 Worker 故障接管。
- Checkpoint、幂等和副作用恢复。
- 成本、速率和每日预算。
- 人工审批和静默失败告警。
- Memory、Skill 和状态的持续治理。
- Kill Switch(紧急停止开关)。

DeerFlow 和 Hermes 可作为样本，但必须用故障注入验证，而不是只看正常 Demo。

## 11. 推特与社区信息

推特适合：

- 发现新论文、RFC、仓库和术语。
- 跟踪维护者对设计取舍的补充说明。
- 发现失败案例和争议。

推特不适合：

- 单独证明性能提升。
- 单独证明某个功能已经发布。
- 直接决定学习总纲。
- 替代源码、协议、实验和版本记录。

线索晋级流程：

```text
推特线索
   ↓
原始文档 / 源码 / 论文
   ↓
最小实验
   ↓
前沿雷达
   ↓
主干候选
```

## 13. 晋级与淘汰规则

### 晋级到主干

- 至少一个一级或二级来源。
- 至少一个可复现实验或独立实现。
- 能定位到稳定问题，而不只是新名词。
- 能定义失败边界和掌握证据。
- 第一轮投入收益明显高于复杂度。

### 保留在雷达

- 概念真实但工程证据不足。
- 只适用于特定领域。
- 需要高成本训练或基础设施。
- 安全和治理问题尚未解决。

### 归档

- 长期没有原始来源。
- 与现有概念重复且没有新增解释力。
- 实验无法证明增益。
- 项目停止维护或关键结论无法复现。
