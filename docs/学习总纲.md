# Agent 开发学习总纲

## 1. 总纲定位

这份文档是仓库唯一的知识主干，完整定义：

- Agent 开发应该学习哪些内容。
- 各部分之间是什么关系。
- 第一轮应该投入到什么深度。
- 每个章节需要用什么实验和证据证明掌握。
- 哪些方向属于主干，哪些方向暂时作为支线。

其他文档可以引用、解释和追踪这里的内容，但不能另建一套知识目录。

总纲只负责知识边界，不承担全部正文。每个稳定模块的详细内容统一沉淀到[知识模块](知识模块/README.md)，并同时形成：

- 理解版：负责推导、机制、案例、失败、实验和边界。
- 题目版：负责 30 秒回答、3 分钟回答、连续追问和真实证据。

课程负责教学过程，题库负责问题来源，它们都不能替代理解版和题目版。

## 2. 学习目标

完成第一轮学习后，应该具备下面的能力：

1. 能从模型机制解释 Agent 为什么有效、为什么不稳定。
2. 能不依赖高级框架手写最小 Agent Loop(智能体执行循环)。
3. 能设计上下文、状态、记忆、工具、检索和权限边界。
4. 能判断一个任务应该使用单次模型调用、固定工作流、Agent、Graph(状态图运行时)还是多个 Agent。
5. 能设计支持长任务、暂停恢复、人工审批和故障恢复的 Harness(智能体运行支撑环境)。
6. 能用 Trace(完整执行轨迹)、Eval(系统化评测)和失败样本定位问题。
7. 能建立受控的持续改进闭环，让 Prompt、Skill、Memory、Tool、Workflow 和 Harness 根据证据演进。
8. 能把实验系统提升为可观测、可靠、安全、成本可控的生产服务。

第一轮按下面的依赖关系推进：

```text

        ↓

        ↓

        ↓

   ↓
接入综合实验或贯穿项目
```

## 5. 第一部分：理解模型

### 5.1 模型与表示基础

#### 章节目标

理解模型能力从哪里来，以及它为什么会在 Agent 系统中表现出非确定性、幻觉、上下文依赖和工具调用需求。不以完整训练算法和数学推导为第一轮目标。

#### 核心知识点

- Token(模型处理文本的基本单位)、Tokenizer(文本切分器)与上下文窗口。
- Transformer、Self-Attention(自注意力机制)和位置编码的工作直觉。
- 自回归生成和下一 Token 预测。
- 预训练、指令微调、偏好对齐和推理阶段的区别。
- Embedding(语义向量表示)表达什么，相似度能说明什么、不能说明什么。
- Temperature、Top-p、Stop 等解码参数如何影响输出。
- 幻觉、非确定性、知识截止和上下文依赖。
- 多模态模型如何接收和生成文本、图片、音频或视频。
- 模型规模、延迟、成本、上下文窗口和工具能力的选型维度。
- Prompt、RAG、Tool Use 和 Fine-tuning(微调)分别改变系统的哪一部分。

#### 最小实验

- 使用同一请求重复调用模型，观察非确定性和解码参数影响。
- 使用不同上下文长度和信息位置，观察召回质量变化。
- 对同一问题分别采用 Prompt、检索和工具调用，比较它们解决的问题。

#### 第一轮掌握要求

能从模型机制解释 Agent 的不稳定性、上下文限制和工具调用必要性；能够进行模型选型，但不要求手写 Transformer 或训练大模型。

### 5.2 模型交互原语

#### 章节目标

越过框架封装，理解模型服务真实接收和返回的数据结构。Agent 的上层能力最终都会落到这些协议和事件上。

#### 核心知识点

- System、Developer、User、Assistant、Tool 消息角色的语义和优先级。
- 模型请求与响应的真实数据结构。
- Structured Output(结构化输出)与 Schema(字段约束)。
- Function Calling、Tool Calling(工具调用协议)的请求、参数和结果回填。
- 流式响应与事件模型。
- 多模态消息如何组织。
- Token Usage(用量统计)、Finish Reason(结束原因)和错误响应。
- 超时、限流、重试、退避和请求取消。
- 幂等键、请求追踪和供应商差异。
- 原生 API 与框架封装的责任边界。

#### 最小实验

- 直接调用一次模型 API，打印完整请求和响应。
- 实现流式文本输出和中途取消。
- 实现结构化输出，并故意制造字段缺失和类型错误。
- 手写一次完整工具调用：模型选择工具、生成参数、执行、回填结果、继续生成。

#### 第一轮掌握要求

能不依赖 Agent 框架完成流式输出、结构化结果和一次完整工具调用；遇到框架问题时能够下钻到真实协议排障。

## 6. 第二部分：构造 Agent 执行内核

### 6.1 Agent Loop 与决策

#### 章节目标

掌握 Agent 最小工作机制。任何 Graph、Multi-Agent(多智能体协作)或高级 Harness 最终都包含一个或多个执行循环。

#### 核心知识点

- Observe、Reason、Act、Result、Verify、Stop 的最小循环。
- ReAct(边推理边行动)的工作方式和局限。
- 工具选择、参数生成、参数校验和结果回填。
- 终止条件、最大步数、Token 预算、时间预算和成本预算。
- Planning(先形成计划)与边执行边规划。
- Replanning(根据结果重写计划)、失败重试和局部恢复。
- Reflection(执行后反思)与 Self-Correction(自我纠正)。
- Evaluator-Optimizer(评估后继续优化)循环。
- 确定性代码和模型决策的边界。
- 死循环、重复调用、错误累积和 Reward Hacking(钻评测规则漏洞)。
- Task Loop(完成单次任务的循环)与 Verification Loop(验证不通过就返工的循环)。

#### 关键判断

每一个模型决策点都要回答：

1. 这里真的需要模型判断吗？
2. 输入信息是否足够且没有冲突？
3. 输出是否可以被程序验证？
4. 失败后应该重试、改计划、降级还是停止？
5. 谁拥有最终控制权，模型还是确定性代码？

#### 最小实验

- 手写不依赖 Agent 框架的最小执行循环。
- 加入最大步数、预算、超时和停止条件。
- 制造错误工具参数、工具超时、重复调用和无法终止。
- 加入确定性验证器，让 Agent 在不通过时修正一次。

#### 第一轮掌握要求

能通过 Trace 解释每一轮为什么继续或停止；能定位错误来自模型决策、工具执行、状态更新还是终止逻辑。

## 7. 第三部分：管理信息与能力

### 7.1 Context、State 与 Memory

#### 章节目标

把“模型当前看到的信息”“系统保存的运行状态”和“跨任务复用的记忆”分开设计，避免所有内容都塞进消息历史。

#### 核心知识点

- Prompt(给模型的指令)与 Context(本轮模型看到的全部信息)的区别。
- 静态上下文、动态上下文和运行时上下文。
- Context Selection(上下文选择)、Compression(压缩)与 Isolation(隔离)。
- 消息窗口裁剪、摘要和 Compaction(压缩历史并保留关键状态)。
- Working Memory(当前任务工作记忆)与任务草稿。
- Session State(会话状态)与持久化状态。
- Episodic Memory(事件经历记忆)、Semantic Memory(事实知识记忆)和 Procedural Memory(操作方法记忆)。
- 长期记忆的写入、检索、更新、冲突处理和遗忘。
- 文件系统和 Artifact(任务产物文件)作为外部记忆。
- Context Pollution(无关信息污染)、Context Rot(上下文越长效果越差)和信息冲突。
- Subagent(子智能体)的上下文隔离。
- 多用户、多会话和多任务的状态边界。

#### 关键判断

一条信息进入系统前先判断：

```text
只在本轮有用       → 当前 Context
任务期间持续变化   → Working State
跨会话需要保留     → Long-term Memory
体积较大或需审计   → File / Artifact / Database
可复用操作方法     → Skill
```

#### 最小实验

- 对超长消息做窗口裁剪和摘要，对比信息损失。
- 将任务状态持久化，重启进程后恢复并继续。
- 分别实现一条事实记忆和一条操作经验记忆。
- 制造旧记忆与新事实冲突，验证更新和回滚策略。

#### 第一轮掌握要求

能说明一条信息应该放入当前上下文、状态存储、长期记忆、Skill 还是外部文件；能实现最小压缩、持久化和恢复。

### 7.2 Tools、Environment 与 MCP

#### 章节目标

让模型能够以可理解、可验证、可控的方式影响外部世界，而不是简单给它一组函数。

#### 核心知识点

- Tool Schema(工具参数结构)、工具描述、粒度和返回契约。
- 参数校验、错误分类和失败语义。
- 只读工具、写工具和高风险工具。
- 工具幂等、超时、重试、取消和补偿。
- 串行、并行和批量工具调用。
- 工具结果压缩和大结果外置。
- Shell、Filesystem、Browser、Database 和 HTTP API 环境。
- Sandbox(隔离执行环境)、资源限制和副作用隔离。
- MCP 的 Host(宿主应用)、Client(协议客户端)、Server(能力提供方)、Transport(传输方式)和 Capability(协议能力)。
- MCP 与普通函数调用、SDK 和 Skill 的边界。
- Tool Discovery(动态发现工具)、动态加载和权限过滤。
- 人工审批和可恢复执行。

#### 关键判断

一个工具设计必须回答：

1. 模型能否仅根据名称和描述正确选择它？
2. 参数是否明确、可校验且避免歧义？
3. 返回值是否提供下一步决策真正需要的信息？
4. 调用失败能否区分可重试、需改参和永久失败？
5. 是否可能产生不可逆副作用？
6. 权限是否按任务、用户和环境最小化？

#### 最小实验

- 设计两个功能重叠的工具，观察错误选择，再重构边界。
- 为写工具加入参数校验、幂等键、审批和审计记录。
- 对长工具结果做摘要与文件外置，比较上下文消耗。
- 实现一个最小 MCP Server，并与普通函数调用做协议对照。

#### 第一轮掌握要求

能设计模型容易正确调用、失败可诊断、权限可控制的工具；能解释什么时候需要 MCP，什么时候普通 API 或 SDK 已经足够。

### 7.3 Knowledge、Search 与 RAG

#### 章节目标

建立完整的信息检索链路，能够分别诊断“没有找到正确证据”和“已经找到证据但回答错误”。

#### 核心知识点

- 文档解析、清洗、切分和元数据。
- Embedding 模型和向量索引。
- Dense Search(向量语义检索)、Sparse Search(稀疏词项检索)、Keyword Search 和 Hybrid Search(混合检索)。
- Query Rewrite(问题改写)、Expansion(扩展)和 Decomposition(拆解)。
- Metadata Filter(元数据过滤)和权限感知检索。
- Top-k、相似度阈值、召回率和精确率。
- Rerank(对候选结果重新排序)与上下文排序。
- 引用、溯源和证据绑定。
- Retrieval Eval(检索评测)与 Generation Eval(生成评测)。
- Agentic Search(由 Agent 动态决定搜索步骤)与固定 RAG Pipeline(固定检索流水线)。
- 长上下文、文件搜索、数据库查询、Web Search 和 RAG 的选择。
- 知识增量更新、版本、删除和权限变更。

#### 最小实验

- 构建包含解析、切分、索引、检索、引用的最小链路。
- 分别制造切分失败、召回失败、排序失败和生成失败。
- 对比关键词、向量和混合检索。
- 构造无权限文档，验证检索阶段而非生成阶段完成隔离。

#### 第一轮掌握要求

能从输入问题一路检查到最终引用，明确错误发生在哪个阶段；能解释什么时候不应该使用向量数据库。

## 8. 第四部分：处理复杂任务和长期任务

### 8.1 编排模式

#### 章节目标

理解常见编排模式解决什么问题，以及复杂度何时值得。不要把“多 Agent”当成默认高级方案。

#### 核心知识点

- Prompt Chaining(按固定顺序串联模型步骤)。
- Router(根据输入选择处理分支)。
- Parallelization(并行执行独立任务)。
- Map-Reduce(拆分处理后聚合结果)。
- Planner-Executor(规划者与执行者分离)。
- Orchestrator-Workers(协调者动态分配工作单元)。
- Evaluator-Optimizer(评估结果并反复优化)。
- Reflection(复盘后修正)。
- Handoff(把控制权移交给另一个 Agent)。
- Agent as Tool(把 Agent 当作上层 Agent 的工具)。
- Supervisor(监督协调者)与 Subagent。
- Multi-Agent Collaboration(多个 Agent 共同协作)。
- A2A(独立智能体系统之间的互操作协议)与跨系统 Agent 协作。
- 动态任务分解与静态工作流。
- 上下文共享、隔离和结果聚合。

#### 每个模式都要回答

1. 控制权在代码还是模型？
2. 状态由谁维护？
3. 失败在哪里重试？
4. 上下文是否隔离？
5. 是否可以并行？
6. 是否真的需要多个 Agent？

#### 最小实验

- 用同一任务实现固定链、Router 和 Planner-Executor。
- 比较单 Agent、Subagent 和多 Agent 的成功率、延迟、成本和可调试性。
- 制造一个子任务失败，验证局部重试和结果聚合。

#### 第一轮掌握要求

能根据任务的不确定性、并行性、上下文隔离和失败边界选择模式，而不是根据框架示例选择。

### 8.2 Graph 与 Durable Runtime

#### 章节目标

将复杂控制流、持久化状态和故障恢复变成显式模型，使长任务可以观察、暂停、恢复和重放。

#### 核心知识点

- State(运行状态)、Node(处理节点)和 Edge(状态转移边)。
- Conditional Edge(条件分支)、Loop 和 Reducer(合并状态更新的规则)。
- Command、Event 和状态转换。
- Subgraph(子图)和模块边界。
- Checkpoint(执行检查点)、Thread(一次持续任务的状态线)和持久化。
- Interrupt(主动暂停)、Human-in-the-loop(人工介入)和 Resume(继续执行)。
- Retry Policy(重试策略)、Timeout 和 Cancellation。
- Durable Execution(进程中断后仍可恢复的执行)。
- 节点幂等和副作用管理。
- Time Travel(从历史状态分叉执行)、Replay(按历史轨迹重放)和 Debug。
- 流式事件和进度输出。
- 确定性节点与 Agent 节点混合。

#### 关键边界

- Graph 是控制流和状态 Runtime(运行时)，不是比 Loop 更新的 Agent 算法。
- Checkpoint 保存状态，不自动保证外部副作用可以安全重放。
- 节点恢复时可能重新执行，写操作必须考虑幂等和补偿。
- 暂停等待人工输入与执行失败是两种不同状态。

#### 最小实验

- 将包含分支、循环和审批的任务建模为显式状态图。
- 在进程退出后从 Checkpoint 恢复。
- 在节点写外部系统后故意崩溃，验证幂等或补偿。
- 从旧状态分叉运行，对比两条执行路径。

#### 第一轮掌握要求

能设计一个包含分支、循环、审批、恢复和副作用的状态图；能解释哪些状态属于 Graph，哪些事实属于外部业务系统。

## 9. 第五部分：构造 Agent Harness

### 9.1 Harness Engineering

#### 章节目标

理解同一个模型为什么会因为运行支撑环境不同而表现出巨大差异，并能系统设计模型周围的上下文、工具、环境、权限、反馈和验证机制。

#### 核心知识点

- Instructions(长期指令)、Rules(规则)和约束的组织。
- Context 构建与按需加载。
- Tool Interface(工具接口)和 Toolset(可用工具集合)设计。
- Skills(可复用的方法与知识包)、领域知识包和 Progressive Disclosure(逐步按需披露)。
- Filesystem、Shell、Browser 和代码执行环境。
- Sandbox、Workspace(任务工作区)和 Artifact 管理。
- Hook(生命周期插入点)、Middleware(调用链中间处理层)和扩展点。
- 权限模型、人工审批和最小权限。
- 环境反馈和 Verification(结果验证)。
- 长任务计划、进度记录和跨会话接力。
- Subagent 的上下文隔离、并行和结果汇总。
- Context Compression 与外部状态。
- 模型、工具和环境的可替换性。
- Agent Legibility(让仓库、界面、日志和规则对 Agent 可理解)。
- Harness Entropy(支撑规则和工具长期堆积造成的混乱)及定期清理。

#### Harness 的五个核心问题

```text
模型看见什么      → Context
模型可以做什么    → Tools / Environment
模型必须遵守什么  → Instructions / Permission
模型如何知道对错  → Feedback / Verification
任务如何持续推进  → State / Plan / Checkpoint
```

#### 最小实验

- 在同一个模型和任务上，仅改变工具描述、上下文加载和验证器，对比结果。
- 设计按需加载的 Skill，比较全部注入与渐进披露。
- 为任务创建独立 Workspace 和 Sandbox，限制文件与网络能力。
- 让 Agent 自己启动目标系统、读取日志、执行测试并验证产物。
- 删除一个 Harness 组件，观察它是否真正产生增益。

#### 第一轮掌握要求

能画出一个 Agent 的完整 Harness；能解释其中每个组件补偿了模型的什么能力缺口，并通过消融实验判断它是否仍然必要。

## 10. 第六部分：评测并持续改进

### 10.1 Trace 与 Eval

#### 章节目标

将“感觉效果不错”转化为可观察、可复现、可比较的工程证据。

#### 核心知识点

- Trace(一次完整执行轨迹)、Span(轨迹中的一个操作片段)和 Event(运行事件)。
- Golden Dataset(有明确输入和验收标准的基准样本集)。
- Offline Eval(发布前离线评测)与 Online Eval(真实流量中的在线评测)。
- Task Success(任务成功率)、Tool Accuracy(工具使用正确率)和 Trajectory Quality(执行路径质量)。
- Retrieval、Generation 和端到端评测。
- Deterministic Check(程序确定性校验)、Human Review 和 LLM as Judge(使用模型评分)。
- LLM Judge 的偏差、位置效应、提示敏感性和与被测模型共谋风险。
- Trial(同一任务的一次尝试)、重复采样和置信度。
- 回归测试和版本对比。
- 延迟、Token、成本和成功率预算。
- 失败分类、错误归因和代表性样本。
- 线上监控、人工反馈和数据回流。

#### 评测对象必须分层

```text
最终结果是否正确          → Outcome Eval
工具和中间步骤是否合理    → Trajectory Eval
检索证据是否充分          → Retrieval Eval
状态和副作用是否正确      → Environment Eval
成本与延迟是否可接受      → Efficiency Eval
是否违反权限和安全边界    → Safety Eval
```

#### 最小实验

- 为一个 Agent 创建至少十条正常与失败样本。
- 使用程序断言和 LLM Judge 分别评分，比较分歧。
- 对同一版本重复运行多次，观察非确定性。
- 比较两个 Prompt、模型或 Harness 版本，验证是否真实提升。

#### 第一轮掌握要求

每个实验和项目能力都有明确成功标准、失败样本和回归验证；能够从 Trace 定位失败环节，而不是只阅读最终回答。

### 10.2 Loop Engineering 与持续改进

#### 章节目标

在单次任务循环之外建立外层学习循环，让系统能够从真实执行证据中持续优化，同时防止错误经验、评测过拟合和失控修改。

#### 四层 Loop

```text
第一层：Task Loop
Observe → Decide → Act → Verify → Stop

第二层：Verification Loop
执行 → 验证 → 反馈 → 修正 → 再验证

第三层：Event-driven Loop(事件驱动循环)
事件触发 → 执行 → 审批 / 恢复 → 持续运行

第四层：Improvement Loop(系统改进循环)
收集 Trace → 失败归因 → 生成候选改进
→ 离线 Eval → 安全门禁 → 发布 / 回滚
```

#### 核心知识点

- 从 Trace 中提取成功经验和失败模式。
- 失败聚类、根因归因和代表性样本选择。
- 将偶然成功与可复用策略分开。
- Prompt 优化、上下文策略优化和工具描述优化。
- Memory Consolidation(把零散记忆合并为稳定知识)。
- Skill Discovery(从轨迹发现可复用方法)、生成、测试、版本和淘汰。
- Tool、Workflow 和 Harness 的候选修改。
- Harness Adaptation(运行支撑环境适配)与模型权重更新的区别。
- 离线候选生成与在线自动修改的风险差异。
- Holdout Set(不参与优化的保留评测集)和防止 Eval 过拟合。
- 非回退门禁：新版本不能只提升局部样本并破坏已有能力。
- Shadow Run(影子运行，不影响真实用户)、Canary(小流量试运行)和渐进发布。
- 版本、审批、审计、回滚和 Kill Switch(紧急停止开关)。
- 数据投毒、错误记忆扩散、Reward Hacking 和自我确认偏差。
- Agent 修改 Prompt、Skill、配置和代码时的权限分级。
- 开放式自我改写与受控工程优化的边界。

#### 受控改进闭环

```text
真实任务与 Trace
       ↓
失败分类和根因归因
       ↓
提出改进假设
       ↓
生成 Prompt / Skill / Tool / Workflow / Harness 候选
       ↓
离线回放 + 保留集评测 + 安全检查
       ↓
人工审批或策略门禁
       ↓
影子运行 / 小流量发布
       ↓
监控、回滚、继续积累证据
```

#### 最小实验

- 从一批失败 Trace 中聚类三类问题，并提出不同层次的修复方案。
- 从成功轨迹生成一个 Skill，使用独立样本验证能否复用。
- 自动生成两个 Prompt 或工具描述候选，只允许通过回归门禁的版本发布。
- 故意写入一条错误记忆，验证审批、版本和回滚。
- 比较“只改模型 Prompt”和“修改 Harness”对成功率与成本的影响。

#### 第一轮掌握要求

能设计一个可审计、可评测、可回滚的改进闭环；不会把“Agent 可以改自己”误判为已经具备安全可靠的自进化能力。

## 11. 第七部分：走向生产环境

### 11.1 可靠性、安全与治理

#### 章节目标

控制 Agent 的非确定性、外部副作用和权限风险，使系统发生错误时能够被限制、发现、恢复和追责。

#### 核心知识点

- Prompt Injection(通过输入诱导 Agent 违反原指令)。
- Tool Output Injection(工具返回内容中的恶意指令)。
- 数据泄露、越权调用和供应链风险。
- Guardrail(输入、输出或工具调用的安全检查)与 Policy(可执行策略)。
- 内容过滤和敏感数据处理。
- Least Privilege(最小权限)和高风险动作审批。
- 身份、用户、租户、任务和工具权限边界。
- 凭证隔离、短期令牌和秘密管理。
- Sandbox、网络限制、资源配额和副作用隔离。
- 故障注入、超时、重试、降级和恢复。
- 幂等、补偿事务和人工兜底。
- 数据保留、删除、审计和合规。
- 第三方工具、MCP Server 和 Skill 的供应链治理。
- 安全 Eval、红队测试和持续监控。

#### 最小实验

- 在用户输入、检索文档和工具结果中分别注入恶意指令。
- 为高风险写操作加入审批、最小权限和审计。
- 模拟模型超时、工具失败、状态库不可用和重复执行。
- 验证 Agent 无法读取未授权文件、凭证和其他用户状态。

#### 第一轮掌握要求

能建立威胁模型，明确可信边界和副作用；能够证明高风险动作默认无法绕过审批和权限控制。

### 11.2 Agent 系统工程

#### 章节目标

把本地 Demo 提升为具有明确契约、可观测、可扩展、可治理的服务。

#### 核心知识点

- API 服务、流式协议和异步任务。
- 并发、队列、Backpressure(下游处理不过来时的背压)和限流。
- 缓存、批处理和模型路由。
- 多租户、会话隔离和数据模型。
- 配置、密钥和环境管理。
- 日志、指标、Trace 和告警。
- 容器化、部署、扩缩容和灰度。
- 成本核算、预算和配额。
- 模型、Prompt、Skill、Tool 和 Harness 版本管理。
- 数据保留、删除和合规。
- SLA(服务等级目标)、降级、灾备和恢复。
- 长任务调度、Worker(后台执行进程)和任务租约。
- 状态存储、Artifact 存储和业务数据的一致性。
- 模型供应商故障切换和能力差异治理。

#### 最小实验

- 将 Agent 封装为支持流式事件和异步任务的 API。
- 并发执行多条任务，验证会话隔离、限流和取消。
- 统计每个任务的模型、工具、存储和人工成本。
- 模拟进程退出和供应商故障，验证恢复和降级。

#### 第一轮掌握要求

能给 Agent 服务定义输入输出契约、状态边界、可观测指标和故障恢复方案；能说明哪些生产问题由 Agent 特性引入，哪些属于通用分布式系统问题。

## 12. 支线知识

支线必须进入全局视野，但第一轮不与 Agent 主干平均投入。

| 支线方向 | 第一轮要求 | 深入学习的触发条件 |
|---|---|---|
| 机器学习核心算法 | 知道监督、无监督、分类、排序和预测的基本问题 | 需要训练传统模型 |
| Transformer 数学推导 | 能解释核心公式和计算复杂度 | 研究模型结构或推理优化 |
| LoRA、QLoRA、SFT | 知道它们改变模型行为的方式和成本 | Prompt、RAG、Tool 无法完成行为适配 |
| 量化与私有化推理 | 理解精度、吞吐、显存和延迟取舍 | 需要自部署或显著降本 |
| OpenCV、YOLO | 能定位传统视觉链路的作用 | 项目涉及检测、跟踪或传统图像处理 |
| 多模态训练 | 知道数据、对齐和评测问题 | 需要定制视觉、语音或视频模型 |
| 具身智能 | 理解感知、规划、控制和物理反馈闭环 | 项目进入机器人或真实物理环境 |
| 分布式训练 | 理解数据、模型和流水线并行概念 | 目标转向模型训练工程 |

“第一轮低投入”表示延后深入，不表示删除。

## 13. 跨章节概念定位

| 概念 | 在体系中的位置 |
|---|---|
| Prompt Engineering | 编写和组织模型指令的方法 |
| Context Engineering | 每轮选择、组织、压缩和隔离模型可见信息 |
| Tool Calling | Agent Loop 对外行动的模型协议 |
| Tool Engineering | 工具契约、错误、幂等、副作用和权限设计 |
| MCP | AI 应用接入外部工具、资源和交互能力的标准协议 |
| A2A | 独立 Agent 系统之间进行能力发现、任务通信和状态协作的协议 |
| RAG | 从外部知识中检索证据并加入 Context 的机制 |
| Memory | 跨轮次或跨任务保存和恢复信息 |
| Skill | 可复用、可按需加载、可测试的方法和领域知识包 |
| Sandbox | 隔离 Agent 代码、文件、网络和命令副作用的环境 |
| Human-in-the-loop | 执行过程中的暂停、检查、审批和恢复 |
| Graph | 显式状态、控制流和持久化执行 Runtime |
| Subagent | 隔离上下文并完成子任务的执行单元 |
| Multi-Agent | 多个 Agent Loop 的协作拓扑 |
| Harness | 环绕模型与 Loop 的上下文、工具、环境、权限和反馈系统 |
| Eval | 衡量能力、发现失败和验证改进的系统 |
| Loop Engineering | 设计、叠加和优化任务、验证、事件与改进循环 |
| Self-Evolution | 系统基于经验更新 Memory、Skill、Prompt、Tool、Workflow、Harness 或模型的能力 |

## 14. 完整性与维护原则

- 新概念必须先定位到现有章节，再判断是否需要新增章节。
- 框架名称不作为一级知识模块，框架只是机制实现样本。
- 热点名词先进入`前沿雷达.md`，不能因为流行直接成为主干。
- 主干知识点必须进入`学习进度.md`，但进度文档不重复解释知识。
- 每个主干章节必须定义机制、失败边界、最小实验和掌握证据。
- 资料变化时先判断底层机制是否变化，不跟随 API 名称频繁重写总纲。
- 新内容进入主干必须有官方文档、源码、论文或可复现实验支撑。
- 学习中发现缺口时，先更新总纲和进度，再调整项目。
- 定期删除已经被模型能力吸收、实验无法证明增益或只增加复杂度的 Harness 组件。
