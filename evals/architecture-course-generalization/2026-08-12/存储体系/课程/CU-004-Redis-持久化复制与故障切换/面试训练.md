# CU-004：Redis 持久化、复制与故障切换 - 面试训练

> 对应推导式理解：[推导式理解](推导式理解.md)

## 1. Redis 的 RDB 和 AOF 有什么区别，怎样选择？

题型：缓存与持久化原理题

一句话核心判断：RDB 保存时间点数据集，AOF 保存写操作序列，选择取决于恢复速度、可接受数据丢失窗口和运行时成本。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 进程重启后所有内存数据消失 |
| 最小机制是什么 | 快照、追加日志、同步策略和安全切换 |
| 工程收益 | 能按 RPO 和恢复速度设计 Redis 的角色 |
| 边界和代价 | fork、Copy-on-Write、磁盘 I/O 和日志重写 |

30 秒回答：

> RDB 周期性保存完整时间点快照，文件紧凑、加载快，但两次快照之间的数据可能丢失；AOF 记录写命令，可通过 always、everysec 等同步策略控制窗口，通常恢复点更接近故障时刻，但文件更大并需要重写。实际选择先看 Redis 是可重建缓存还是事实源，再看可接受 RPO、恢复时间和性能成本。

完整回答：

RDB 适合备份、快速恢复和从节点全量同步基线。后台快照通常通过 fork 产生一致视图，写入密集时 Copy-on-Write 会增加内存压力。

AOF 在命令执行后追加日志，持久化强度取决于同步策略。AOF 重写根据当前数据状态生成更短的等价命令集，并在切换过程中继续处理增量写。两者可以组合，但必须明确启动加载顺序、损坏检测和容量告警。

ASCII 图或关键表：

| 维度 | RDB | AOF |
|---|---|---|
| 数据形态 | 时间点快照 | 写命令日志 |
| 恢复速度 | 通常较快 | 取决于日志长度 |
| 丢失窗口 | 快照间隔 | 同步策略窗口 |
| 运行成本 | fork、快照 I/O | 持续追加、fsync、重写 |

追问：

- 原理追问：AOF 重写期间的新写入怎样处理？
- 工程追问：RDB fork 为什么可能造成延迟抖动？
- 项目追问：登录会话和热点商品缓存会使用相同持久化配置吗？

证据：

Redis 配置、RDB/AOF 文件、INFO persistence 指标和重启恢复序号。

阶段一：RDB 快照与 AOF 日志。

## 2. Redis 主从复制怎样支持断线后的部分重同步？

题型：复制协议原理题

一句话核心判断：主从通过复制身份和偏移描述进度，主节点的复制积压缓冲仍覆盖缺失区间时，副本可以只补增量。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 每次短暂断线都要重新传输完整数据集 |
| 最小机制是什么 | 复制 ID、主从偏移和积压缓冲 |
| 工程收益 | 降低短时网络抖动后的恢复流量与时间 |
| 边界和代价 | 缓冲有限，断线过久仍需全量同步 |

30 秒回答：

> 主节点和副本维护复制身份与偏移，副本断线重连时会携带自己已处理的位置。如果主节点仍保留对应复制历史，并且缺失范围还在复制积压缓冲中，就从该偏移继续发送；否则副本需要重新进行全量同步，再接收后续增量。

完整回答：

复制流可以理解为一条有位置的写命令序列。副本持续推进自己的偏移，主节点在固定容量的积压缓冲中保留最近一段历史。

部分重同步是否成功取决于复制身份匹配和历史是否仍可取。缓冲过小、断线太久或主节点复制历史变化都会触发全量同步。偏移只表示复制流进度，不证明副本已 fsync，也不保证读副本没有陈旧。

ASCII 图或关键表：

```text
主复制流：1000 ---------------- 1200
积压缓冲：      1080 --------- 1200
副本偏移：      1100
重连结果：从 1101 增量发送
```

追问：

- 原理追问：复制积压缓冲太小会怎样？
- 工程追问：怎样监控副本延迟和全量同步频率？
- 项目追问：允许客户端读取副本时怎样处理陈旧会话？

证据：

INFO replication 中的复制 ID、偏移、积压缓冲状态和同步日志。

对应推导章节：

阶段二：主从复制与复制偏移。

## 3. Sentinel 故障切换为什么不能保证已确认写零丢失？

题型：高可用与一致性边界题

一句话核心判断：Sentinel 自动恢复主节点角色和服务入口，但 Redis 普通复制默认异步，故障时尚未到副本的写无法被选主过程恢复。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 主节点故障后需要人工发现和切换 |
| 最小机制是什么 | 多 Sentinel 故障确认、选主和客户端发现 |
| 工程收益 | 缩短不可用时间并自动重配拓扑 |
| 边界和代价 | 检测窗口、切换抖动、旧写丢失和重试重复 |

30 秒回答：

> Sentinel 负责监控、确认主节点下线、选择进度较新的副本并提升为新主，再通知客户端重连。但普通主从复制是异步的，主节点可能在副本收到命令前就向客户端返回成功；如果此时主故障，所有候选副本都没有这次写，切换只能恢复可用性，不能创造缺失数据。

完整回答：

故障切换首先处理控制面：多个 Sentinel 从主观下线形成客观下线，协调由谁执行切换，再根据优先级和复制进度选择副本。新主产生后，其他副本被重新配置，客户端通过 Sentinel 或代理发现新地址。

数据面仍受复制进度限制。可通过监控延迟、限制副本不足时的主写入、关键操作使用 WAIT 或把 Redis 定位为可重建缓存来降低风险，但 WAIT 也不把系统变成共识数据库。业务还要处理重试幂等和旧主恢复后的角色变化。

ASCII 图或关键表：

```text
客户端成功写 #1050
主节点偏移   #1050
最佳副本偏移 #1040
主节点故障
  → Sentinel 提升副本
  → #1041 - #1050 可能丢失
```

追问：

- 原理追问：主观下线和客观下线有什么区别？
- 工程追问：WAIT 能保证哪些事情，不能保证哪些事情？
- 项目追问：如果 Redis 中的会话丢失，业务会怎样恢复或降级？

证据：

Sentinel 切换日志、客户端成功序号、主从偏移差、新主最大数据序号和重连耗时。

对应推导章节：

阶段三：Sentinel 故障检测与选主；阶段四：异步复制的数据丢失窗口。
