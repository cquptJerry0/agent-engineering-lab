中心问题：登录会话保存在 Redis 中，主节点故障后 Sentinel 已经完成切换，为什么仍可能丢失刚刚返回成功的登录状态？

## 核心推导链

```text
Redis 只在内存保存会话
  ↓ 进程重启会丢失
RDB 快照 / AOF 日志提供单机恢复
  ↓ 单机和机器仍会失效
主从复制传播写入并记录偏移
  ↓ 主节点故障需要新入口
Sentinel 判断主观与客观下线并选主
  ↓ 复制默认异步
故障切换可能丢失尚未到副本的已确认写
```

## 贯穿案例与初始状态

认证服务执行：

```text
SET session:abc user-42 EX 3600
```

客户端收到成功后立即访问另一个实例。此时 Redis 主节点进程崩溃，随后 Sentinel 选举副本为新主。

| 维度 | 初始状态 |
|---|---|
| 用户目标 | 登录成功后会话持续可读，节点故障时服务自动恢复 |
| 已有输入 | 会话 Key、TTL、主节点、两个副本和三个 Sentinel |
| 当前状态 | 最新写首先只存在主节点内存 |
| 可用能力 | RDB、AOF、异步复制、复制积压缓冲、Sentinel |
| 约束与资源边界 | 持久化与复制都异步推进，故障检测存在时间窗口 |
| 预期输出 | 新主可写、客户端重连，并明确最多可能丢失什么 |
| 副作用或复杂度代价 | 磁盘 I/O、复制延迟、切换抖动和陈旧读 |
| 成功标准 | 能区分重启恢复、节点冗余、自动选主和数据安全 |

## 阶段一：RDB 快照与 AOF 日志

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| RDB 快照 | 保存某个时间点的数据集 | 恢复快但存在快照间隔窗口 |
| AOF 追加日志 | 记录写命令 | 可按同步策略缩小丢失窗口 |
| AOF 重写 | 用当前数据状态压缩历史命令 | 控制日志体积 |

### 当前问题

纯内存 Redis 进程重启后，所有会话状态消失。系统需要把内存状态转化为可恢复介质数据。

### 推导过程

V0 只有内存。V1 引入两类持久化：

```text
RDB：定期把当前数据集生成快照
AOF：按写入顺序追加命令，并周期同步
```

RDB 提供紧凑恢复基线，AOF 用更细粒度日志缩小最近写入窗口；重写根据当前状态生成等价更短日志。

### 机制全解

RDB 是时间点快照，适合备份和快速加载，但两次快照之间的写可能在崩溃时丢失。后台生成快照还会带来 fork、Copy-on-Write 和 I/O 压力。

AOF 记录改变数据的操作。`appendfsync always`、`everysec`和`no`代表不同持久化延迟与性能取舍。AOF 重写不是简单删除旧日志，而是根据当前数据生成可恢复到等价状态的新命令集，再安全切换日志。

同时开启时还要明确启动恢复优先级和损坏处理策略。持久化解决单机重启恢复，不提供节点仍然可访问的高可用。

### 状态变化

| 维度 | 纯内存 | 持久化后 |
|---|---|---|
| 输入 | 会话写命令 | 命令、快照周期和同步策略 |
| 状态 | 只在内存 | 内存 + RDB / AOF |
| 控制过程 | 写完立即返回 | 后台快照或日志追加与同步 |
| 输出 | 重启全丢 | 可恢复到某个持久点 |
| 仍未解决 | 无恢复 | 节点故障期间不可服务 |

### 阶段结论

持久化回答“节点重启后恢复什么”，但不回答“节点失效时谁继续提供服务”。

## 阶段二：主从复制与复制偏移

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| 主从复制 | 把主节点写命令传播给副本 | 提供冗余和读副本 |
| 复制偏移 | 表示副本已经处理到的数据位置 | 判断复制进度 |
| 复制积压缓冲 | 保留最近复制流 | 支持部分重同步 |

### 当前问题

即使主节点能够从 AOF 恢复，进程重启期间服务仍不可用，机器损坏还可能让本地持久化一起丢失。

### 推导过程

V1 只有单机恢复。V2 增加副本：主节点执行写入后，把复制流发送给副本；双方用复制 ID 和偏移描述进度。短暂断线时，如果缺失区间仍在积压缓冲中，副本只补缺口，否则需要完整同步。

### 机制全解

Redis 复制默认异步，主节点不会为每次普通写等待副本确认。副本初次连接或无法部分同步时，需要加载主节点生成的数据基线，再继续接收后续写命令。

复制偏移让系统知道副本落后多少字节，但“偏移接近”不等价于业务无丢失，也不代表副本已经把数据持久化到磁盘。复制可以提供冗余和扩展读，但读副本可能观察旧数据。

### 状态变化

| 维度 | 单机持久化 | 加入复制后 |
|---|---|---|
| 输入 | 本地写命令 | 复制流、复制 ID 和偏移 |
| 状态 | 一个节点的数据版本 | 主节点和多个副本进度 |
| 控制过程 | 本地日志与快照 | 全量或部分同步 |
| 输出 | 重启后恢复 | 节点间冗余和可选读扩展 |
| 仍未解决 | 单机不可用 | 谁判断主故障并切换入口 |

### 阶段结论

复制建立副本状态和追赶协议，但不会自动决定何时提升副本，也没有改变普通写的异步确认语义。

## 阶段三：Sentinel 故障检测与选主

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| 主观下线 | 单个 Sentinel 认为主节点不可达 | 产生故障怀疑 |
| 客观下线 | 足够 Sentinel 同意故障 | 允许进入故障切换 |
| 副本选择与提升 | 从候选副本选新主 | 恢复写入口 |
| 客户端发现 | 返回当前主节点地址 | 让应用重连 |

### 当前问题

复制拓扑已经存在，但客户端仍连接旧主；单个监控进程的网络抖动也不能直接决定主节点死亡。

### 推导过程

V2 有副本但无控制面。V3 引入多个 Sentinel：持续监控主从状态，先形成主观下线，再通过法定数量确认客观下线；获得故障切换领导权的 Sentinel 选择合适副本提升为新主，重配其他副本并向客户端提供新地址。

### 机制全解

Sentinel 使用多个观察者减少单点误判。故障切换包含故障确认、选举协调、候选副本选择、提升、其余副本重配置和客户端拓扑更新。

客户端必须使用支持 Sentinel 的发现方式并实现重连、超时和幂等重试。切换期间可能出现短暂不可写、旧连接失败和请求重试。Sentinel 解决的是监控和自动故障切换，不负责数据分片。

### 状态变化

| 维度 | 静态主从 | Sentinel 控制后 |
|---|---|---|
| 输入 | 固定主地址 | 多观察者健康信息 |
| 状态 | 主从复制进度 | 主观/客观下线、任期和新拓扑 |
| 控制过程 | 人工切换 | 检测、协调、提升和重配置 |
| 输出 | 主故障后中断 | 自动产生新主并更新发现 |
| 仍未解决 | 无自动恢复 | 已确认写是否都在新主 |

### 阶段结论

Sentinel 提高服务恢复自动化，但故障切换只能从已有副本中选择，无法创造尚未复制的数据。

## 阶段四：异步复制的数据丢失窗口

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| 异步复制窗口 | 描述主确认与副本接收之间的差异 | 界定故障切换可能丢失的数据 |
| 复制延迟 | 衡量副本落后程度 | 影响读一致性与选主质量 |
| WAIT 与写入约束 | 在特定请求中等待副本确认或限制风险 | 缩小但不消除所有故障窗口 |

### 当前问题

认证服务收到 SET 成功，但主节点在把命令发给副本前崩溃。Sentinel 提升的副本没有该会话，用户下一次请求重新变成未登录。

### 推导过程

V3 自动切换可用，但把“新主上线”误当成“所有已确认写都保留”。V4 显式建模两个进度：

```text
主节点客户端确认偏移 = 1050
最佳副本已应用偏移   = 1040
```

故障切换后，偏移 1041 到 1050 的写存在丢失风险。系统可监控复制延迟，配置主节点在副本不足或落后过大时拒绝写，也可对关键操作使用 WAIT 等待副本确认，但仍需理解其故障语义。

### 机制全解

异步复制优先低写延迟，代价是客户端成功与副本持有之间存在窗口。Sentinel 选主通常会考虑副本优先级和复制进度，但任何副本都没有的数据无法恢复。

WAIT 可以让客户端等待指定数量副本确认已接收复制流，提升数据安全概率，但它不把 Redis 转化为强一致共识系统，也不等价于副本已经持久化。网络分区、旧主重新出现和客户端重试还需要幂等或业务补偿。

### 状态变化

| 维度 | 只关注可用性 | 显式建模丢失窗口 |
|---|---|---|
| 输入 | 节点健康和拓扑 | 客户端确认偏移、各副本偏移和持久化策略 |
| 状态 | 有新主即可 | 知道可能缺失的写入区间 |
| 控制过程 | 自动切换 | 监控延迟、限制写入、等待副本或补偿 |
| 输出 | 服务恢复 | 服务恢复且风险可量化 |
| 仍未解决 | 隐性数据丢失 | 强一致事务和跨地域容灾 |

### 阶段结论

高可用、持久化和数据一致性是三组不同目标。Redis 可以组合这些能力，但必须明确客户端成功点、复制确认和持久化点之间的距离。

## 正常链路与失败链路

```text
正常：
SET → AOF 追加 / 内存更新 → 复制流发送 → 副本偏移推进
  → 主故障 → Sentinel 确认 → 提升最新副本 → 客户端重连

失败：
主节点先回复成功 → 写尚未复制 → 主故障
  → Sentinel 提升旧副本 → 会话丢失
  → 可用性恢复但业务状态回退
```

## 实验任务卡

### 实验任务一：比较 RDB 与 AOF 恢复窗口

实验目标：观察不同持久化策略对重启恢复点和延迟的影响。

覆盖知识点：RDB 快照、AOF 追加日志和重写。

准备条件：本地 Redis 测试实例，分别配置 RDB、AOF everysec 和无持久化模式。

操作步骤：

```text
1. 连续写入带序号的 1000 个 Key。
2. 在固定时间点强制结束 Redis 进程。
3. 重启后统计最大连续序号和缺失数量。
4. 比较启动时间、文件大小和运行时延迟。
```

预期现象：无持久化全部丢失；RDB 恢复到最近快照；AOF everysec 通常保留更接近故障时的数据，但具体结果受同步时刻影响。

通过标准：能把恢复结果对应到配置，且不把进程强杀等同机器断电。

产出证据：配置、持久化文件、恢复序号、启动耗时和写延迟。

### 实验任务二：制造复制落后与 Sentinel 切换

实验目标：验证自动故障切换与数据零丢失不是同一结论。

覆盖知识点：主从复制、复制偏移与部分重同步；Sentinel 监控、选主与客户端重连；异步复制的数据丢失窗口。

准备条件：一主两从三 Sentinel 的隔离测试环境，可控制副本网络或暂停进程。

操作步骤：

```text
1. 暂停两个副本或限制复制网络。
2. 向主节点写入递增序号并记录客户端成功响应。
3. 在副本落后时终止主节点。
4. 等待 Sentinel 完成切换。
5. 连接新主，比较最大序号和复制偏移。
6. 恢复旧主并观察其角色变化。
```

预期现象：Sentinel 可以恢复新主和写入口，但新主可能缺少最后一段成功写。

通过标准：能量化客户端确认序号与新主最大序号差，并记录切换不可写窗口。

产出证据：Sentinel 日志、主从偏移、客户端成功序号、新主数据和重连时间线。

## 边界、代价与下一问题

本 CU 聚焦 Sentinel 主从模式，没有展开 Redis Cluster 槽位迁移、跨分片事务和多机房灾备。测试中的强杀和网络隔离也不能覆盖所有电源、磁盘和时钟故障。

如果业务不能接受会话丢失，应先判断 Redis 是否只是可重建缓存；若它承担唯一事实源，需要更强持久化、复制确认、上游数据库或业务补偿。

## 自测题与答案

### 题目一

RDB 和 AOF 的核心取舍是什么？

参考答案：RDB 保存时间点快照，文件紧凑、恢复快，但快照间隔内写入可能丢失；AOF 记录写操作，可用同步策略缩小窗口，但日志更大并需要重写。

判分点：覆盖恢复点、运行成本和文件形态。

常见误区：认为 AOF 一定零丢失，忽略 appendfsync 配置和设备故障。

### 题目二

Redis 部分重同步依赖什么状态？

参考答案：依赖主从复制身份、复制偏移和主节点保留的复制积压缓冲；缺失区间仍在缓冲中时可以增量追赶，否则需要全量同步。

判分点：说出偏移和积压缓冲。

常见误区：认为只要副本重连就一定不需要全量同步。

### 题目三

Sentinel 已完成故障切换，为什么还可能丢数据？

参考答案：普通 Redis 主从复制默认异步，主节点可以在副本接收前回复客户端；故障切换只能选择已有副本，尚未复制的数据不在任何候选新主上。

判分点：区分可用性恢复和数据安全，并指出主确认与副本进度差。

常见误区：把“有多个副本”直接等同于强一致。

## 知识关系图

```text
[内存数据]
  ├─ 时间点保存 → [RDB 快照]
  └─ 写操作记录 → [AOF 日志]
                       ↓ 单机仍会故障
[主从复制]
  └─ 用复制偏移追踪进度 → [副本]
                                  ↓ 主节点失效
                             [Sentinel 选主]
                                  ↓
                         [客户端重连与服务恢复]
                                  └─ 仍受异步复制窗口限制 → [可能丢失最近写]
```

### 如何读图

先沿持久化分支判断单节点重启能恢复什么，再沿复制和 Sentinel 分支判断节点故障后谁接管。最后比较客户端确认点与副本偏移，判断高可用切换后的数据风险。
