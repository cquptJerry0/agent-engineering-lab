# CU-003：页缓存、文件系统与 fsync 持久化语义 - 面试训练

> 对应推导式理解：[推导式理解](推导式理解.md)

## 1. write、flush、close 和 fsync 的语义有什么区别？

题型：操作系统与存储基础题

一句话核心判断：它们跨越的缓冲层和保证范围不同，只有明确的同步协议才能建立应用需要的持久化提交点。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 应用会把“内核接受”误报成“断电不丢” |
| 最小机制是什么 | 用户缓冲、页缓存、同步接口和错误检查 |
| 工程收益 | 能定义日志、配置和事务的真实成功语义 |
| 边界和代价 | 同步写增加延迟，具体保证依赖平台和设备 |

30 秒回答：

> flush 通常把语言或库的用户态缓冲提交给内核；write 表示内核接受字节并更新页缓存；close 释放文件描述符，但一般不能替代持久化同步；fsync 会等待文件数据和恢复所需元数据同步，并返回错误。文件可立即读到可能只是命中页缓存，不能证明断电后仍在。

完整回答：

应用写文件经历多层缓冲。标准库或运行时可以先把数据留在进程内，flush 负责把这部分数据交给操作系统。write 返回后，数据通常已经在内核页缓存中并被标记为脏页。

close 负责关闭描述符和触发必要清理，但应用如果需要在返回成功前建立持久化边界，应使用平台定义的同步接口并检查错误。fsync 的完成还不一定覆盖新文件名的目录项，所以原子替换协议可能还需要同步父目录。

ASCII 图或关键表：

```text
应用缓冲 --flush--> 内核页缓存 --fsync--> 文件系统 / 设备持久状态
                                close 主要负责释放描述符
```

追问：

- 原理追问：为什么读回刚写的数据不能证明已经持久化？
- 工程追问：每次请求都 fsync 会带来什么性能问题？
- 项目追问：审计日志和普通调试日志会采用相同持久化策略吗？

证据：

strace 中的 write/fsync/close 序列、同步耗时分布和故障恢复结果。

对应推导章节：

阶段一：应用缓冲与内核页缓存；阶段二：脏页回写与文件系统状态；阶段三：fsync 与持久化确认。

## 2. 怎样可靠地更新一个配置文件，避免崩溃后留下半文件？

题型：文件更新工程题

一句话核心判断：使用同目录临时文件生成完整候选版本，先同步内容，再原子重命名，最后按平台语义同步父目录。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | truncate 后崩溃可能留下空文件或半内容 |
| 最小机制是什么 | 临时文件、内容校验、fsync、rename 和目录同步 |
| 工程收益 | 恢复时更接近旧版本或完整新版本二选一 |
| 边界和代价 | 跨文件系统 rename、权限和平台差异需单独处理 |

30 秒回答：

> 我不会直接覆盖目标文件，而是在同一目录写临时文件，完成 flush 和 fsync 后校验内容，再用 rename 原子替换目标路径，并根据操作系统和文件系统语义同步父目录。这样内容完整性、路径切换原子性和目录项持久化由不同步骤分别保证。

完整回答：

直接 truncate 目标文件后分段写入，崩溃可能发生在任意位置。临时文件策略保留旧版本，只有新版本完整写入并同步后才切换路径。

同目录很重要，因为跨文件系统移动可能变成复制加删除。rename 保证并发读者通常看到旧文件或新文件，不看到中间路径状态；但“原子可见”与“断电持久”不同，目录项变化可能还要同步父目录。

ASCII 图或关键表：

```text
write temp
  → fsync temp
  → verify
  → rename temp to target
  → fsync parent directory
  → report success
```

追问：

- 原理追问：rename 的原子性解决了什么，没有解决什么？
- 工程追问：临时文件残留怎样安全清理？
- 项目追问：多个配置文件需要一起更新时，这个协议还够吗？

证据：

不同故障点下的目标文件哈希、目录内容和恢复矩阵。

对应推导章节：

阶段四：原子重命名与目录同步。

## 3. 为什么数据库通常使用 WAL，而不是每次提交都同步所有数据页？

题型：存储引擎演进题

一句话核心判断：WAL 把离散随机数据页更新转换为较小的顺序日志持久化，再异步回写数据页，从而兼顾提交延迟和崩溃恢复。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 每个事务都等待多个随机数据页落盘 |
| 最小机制是什么 | 先日志后数据页、提交记录和恢复重放 |
| 工程收益 | 提交只同步连续日志，并可使用组提交 |
| 边界和代价 | 日志管理、检查点和恢复过程增加复杂度 |

30 秒回答：

> 数据库一次事务可能修改多个离散数据页，如果提交时同步全部页，随机 I/O 和写入数量都很高。WAL 要求描述变化的日志先于对应数据页持久化，事务提交只需保证日志到达持久化边界；崩溃后再根据日志重做已提交变化，未提交变化由事务状态或 Undo 处理。

完整回答：

WAL 利用顺序追加降低提交路径成本。数据页可以继续留在缓冲池中，由后台线程批量回写；只要更新这些页所需的日志已经先持久，崩溃后就能从检查点开始重放。

Group Commit 还可以让多个事务共享一次日志同步。代价是系统必须维护日志序列号、检查点、恢复扫描和日志空间，并确保日志与数据页的顺序约束不被破坏。

ASCII 图或关键表：

```text
事务修改缓冲页
  → 追加 WAL
  → fsync WAL / 组提交
  → 返回提交成功
  → 后台回写数据页
  → 崩溃后重放
```

追问：

- 原理追问：为什么日志必须先于数据页持久化？
- 工程追问：检查点太慢会产生什么问题？
- 项目追问：你会怎样验证一个数据库的提交持久化配置？

证据：

数据库 WAL 配置、提交日志、检查点指标和崩溃恢复实验。

对应推导章节：

阶段二：脏页回写与文件系统状态；阶段三：fsync 与持久化确认。
