## 核心推导链

```text
应用生成订单数据
  ↓ 写入运行时缓冲
flush 把字节交给 write
  ↓ 进入内核页缓存并标记脏页
后台回写安排文件数据与元数据
  ↓ 仍存在崩溃窗口
fsync / fdatasync 请求持久化
  ↓ 文件替换还涉及目录项
临时文件 + 原子重命名 + 目录同步
```

| 用户目标 | 返回成功后，进程崩溃或机器断电仍能恢复已确认订单 |
| 已有输入 | JSON 字节、目标路径和文件描述符 |
| 当前状态 | 应用只知道高层写文件 API 返回成功 |

| 约束与资源边界 | 磁盘慢于内存，系统需要批量回写；断电时内存状态会消失 |

| 成功标准 | 能指出每次返回成功时数据停留层级，以及断电后保证范围 |

## 阶段一：应用缓冲与内核页缓存

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| 用户缓冲 | 聚合小写入，减少系统调用 | 可能让数据仍停在进程内 |
| 运行时 flush | 把语言或库缓冲交给内核 | 不等价于稳定介质写入 |
| 内核页缓存 | 用内存吸收读写并延迟设备 I/O | 引出脏页和回写 |

### 当前问题

高层`writeFile`或流写入可能先进入语言运行时缓冲。即使 API 已经把字节交给内核，数据也通常先进入页缓存，不会同步等待设备完成写入。

### 推导过程

V0 把“函数返回”当作“磁盘完成”。V1 拆分数据位置：

```text
业务对象
  → 序列化字节
  → 语言 / 库缓冲
  → 系统调用
  → 内核页缓存
```

每次边界返回只证明下一层接受了数据，不能越级证明最终介质已经持久。

### 机制全解

用户缓冲存在于进程地址空间，例如标准 I/O 或运行时流内部。flush 通常只把这部分数据提交给操作系统。内核页缓存则保存文件页，允许应用快速完成 write，并由内核统一调度后续设备写入。

缓冲提高吞吐并合并小 I/O，但把“应用观察到成功”和“断电后数据仍在”分开。进程崩溃会丢失尚未 flush 的用户缓冲；机器断电还会丢失未写入稳定介质的页缓存。

### 状态变化

| 维度 | 高层写入开始前 | 缓冲与页缓存后 |
|---|---|---|
| 输入 | 业务对象 | 序列化字节和目标文件 |
| 状态 | 数据只在应用对象中 | 可能在用户缓冲或页缓存 |
| 控制过程 | 调用高层 API | flush、系统调用和内核复制 |
| 输出 | 无文件写入状态 | write 可快速返回 |
| 仍未解决 | 没有保存 | 断电后是否保留 |

### 阶段结论

应用缓冲和页缓存解释了为什么写文件可以很快，也解释了为什么“返回成功”仍不等于持久化。

## 阶段二：脏页回写与文件系统状态

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| write 系统调用 | 把字节复制或映射到内核管理的文件页 | 产生脏页 |
| 脏页与后台回写 | 延迟、合并并调度设备写入 | 提高吞吐但保留窗口 |
| 文件数据与元数据 | 分别表示内容和文件结构信息 | 两者都可能需要持久 |

### 当前问题

页缓存中有新内容，但文件长度、目录项和数据块分配等元数据也需要更新；崩溃可能发生在任意写入顺序之间。

### 推导过程

V1 只知道数据在页缓存。V2 引入文件系统状态：write 修改文件页并标记脏页，内核按内存压力、时间和回写策略提交设备请求。文件系统还要更新 inode、块分配和目录项，并可能通过日志保护元数据一致性。

### 机制全解

write 返回通常表示内核接受了写入。脏页记录“内存版本比设备版本新”，后台线程会异步回写。回写顺序受文件系统、I/O 调度和设备影响，不应从源码调用顺序直接推断断电后的落盘顺序。

文件系统日志常用于保证元数据结构在崩溃后可恢复，但不同日志模式对文件数据的保护不同。日志“可恢复文件系统结构”不自动等于“业务文件内容一定是最新版本”。

### 状态变化

| 维度 | 页缓存刚接受数据 | 文件系统与回写阶段 |
|---|---|---|
| 输入 | 文件页和偏移 | 脏页、inode、目录项和块映射 |
| 状态 | 内存有新内容 | 数据和元数据分别等待回写 |
| 控制过程 | write 快速返回 | 文件系统排序、日志与后台写入 |
| 输出 | 应用可继续运行 | 设备逐步接收数据 |
| 仍未解决 | 不知道写入时机 | 应用怎样要求明确持久化 |

### 阶段结论

文件是一组数据与元数据状态，后台回写只提供最终进展，不提供业务提交时刻所需的同步保证。

## 阶段三：fsync 与持久化确认

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| fsync | 请求同步文件数据及相关元数据 | 建立明确完成点 |
| fdatasync | 更聚焦文件数据和必要元数据 | 在部分场景降低同步范围 |
| 错误传播 | 把设备或文件系统失败返回应用 | 让成功声明可验证 |

### 当前问题

后台回写“最终会发生”无法满足订单提交要求。应用必须在返回成功前等待特定文件状态完成持久化，并处理同步失败。

### 推导过程

V2 依赖内核何时回写。V3 在写完后调用 fsync 或适合的同步接口，等待内核把目标文件所需状态提交到设备，并检查返回值。业务成功点从“write 返回”后移到“同步完成且无错误”。

### 机制全解

fsync 请求同步文件内容以及恢复该文件所需的元数据。fdatasync 更关注数据和影响读取正确性的必要元数据，理论上可能减少无关元数据同步。具体保证仍受操作系统、文件系统、设备和硬件缓存语义影响。

同步调用必须检查错误；延迟突然升高也可能来自设备回写、文件系统日志提交或队列拥塞。每次请求都同步会牺牲吞吐，因此数据库常使用 WAL 和 Group Commit，把多个事务共享一次持久化成本。

### 状态变化

| 维度 | 依赖后台回写 | 调用同步接口后 |
|---|---|---|
| 输入 | 脏页与元数据 | 文件描述符和持久化请求 |
| 状态 | 完成时间不确定 | 有明确等待与错误结果 |
| 控制过程 | 内核自主批量回写 | 应用等待同步完成 |
| 输出 | 只能声明“已接受” | 可声明指定文件状态已同步 |
| 仍未解决 | 提交点不明确 | 新文件名和目录项是否持久 |

### 阶段结论

fsync 把持久化从后台期望变成应用可等待的协议，但文件内容同步不一定包含新目录项的持久化。

## 阶段四：原子重命名与目录同步

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| 临时文件写入 | 避免直接覆盖旧文件形成半写 | 提供完整候选版本 |
| 原子重命名 | 让路径从旧版本一次切换到新版本 | 保证观察者不见中间内容 |
| 目录同步 | 持久化目录项变化 | 缩小重启后路径丢失窗口 |

### 当前问题

直接覆盖`orders.json`时，崩溃可能留下截断文件。改成临时文件后，即使临时文件内容已 fsync，rename 创建的新目录映射也可能尚未持久。

### 推导过程

V3 同步目标文件，但覆盖过程仍可能暴露半成品。V4 使用：

```text
写 orders.tmp
  → fsync(orders.tmp)
  → rename(orders.tmp, orders.json)
  → fsync(父目录)
```

rename 在同一文件系统内通常提供路径切换原子性；目录同步用于要求目录项变化也进入持久化边界。

### 机制全解

原子重命名解决“观察者看到旧文件或新文件，而不是中间文件”的问题，不自动解决新内容是否已经稳定写入。正确顺序需要先同步临时文件，再重命名，最后根据目标平台语义同步父目录。

跨文件系统移动可能退化为复制和删除，不具备同样原子性。Windows、Linux、不同文件系统和网络文件系统的细节也可能不同，因此跨平台库必须明确其持久化合同。

### 状态变化

| 维度 | 直接覆盖 | 临时文件替换协议 |
|---|---|---|
| 输入 | 旧路径和新内容 | 临时路径、新内容和父目录 |
| 状态 | 旧文件可能被截断 | 旧版本与完整候选版本并存 |
| 控制过程 | 原地写入 | 写临时文件、同步、重命名、目录同步 |
| 输出 | 可能出现半文件 | 路径原子切换且持久化边界更清晰 |
| 仍未解决 | 内容损坏窗口 | 多文件事务和应用级恢复 |

### 阶段结论

可靠文件更新是一段协议，不是一次 API 调用。内容完整性、路径原子性和断电持久性由不同步骤分别保证。

## 正常链路与失败链路

```text
正常：
序列化 → flush 用户缓冲 → write 进入页缓存
  → fsync 临时文件 → rename → fsync 父目录 → 返回成功

失败：
只 flush / 只 close / 只 rename
  → 进程崩溃或断电
  → 数据仍在缓冲、文件截断或目录项消失
```

## 实验任务卡

### 实验任务一：观察 write、flush 与 fsync 的系统调用差异

实验目标：确认语言层 flush 和内核持久化同步不是同一动作。

覆盖知识点：用户缓冲、运行时缓冲和内核页缓存；write 系统调用、脏页和后台回写。

准备条件：Linux 环境、一个小型写文件程序和`strace`。

操作步骤：

```bash
strace -ff -e trace=write,fsync,fdatasync,close,rename \
  ./write-demo
```

分别运行：

```text
版本 A：写入后不 flush，立即异常退出。
版本 B：flush 后正常 close。
版本 C：flush 后调用 fsync。
```

预期现象：三个版本产生的系统调用序列不同；flush 可能触发 write，但只有版本 C 明确出现同步调用。

通过标准：能指出每个版本最后可证明的数据层级，并且不把 close 等同 fsync。

产出证据：strace 输出、程序代码和状态层级表。

### 实验任务二：验证临时文件替换协议

实验目标：比较直接覆盖与临时文件原子替换在故障窗口中的差异。

覆盖知识点：文件系统元数据、日志和原子重命名；fsync、fdatasync、目录同步与崩溃窗口。

准备条件：可反复运行的写入脚本、文件内容校验和，以及可使用进程强杀模拟的实验环境。

操作步骤：

```text
1. 版本 A 直接 truncate 后分段写目标文件。
2. 在不同写入位置强杀进程，记录文件长度与哈希。
3. 版本 B 写临时文件、fsync、rename、同步父目录。
4. 在相同步骤强杀，检查目标路径是旧版本还是完整新版本。
```

预期现象：直接覆盖可能留下截断或半内容；替换协议更接近“旧版本或完整新版本”。

通过标准：所有存活文件均能通过完整哈希校验，并明确进程强杀不能完全等价于机器断电。

产出证据：故障点、文件长度、哈希和恢复结果矩阵。

## 边界、代价与下一问题

本 CU 的实验以进程强杀为主，它不能完整模拟电源故障、设备缓存和文件系统损坏。不同操作系统、文件系统和硬件的保证需要单独核对。

同步持久化会提高尾延迟，因此真实系统还要使用日志、批量提交、检查点和异步复制平衡吞吐与数据丢失窗口。

## 自测题与答案

### 题目一

write 返回成功能证明什么，不能证明什么？

参考答案：通常能证明内核接受了指定字节，不能证明数据已经写到稳定介质，也不能证明目录项和所有相关元数据已经持久。

判分点：明确区分内核接受与设备持久化。

常见误区：认为“文件能立即读到”就代表断电后仍在，因为读取可能命中页缓存。

### 题目二

flush 和 fsync 的职责有什么不同？

参考答案：flush 通常把用户态或运行时缓冲交给内核；fsync 请求内核把文件所需状态同步到持久化设备并返回结果。

判分点：指出两者跨越的边界不同。

常见误区：把任意语言 API 中名为 flush 的操作都理解成设备刷盘。

### 题目三

为什么临时文件已经 fsync 后，还可能需要同步父目录？

参考答案：文件内容和目录项是不同状态；rename 改变了目录中的名称到 inode 映射，文件同步不一定持久化该目录项变化。

判分点：说出目录项是独立元数据状态。

常见误区：认为 rename 原子就等于 rename 已持久。

## 知识关系图

```text
[用户缓冲]
  └─ flush 提交 → [write 系统调用]
                      └─ 修改 → [内核页缓存与脏页]
                                   └─ 文件系统组织 → [数据块与元数据]
                                                        └─ fsync 请求同步 → [稳定介质]

[临时文件]
  └─ 内容同步 → [原子重命名]
                    └─ 修改目录项 → [父目录同步]
```

### 如何读图

沿第一条链判断数据当前在哪一层，沿第二条链判断文件路径切换是否完整。任何一步的“成功”只覆盖该步骤声明的状态，不能替代后续持久化边界。
