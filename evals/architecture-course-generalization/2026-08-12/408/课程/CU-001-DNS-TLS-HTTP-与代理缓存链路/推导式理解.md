## 选课依据与覆盖知识点

| 序号 | 知识点 | 总纲主归属 | 当前状态 | 本 CU 作用 |
|---|---|---|---|---|
| 1 | DNS 递归解析与缓存层级 | 计算机网络 | 未开始 | 把域名转换为可连接地址 |

## 核心推导链

```text
URL 只有域名
  ↓ DNS 解析
获得目标 IP
  ↓ TCP 建连 + TLS 握手
形成可信加密连接
  ↓ HTTP 请求响应
交换资源与缓存元数据
  ↓ 浏览器 / 代理 / CDN 判断新鲜度
直接命中、条件验证或回源
```

## 贯穿案例与初始状态

用户首次访问`https://shop.example.com/products/42`，随后刷新页面，并在 CDN 中保留旧版本资源。

| 维度 | 初始状态 |
|---|---|
| 用户目标 | 打开商品详情并看到最新价格 |
| 已有输入 | URL、浏览器网络栈、本地 DNS 与 HTTP 缓存 |
| 当前状态 | 只有域名和资源路径，不知道服务地址、身份和资源版本 |
| 可用能力 | DNS 解析器、TCP/IP、TLS、HTTP、CDN |
| 约束与资源边界 | DNS 和资源都可能缓存；弱网可能丢包；证书可能失效 |
| 预期输出 | 一个来源可信、内容版本正确的 HTTP 响应 |
| 复杂度代价 | 多次往返、证书校验、缓存一致性与观测成本 |
| 成功标准 | 能把延迟或错误定位到解析、连接、握手、HTTP 或缓存阶段 |

## 阶段一：DNS 递归解析与缓存层级

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| DNS 递归解析 | 沿解析链寻找权威记录 | 把 URL 交给网络地址 |
| 本地与递归缓存 | 用 TTL 复用历史答案 | 降低延迟，也可能保留旧地址 |
| CNAME 与负载入口 | 把业务域名指向 CDN 或网关 | 决定后续连接落点 |

### 当前问题

浏览器知道域名，却不能直接向域名发送 IP 数据包；同时本地、操作系统、递归解析器都可能持有不同时间生成的答案。

### 推导过程

V0 只能保存 URL。为了路由到目标主机，V1 引入 DNS：先查浏览器和操作系统缓存，未命中时交给递归解析器，递归解析器再根据根、顶级域和权威服务器的委派关系取得记录。TTL 让答案可缓存，但也定义了变更传播窗口。

### 机制全解

DNS 将层次化名称映射为记录。递归解析器替客户端完成后续查询，迭代查询则由查询者逐步取得下一跳线索。A/AAAA 记录给出地址，CNAME 给出别名，权威服务器拥有对应区域的最终定义。

缓存命中只能证明“在 TTL 和缓存策略内可复用”，不能证明目标服务健康。负缓存还会短期保存不存在结果。切换 IP 时，旧记录可能同时存在于浏览器、操作系统、递归解析器和 CDN 调度层，因此故障可能表现为部分用户异常。

### 状态变化

| 维度 | 进入阶段前 | 引入 DNS 后 |
|---|---|---|
| 输入 | 域名和路径 | 域名、记录类型、缓存状态 |
| 状态 | 不知道目标地址 | 得到 IP、TTL、别名链和解析来源 |
| 控制过程 | 无法路由 | 缓存查找或递归解析 |
| 输出 | 不能建立连接 | 可选择目标 IP |
| 仍未解决 | 地址未知 | 目标是否可达、是否可信 |

### 阶段结论

DNS 只完成“名称到地址”的发现，并引入可观测的 TTL 和缓存来源；它不提供可靠传输和服务身份。

## 阶段二：TCP 连接与 TLS 握手

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| TCP 三次握手 | 同步连接状态与初始序列空间 | 建立可靠字节流 |
| 重传、窗口与拥塞控制 | 处理丢包、接收能力和网络负载 | 影响请求时延和吞吐 |
| TLS 握手 | 验证证书并协商会话密钥 | 为 HTTP 提供可信加密通道 |

### 当前问题

IP 只标识网络落点。浏览器还不知道对端是否可达、双方字节序列从哪里开始，也不能确认连接的服务器就是域名对应的合法服务。

### 推导过程

V1 有了地址但只能发送不可靠 IP 包。V2 先用 TCP 握手建立双方连接状态，再通过序列号、确认和重传提供有序字节流。随后 TLS 使用域名、证书链和密钥交换验证身份并建立会话密钥。

### 机制全解

TCP 握手让双方确认收发能力并建立连接状态。可靠性来自序列号、确认、超时重传和乱序重组；接收窗口限制发送方不要压垮对端，拥塞控制限制发送方不要压垮网络。

TLS 位于 HTTP 语义与传输之间。客户端验证证书的域名、有效期和信任链，双方协商算法并通过密钥交换得到会话密钥。加密能保护传输内容和完整性，但不能证明应用返回的数据符合业务预期。

### 状态变化

| 维度 | DNS 完成后 | 连接与握手后 |
|---|---|---|
| 输入 | IP、端口、域名 | TCP 状态、证书、握手参数 |
| 状态 | 目标地址可选 | 双方有序列空间、密钥和认证结果 |
| 控制过程 | 直接尝试发包 | 握手、证书验证、重传和窗口控制 |
| 输出 | 不可靠地址目标 | 可信加密字节流 |
| 仍未解决 | 无连接语义 | 请求什么资源、资源是否最新 |

### 阶段结论

TCP 与 TLS 解决传输可靠性、身份和机密性，但仍然只提供字节通道，尚未定义商品请求和缓存语义。

## 阶段三：HTTP 请求响应与连接复用

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| HTTP 方法、状态码和头部 | 表达资源操作和结果语义 | 把字节流变成应用消息 |
| Keep-Alive 与连接复用 | 降低重复握手成本 | 改善多资源加载 |
| HTTP/2 多路复用 | 在一条连接上并发多个流 | 减少应用层排队 |

### 当前问题

安全字节流不知道`/products/42`是什么，也不知道响应是成功、重定向、未修改还是服务端错误。

### 推导过程

V2 已有可信连接。V3 引入 HTTP 消息：请求行和头部描述目标、方法、内容协商和缓存条件；响应状态、头部和正文描述结果。连接复用避免每个资源都重新建连，HTTP/2 再把一条连接拆成多个逻辑流。

### 机制全解

HTTP 是无状态的应用层语义协议。GET 应保持安全和幂等，POST 通常用于提交处理；状态码只描述本次 HTTP 结果，不等价于业务成功。Host 或`:authority`区分同一地址上的虚拟主机。

连接复用降低握手与慢启动开销。HTTP/2 解决 HTTP/1.1 同连接上的应用层队头阻塞，但底层 TCP 丢包仍可能影响同连接中的多个流。HTTP/3 使用 QUIC 把流独立性下沉到传输层，但部署和观测成本更高。

### 状态变化

| 维度 | 进入阶段前 | 引入 HTTP 后 |
|---|---|---|
| 输入 | 加密字节流 | 方法、路径、头部、正文 |
| 状态 | 只有连接状态 | 形成请求、响应和流状态 |
| 控制过程 | 发送任意字节 | 按 HTTP 语义解析与复用 |
| 输出 | 无业务含义的字节 | 可解释的资源响应 |
| 仍未解决 | 不知道资源语义 | 是否必须回源、旧内容怎样验证 |

### 阶段结论

HTTP 定义了资源交换和连接复用，但若每次刷新都回源，延迟和源站负载仍然过高。

## 阶段四：HTTP 缓存验证与代理回源

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| Cache-Control | 定义新鲜度、可缓存范围和复用条件 | 控制直接命中 |
| ETag 与条件请求 | 验证缓存副本是否仍与源站一致 | 避免重复传输正文 |
| 代理缓存与 CDN | 在共享节点复用响应 | 降低跨地域延迟和回源量 |

### 当前问题

商品页刷新时，旧响应可能仍然可用，也可能已经过期；CDN 还可能把旧价格返回给部分用户。

### 推导过程

V3 每次都完整请求。V4 引入缓存状态：响应携带新鲜度和验证器；新鲜时直接复用，过期后发送 If-None-Match 等条件请求，未变化时只返回 304。共享缓存还要遵守 private、public、Vary 和授权相关边界。

### 机制全解

Cache-Control 的 max-age 控制新鲜时长，no-cache 表示复用前必须验证，不等于禁止保存；no-store 才表示不应存储。ETag 是资源版本验证器，客户端用条件请求询问当前版本是否变化。

CDN 是共享代理缓存，缓存键通常至少包含主机和路径，也可能受查询参数、Vary 头和自定义规则影响。缓存提升延迟和可用性，却引入失效传播、错误缓存键、缓存投毒和陈旧窗口。价格等强时效数据需要更谨慎的缓存边界。

### 状态变化

| 维度 | 只使用 HTTP | 加入缓存链后 |
|---|---|---|
| 输入 | 每次完整请求 | 请求、缓存键、新鲜度、验证器 |
| 状态 | 只有源站响应 | 浏览器、代理、CDN 各自持有副本 |
| 控制过程 | 总是回源 | 命中、验证或回源 |
| 输出 | 最新但代价高 | 在策略允许范围内复用 |
| 仍未解决 | 源站负载高 | 业务数据与缓存策略如何共同设计 |

### 阶段结论

完整请求链的关键不是背协议顺序，而是知道每一层新增了什么状态、证据和失败窗口。

### 下一问题

后续可以把缓存语义与浏览器离线存储、服务端数据一致性连接起来。

## 正常链路与失败链路

```text
正常：
URL → DNS 命中或递归 → TCP/TLS 成功 → HTTP 200
   → 缓存记录 ETag → 再次请求条件验证 → 304 复用正文

失败：
URL → 旧 DNS 地址 / 证书域名错误 / TCP 重传
   / HTTP 5xx / CDN 错误缓存键
   → 根据阶段证据定位，而不是统一归因“接口慢”
```

## 实验任务卡

### 实验任务一：分解一次 HTTPS 请求时序

实验目标：把一次 URL 请求拆成 DNS、连接、TLS、HTTP 和缓存阶段。

覆盖知识点：DNS 递归解析与缓存层级、TCP 连接与 TLS 握手、HTTP 请求响应与连接复用。

准备条件：安装`curl`、`dig`和`openssl`，选择一个可访问 HTTPS 域名。

操作步骤：

```bash
dig example.com
openssl s_client -connect example.com:443 -servername example.com </dev/null
curl -o /dev/null -sS -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} first_byte=%{time_starttransfer} total=%{time_total}\n' https://example.com/
```

预期现象：能分别得到解析记录、证书信息和阶段耗时，且 TLS 完成时间不早于 TCP 连接时间。

通过标准：能把异常耗时映射到明确阶段，并说明命令没有证明页面业务正确。

产出证据：命令输出、阶段耗时表和证书摘要。

### 实验任务二：观察强缓存与条件验证

实验目标：区分直接使用缓存、条件请求和完整回源。

覆盖知识点：Cache-Control、ETag、代理缓存与 CDN。

准备条件：一个返回`Cache-Control`和`ETag`的本地 HTTP 服务或公开测试资源。

操作步骤：

```text
1. 首次请求并保存响应头与正文。
2. 在新鲜期内再次请求，观察是否直接复用。
3. 过期后携带 If-None-Match 请求。
4. 修改资源版本后重复条件请求。
```

预期现象：未变化时可得到 304 或缓存命中，版本变化后得到新正文和新验证器。

通过标准：能解释 no-cache 与 no-store 的区别，并指出哪个参与者返回了响应。

产出证据：四次请求的状态码、Age、ETag、Cache-Control 和正文哈希。

## 边界、代价与下一问题

本 CU 没有展开 TCP 拥塞算法细节、证书签发体系和浏览器渲染流水线。网络层的可靠传输不保证应用正确，TLS 不保证业务可信，缓存也不保证内容永远最新。

下一问题可以根据进度选择 TCP 拥塞控制，或进入存储体系中的浏览器持久化与缓存一致性。

## 自测题与答案

### 题目一

浏览器访问 HTTPS URL 时，DNS、TCP、TLS 和 HTTP 分别解决什么问题？

参考答案：DNS 找地址，TCP 提供可靠有序字节流，TLS 验证身份并建立加密通道，HTTP 定义资源请求响应语义。

判分点：四层职责不能混淆；指出后层依赖前层提供的能力。

常见误区：说 TLS 负责可靠重传，或说 DNS 能证明服务健康。

### 题目二

为什么`no-cache`不等于“不缓存”？

参考答案：no-cache 允许保存响应，但复用前必须向源站或验证端确认；no-store 才要求不存储。

判分点：说出保存和复用是两个不同动作，并提到验证器。

常见误区：把浏览器“禁用缓存”开发选项当成协议定义。

### 题目三

页面偶发旧数据时应先收集哪些证据？

参考答案：DNS 解析结果与 TTL、响应来自哪个 IP 或 CDN 节点、Age、Cache-Control、ETag、Vary、请求缓存键及源站版本。

判分点：至少覆盖解析、响应来源、缓存元数据和源站版本。

常见误区：只清浏览器缓存，不判断旧数据在哪一层产生。

## 知识关系图

```text
[DNS 解析]
  └─ 提供目标地址 → [TCP 可靠连接]
                         └─ 承载握手 → [TLS 身份与密钥]
                                           └─ 保护消息 → [HTTP 请求响应]
                                                              └─ 提供缓存元数据 → [浏览器 / 代理 / CDN]
```

### 如何读图

从 URL 的信息缺口开始向右读。每一层只解决前一层留下的一个问题，同时新增自己的状态和失败证据；排障时沿相反方向根据时间点、状态码和缓存头缩小范围。
