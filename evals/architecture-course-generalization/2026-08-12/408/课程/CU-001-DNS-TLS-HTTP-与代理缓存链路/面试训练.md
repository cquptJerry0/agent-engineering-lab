# CU-001：DNS、TLS、HTTP 与代理缓存链路 - 面试训练

> 对应推导式理解：[推导式理解](推导式理解.md)

## 1. 从浏览器输入 URL 到收到 HTTPS 响应，核心链路是什么？

题型：网络原理与全栈排障题

一句话核心判断：这是一条由名称解析、可靠传输、身份加密和应用语义依次接管的状态链，每层都有独立失败证据。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 没有 DNS 不知道地址，没有 TCP/TLS 没有可信通道，没有 HTTP 不知道资源语义 |
| 最小机制是什么 | 域名解析、连接握手、证书验证、请求响应 |
| 工程收益 | 能把首屏慢和访问失败定位到具体阶段 |
| 边界和代价 | 多层握手增加往返，缓存和连接复用用于摊薄成本 |

30 秒回答：

> 浏览器先根据 URL 查询 DNS 得到目标地址，再建立 TCP 连接；HTTPS 随后进行 TLS 握手，校验证书并协商会话密钥。通道建立后浏览器发送 HTTP 请求，服务端或代理返回状态码、响应头和正文。若存在浏览器缓存、代理或 CDN，还要先判断缓存是否新鲜、是否需要条件验证或回源。排障时我会分别看 DNS、连接、TLS、首字节和缓存证据。

完整回答：

URL 首先提供协议、主机和路径。浏览器依次查询浏览器缓存、操作系统缓存和递归解析器，获得 A/AAAA 或别名链。拿到地址后，TCP 通过握手建立连接状态，并用序列号、确认和重传提供有序字节流。

TLS 使用 SNI(服务名称指示)和证书链验证目标域名，再协商密码套件和会话密钥。完成后 HTTP 才能发送方法、路径、头部和正文。

响应可能来自源站，也可能由浏览器、代理或 CDN(内容分发网络)返回。缓存判断会读取 Cache-Control(缓存控制)、ETag(实体标签)、Vary(响应选择维度)和缓存键。

```text
URL
  → DNS 地址
  → TCP 连接
  → TLS 身份与密钥
  → HTTP 请求响应
  → 缓存命中 / 条件验证 / 回源
```

ASCII 图或关键表：

| 证据 | 更可能定位的阶段 |
|---|---|
| `time_namelookup`异常 | DNS |
| 连接超时或大量重传 | TCP 或网络路径 |
| 证书域名/有效期错误 | TLS |
| 4xx/5xx 与首字节慢 | HTTP 或服务端 |
| Age、ETag、X-Cache 异常 | 浏览器、代理或 CDN |

追问：

- 原理追问：TCP 三次握手为什么不能改成两次？
- 工程追问：怎样用`curl -w`和抓包区分连接慢与服务端慢？
- 项目追问：你会为前端请求链记录哪些 Timing 和 Trace 字段？

证据：

`dig`解析链、TLS 证书摘要、`curl`阶段耗时和浏览器 Network Timing。

对应推导章节：

阶段一：DNS 递归解析与缓存层级；阶段二：TCP 连接与 TLS 握手；阶段三：HTTP 请求响应与连接复用。

## 2. HTTP 强缓存和协商缓存有什么区别，ETag 在哪里起作用？

题型：HTTP 缓存原理题

一句话核心判断：强缓存决定新鲜期内是否可以不发请求，协商缓存决定过期后能否只验证版本而不重复传正文。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 所有请求都回源，延迟和带宽成本上升 |
| 最小机制是什么 | 新鲜度、缓存键、验证器和条件请求 |
| 工程收益 | 降低首屏延迟、CDN 回源和重复传输 |
| 边界和代价 | 策略错误会返回旧内容或缓存用户私有数据 |

30 秒回答：

> 强缓存依赖 Cache-Control 等新鲜度信息，在响应仍新鲜时可以直接复用而不回源。缓存过期后，客户端可以携带 ETag 对应的 If-None-Match 做条件请求；资源未变化时服务端返回 304，继续使用本地正文。no-cache 表示复用前必须验证，no-store 才是不要保存。

完整回答：

缓存包含两个决定：能否保存，以及何时可以复用。max-age 为响应定义新鲜期，在这段时间内浏览器或共享缓存可以直接使用副本。超过新鲜期并不意味着必须下载完整正文，只要响应带有 ETag，客户端就能用 If-None-Match 询问资源版本。

若版本未变，返回 304，不传正文；若版本已变，返回新正文和新 ETag。代理缓存还要考虑 public、private、Authorization、Vary 和缓存键，否则可能把一个用户的响应交给另一个用户。

ASCII 图或关键表：

```text
缓存副本
  ├─ 仍新鲜 → 直接复用
  └─ 已过期 → If-None-Match
                 ├─ 304 → 复用旧正文
                 └─ 200 → 保存新正文与 ETag
```

追问：

- 原理追问：ETag 和 Last-Modified 的验证精度有什么差异？
- 工程追问：CDN 缓存键漏掉语言或用户维度会发生什么？
- 项目追问：前端静态资源和商品价格接口会采用相同缓存策略吗？

证据：

浏览器 Network 面板中的 memory/disk cache 标记，响应头中的 Age、Cache-Control、ETag、Vary 和条件请求状态码。

## 3. HTTP/2 已经支持多路复用，为什么还需要 HTTP/3？

题型：协议演进题

一句话核心判断：HTTP/2 消除了 HTTP 层的串行等待，但多个流仍共享同一条 TCP 丢包恢复状态，HTTP/3 用 QUIC 提供独立流和更灵活的连接建立。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | TCP 丢包时，同连接上的多个 HTTP/2 流可能一起等待 |
| 最小机制是什么 | 基于 UDP 的 QUIC 连接、独立流和用户态拥塞控制 |
| 工程收益 | 弱网切换、连接迁移和多流丢包隔离更好 |
| 边界和代价 | UDP 可达性、CPU、观测和部署复杂度增加 |

30 秒回答：

> HTTP/2 在一条 TCP 连接上把请求拆成多个逻辑流，解决了 HTTP/1.1 的应用层队头阻塞；但 TCP 必须按字节序交付，某个包丢失时后续字节即使属于其他流也要等待。HTTP/3 基于 QUIC，把可靠性放到独立流上，并支持更快握手和连接迁移，但部署与排障成本更高。

完整回答：

HTTP/2 的多路复用让多个请求无需排队等待上一个响应完成，头部压缩也降低了重复元数据。但底层仍是一条 TCP 有序字节流，传输层看不到 HTTP 流边界。丢失一个 TCP 段会阻塞后续字节交付。

QUIC 在 UDP 上实现连接、加密和独立可靠流。一个流丢包不会要求其他流等待同一字节序列，同时连接 ID 使网络地址变化时可以迁移连接。代价是协议栈更多位于用户态，服务端 CPU、监控工具和中间网络兼容性都需要重新评估。

ASCII 图或关键表：

```text
HTTP/2：多个 HTTP 流 → 一条 TCP 有序字节流 → 丢包共同等待
HTTP/3：多个 QUIC 流 → 各自可靠状态      → 丢包按流恢复
```

追问：

- 原理追问：QUIC 为什么仍然需要拥塞控制？
- 工程追问：如何验证用户网络是否真的协商到 HTTP/3？
- 项目追问：什么业务场景不值得为了 HTTP/3 增加复杂度？

证据：

浏览器协议列、服务端访问日志、QUIC 握手与丢包指标，以及 HTTP/2/HTTP/3 弱网对照实验。

对应推导章节：

阶段三：HTTP 请求响应与连接复用。
