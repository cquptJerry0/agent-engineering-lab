# CU-005：并发同步、死锁与内存可见性 - 面试训练

> 对应推导式理解：[推导式理解](推导式理解.md)

## 1. 原子性、可见性和有序性分别解决什么问题？

题型：并发基础原理题

一句话核心判断：原子性限制操作被拆分，可见性规定写何时可观察，有序性规定跨线程允许观察到的执行顺序。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 读改写丢失、线程看到旧值或错误顺序 |
| 最小机制是什么 | 原子指令、同步边界和内存模型 |
| 工程收益 | 能正确实现计数器、状态发布和无锁协调 |
| 边界和代价 | 更强同步会限制优化并增加竞争或重试 |

30 秒回答：

> 原子性保证一个操作不会以中间状态被其他线程观察，例如 CAS 把比较和写入合成一个转换；可见性保证线程 A 的写通过锁、原子变量等同步关系对线程 B 可见；有序性约束编译器和 CPU 重排后其他线程可以观察到的顺序。三者相关但不能互相替代。

完整回答：

普通`count++`包含读、加和写，两个线程可以交错，因此缺少原子性。线程把配置写入普通变量后设置就绪标志，如果没有正确同步，另一个线程可能看到标志却没看到完整配置，这是可见性和顺序问题。

语言内存模型用 happens-before 定义保证。例如同一锁的释放先行发生于后续获取，正确使用原子变量也会提供指定内存序。同步只对规定范围生效，不应把一次正确运行当作规范保证。

ASCII 图或关键表：

| 性质 | 典型失败 | 常见机制 |
|---|---|---|
| 原子性 | 丢失更新 | CAS、原子 RMW、锁 |
| 可见性 | 长期读取旧值 | 锁、volatile/原子语义 |
| 有序性 | 观察到部分初始化 | happens-before、内存屏障 |

追问：

- 原理追问：volatile 为什么不能让`count++`原子？
- 工程追问：CAS 自旋在高竞争下有什么问题？
- 项目追问：如何安全发布一个只读配置对象？

证据：

普通计数器与原子计数器多轮对照、线程交错表和语言内存模型规范。

阶段一：原子性与内存可见性。

## 2. 互斥锁、信号量和条件变量应该怎样选择？

题型：同步原语设计题

一句话核心判断：互斥锁保护共享不变量，信号量表达可用资源数量，条件变量协调“状态尚未满足”的等待。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 竞态、资源超配或忙等 |
| 最小机制是什么 | 临界区所有权、计数和等待通知 |
| 工程收益 | 让正确性和资源控制语义清晰 |
| 边界和代价 | 阻塞、上下文切换、虚假唤醒和死锁 |

30 秒回答：

> 多步修改共享状态时用互斥锁保护完整不变量；连接池或并发槽位这类 N 个资源用信号量计数；线程需要等待“队列非空”或“库存补充”时，在锁保护下用条件变量等待，并在唤醒后用 while 重新检查条件。它们解决的问题不同，不能只按 API 外形替换。

完整回答：

互斥锁强调同一时刻一个所有者进入临界区。信号量的计数允许多个执行者同时取得资源，并在释放时归还额度。条件变量与锁组合：检查条件不满足时原子释放锁并休眠，收到通知后重新竞争锁和检查状态。

临界区应覆盖前置条件检查、状态修改和后置条件建立。只锁写操作、不锁条件读取仍可能出错；把 I/O 和长计算放在锁内则会放大尾延迟。

ASCII 图或关键表：

```text
锁：      保护“不变量”
信号量：  保护“最多 N 个”
条件变量：等待“状态变为真”
```

追问：

- 原理追问：条件变量为什么必须与互斥锁配合？
- 工程追问：怎样缩小临界区又不破坏不变量？
- 项目追问：数据库连接池会同时使用哪些同步原语？

证据：

库存临界区状态图、连接池计数指标和条件等待线程转储。

对应推导章节：

阶段二：互斥锁、信号量与条件变量。

## 3. 死锁的四个必要条件是什么，工程上怎样处理？

题型：并发故障排查题

一句话核心判断：死锁要求互斥、占有并等待、不可抢占和循环等待同时成立，工程策略要么预先破坏条件，要么检测后回滚。

启发式思考：

| 思考 | 回答 |
|---|---|
| 没有它会怎样 | 线程永久阻塞，吞吐归零且资源不释放 |
| 最小机制是什么 | 等待图、资源顺序和恢复策略 |
| 工程收益 | 把无限等待转成可预防或可恢复失败 |
| 边界和代价 | 超时可能误判，回滚要求幂等和事务边界 |

30 秒回答：

> 死锁的四个必要条件是资源互斥、线程占有资源时继续等待、资源不能被强制抢占，以及等待关系形成环。最常见的预防方式是给资源建立全局顺序，所有线程按同一顺序加锁，从而破坏循环等待。也可以用 tryLock 加超时，或维护等待图检测循环后选择一个事务回滚。

完整回答：

排查时先取线程转储，列出每个线程持有哪些锁、等待哪些锁，再画资源等待图。出现循环只说明当前存在死锁；没有循环但长期无进展还要考虑饥饿、活锁和外部 I/O。

固定锁顺序适合资源集合可枚举的场景。超时提供上界但不能区分死锁与慢操作。数据库常采用检测与回滚，因为事务本身具有撤销边界；普通业务线程若没有补偿机制，粗暴中断可能留下部分状态。

ASCII 图或关键表：

```text
线程 A：持有库存锁 → 等待订单锁
线程 B：持有订单锁 → 等待库存锁
                    ↑__________↓
```

追问：

- 原理追问：破坏不可抢占条件为什么通常更难？
- 工程追问：锁超时设置太短或太长分别有什么风险？
- 项目追问：线上线程池卡死时你会先看哪些指标和转储？

证据：

线程转储、锁等待图、请求超时分布，以及统一加锁顺序后的回归结果。

对应推导章节：

阶段三：死锁条件与等待图。
