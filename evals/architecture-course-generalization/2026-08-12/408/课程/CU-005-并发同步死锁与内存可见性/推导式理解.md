## 核心推导链

```text
两个线程共享库存
  ↓ 读-改-写可以交错
竞态导致丢失更新
  ↓ 原子操作或互斥锁
单个临界区正确
  ↓ 线程还要等待库存或任务条件
信号量与条件变量协调状态
  ↓ 多把锁顺序不一致
形成等待环与死锁
  ↓ 固定顺序、超时、检测或回滚
```

## 贯穿案例与初始状态

库存服务维护`stock=1`，两个工作线程同时处理两个订单；随后扩展为“库存锁 + 订单锁”的跨对象更新。

| 维度 | 初始状态 |
|---|---|
| 用户目标 | 只允许一个订单扣减成功，并保证失败可解释 |
| 已有输入 | 两个并发订单、共享库存和订单状态 |
| 当前状态 | 每个线程独立执行读、判断、减一和写回 |
| 可用能力 | 多线程、共享内存、原子指令和锁 |
| 约束与资源边界 | 调度顺序不可预测，CPU 和编译器可能重排普通内存访问 |
| 预期输出 | 不超卖、不永久阻塞、失败路径可恢复 |
| 复杂度代价 | 锁竞争、上下文切换、优先级反转和排障成本 |
| 成功标准 | 能列出交错顺序、同步边界和等待图 |

## 阶段一：原子性与内存可见性

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| 原子操作 | 让一个读改写不可被其他线程观察为中间状态 | 解决单变量竞争 |
| 内存可见性 | 规定一个线程的写何时可被另一个线程观察 | 解决缓存与重排 |
| happens-before | 建立跨线程操作的顺序保证 | 连接语言模型与同步原语 |

### 当前问题

`stock--`看起来是一行代码，但通常包含读取、计算和写回。两个线程都可能先读到 1，再分别写回 0，导致两个订单都认为扣减成功。

### 推导过程

V0 假设源码行不可分割。列出真实交错后发现：

```text
线程 A 读 stock=1
线程 B 读 stock=1
线程 A 写 stock=0
线程 B 写 stock=0
```

V1 对单变量使用 CAS 或原子减法，使读改写成为一个原子状态转换；同时通过同步语义建立可见性顺序。

### 机制全解

原子性回答“一个操作能否被拆开观察”，可见性回答“一个线程何时看见另一个线程的写”，有序性回答“操作能否按不同顺序执行或被观察”。三者不是同一概念。

CAS 比较内存中的旧值，只有仍等于期望值时才写入新值；失败者重新读取并重试。原子变量适合简单状态转换，但多变量业务不变量通常仍需要锁、事务或更高层状态机。

happens-before 是语言内存模型提供的可见性关系。例如同一锁的释放先行发生于后续获取，线程启动与加入也建立特定顺序。没有同步关系时，即使物理上某次运行“看起来正确”，程序也不能依赖这种观察。

### 状态变化

| 维度 | 普通读改写 | 原子状态转换 |
|---|---|---|
| 输入 | 共享普通变量 | 原子变量和期望旧值 |
| 状态 | 中间步骤可交错 | 成功或失败作为一个转换 |
| 控制过程 | 最后写入者覆盖 | CAS 失败者重试 |
| 输出 | 可能丢失更新 | 单变量不变量可保持 |
| 仍未解决 | 超卖 | 多变量临界区和条件等待 |

### 阶段结论

一行源码不等于原子操作；原子性、可见性和有序性需要由内存模型和同步原语明确保证。

### 下一问题

同时更新库存和订单状态时，怎样保护多步业务不变量，并让线程等待条件变化？

## 阶段二：互斥锁、信号量与条件变量

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| 互斥锁 | 一次只允许一个线程进入临界区 | 保护多步共享不变量 |
| 信号量 | 表示可用资源计数 | 限制并发数量 |
| 条件变量 | 让线程等待状态条件并在变化后重查 | 避免忙等 |

### 当前问题

扣减库存后还要更新订单状态，两个变量必须保持“成功订单数与库存减少量一致”。单个原子变量无法表达这组不变量；库存为 0 时线程也不应持续轮询。

### 推导过程

V1 只保证单变量更新。V2 把读取库存、判断、更新库存和订单状态放入同一互斥临界区。若线程必须等待库存增加，则在持锁检查条件后进入条件变量等待；等待会原子地释放锁，唤醒后重新获取锁并循环检查条件。

### 机制全解

互斥锁保护的是不变量，不是某一行代码。临界区应覆盖读取前提、修改状态和建立后置条件的完整范围。范围过小会失去正确性，范围过大会降低并发。

信号量维护计数，适合连接池、并发请求槽位等有限资源；互斥锁通常可视为特殊的二值访问控制，但语义和所有权约束更明确。

条件变量本身不保存业务条件，只提供等待和通知机制。线程必须在锁保护下使用`while`重新检查条件，因为可能发生虚假唤醒，也可能有其他线程先消费了状态。

### 状态变化

| 维度 | 单变量原子操作 | 同步原语组合 |
|---|---|---|
| 输入 | 一个共享值 | 多变量不变量、资源计数和条件 |
| 状态 | 成功或 CAS 重试 | 锁所有者、等待队列、资源计数 |
| 控制过程 | 乐观重试 | 互斥进入、阻塞、通知与重查 |
| 输出 | 单变量正确 | 多步状态一致且无忙等 |
| 仍未解决 | 无法协调复杂条件 | 多锁可能形成循环等待 |

### 阶段结论

同步原语的选择取决于要保护的状态：互斥锁保护临界区，信号量表达资源数量，条件变量协调状态条件。

## 阶段三：死锁条件与等待图

### 本阶段知识点群

| 知识点 | 作用 | 前后关系 |
|---|---|---|
| Coffman 四条件 | 判断死锁是否可能 | 从现象抽象必要条件 |
| 资源等待图 | 表示线程持有和等待关系 | 定位循环 |
| 顺序、超时与检测 | 破坏条件或发现后恢复 | 形成工程策略 |

### 当前问题

线程 A 先持有库存锁再等待订单锁，线程 B 先持有订单锁再等待库存锁。两个临界区各自正确，整体却停止前进。

### 推导过程

V2 引入多把锁但没有全局协议。V3 画出等待图：

```text
线程 A ─等待→ 订单锁 ─持有→ 线程 B
线程 B ─等待→ 库存锁 ─持有→ 线程 A
```

系统同时满足互斥、占有并等待、不可抢占和循环等待。固定加锁顺序可以直接破坏循环等待；tryLock + 超时允许失败后释放并重试；数据库也可检测等待图并回滚牺牲事务。

### 机制全解

死锁是多个执行者互相等待对方持有资源，并且没有外部机制打破等待。四个必要条件同时成立时才可能发生。避免策略可以限制资源申请方式，预防策略直接破坏某个条件，检测与恢复则允许发生后选择受害者。

固定顺序简单可靠，但要求所有调用路径共享同一资源排序。超时不能证明发生死锁，也可能误伤慢操作。检测需要维护等待关系，恢复还要求业务操作可回滚或幂等。

锁之外还要区分活锁和饥饿：活锁中的线程不断动作但没有进展，饥饿则是某线程长期得不到资源。

### 状态变化

| 维度 | 无全局锁协议 | 引入死锁策略 |
|---|---|---|
| 输入 | 任意获取多资源 | 资源排序、超时或等待图 |
| 状态 | 隐含持有与等待 | 可观察的边和循环 |
| 控制过程 | 无限阻塞 | 预防、检测、选择受害者并恢复 |
| 输出 | 可能永久无进展 | 失败可界定、可重试或回滚 |
| 仍未解决 | 服务卡死 | 公平性、优先级反转和分布式锁 |

### 阶段结论

锁保证局部互斥，却不自动保证系统整体能继续前进。多资源同步必须同时设计顺序、等待上界和恢复语义。

## 正常链路与失败链路

```text
正常：
读取共享状态 → 在同步边界内验证前提 → 原子提交变化
  → 释放资源 → 通知等待者 → 系统继续前进

失败：
无同步造成丢失更新
  / 条件变量用 if 导致错误通过
  / 多锁顺序相反形成等待环
```

## 实验任务卡

### 实验任务一：复现丢失更新与可见性问题

实验目标：观察普通共享变量与原子变量的结果差异。

覆盖知识点：原子操作与内存可见性。

准备条件：Java、C++或其他具有真实多线程与原子类型的运行环境。

操作步骤：

```text
1. 两个线程分别对共享计数器递增一百万次。
2. 使用普通变量运行多轮并记录结果。
3. 替换为原子递增并重复。
4. 输出线程开始、结束和最终计数。
```

预期现象：普通变量可能小于期望值，原子递增得到稳定结果。

通过标准：能解释错误来自读改写交错，而不是“线程随机漏执行”。

产出证据：多轮结果、核心代码和线程时间线。

### 实验任务二：制造并诊断死锁

实验目标：用等待图解释多锁死锁，并验证固定顺序能够消除循环。

覆盖知识点：互斥锁、信号量与条件变量、死锁条件与避免策略。

准备条件：两个锁、两个线程和线程转储工具。

操作步骤：

```text
1. 线程 A 获取锁 1 后等待锁 2。
2. 线程 B 获取锁 2 后等待锁 1。
3. 保存线程转储并画等待图。
4. 把两个线程统一改为先锁 1 再锁 2。
5. 重复运行并观察是否完成。
```

预期现象：第一版线程永久等待，转储显示互相持有；统一顺序后任务完成。

通过标准：等待图与线程转储一致，并能指出被破坏的是循环等待条件。

产出证据：线程转储、等待图和修复前后完成时间。

## 自测题与答案

### 题目一

原子性和可见性有什么区别？

参考答案：原子性保证操作不可被观察为中间步骤，可见性保证一个线程的写在同步关系下能被另一个线程观察；一个原子动作不自动让任意其他普通变量具有正确可见性。

判分点：分别定义两者，并指出不能互相替代。

常见误区：认为加 volatile 就能让多步复合操作原子。

### 题目二

条件变量等待为什么要使用 while 重新检查条件？

参考答案：条件变量可能虚假唤醒，通知也只表示状态可能变化；线程重新获得锁前，其他线程可能已经消费条件，因此必须在锁内再次判断。

判分点：说出虚假唤醒和状态被其他线程改变至少一个原因。

常见误区：把通知当作资源所有权转移。

### 题目三

固定加锁顺序防止死锁的依据是什么？

参考答案：所有线程都按同一全序申请资源后，不可能形成资源获取方向上的循环，因此破坏了死锁的循环等待条件。

判分点：说出全序和循环等待。

常见误区：认为超时也是严格防止死锁，它只是建立等待上界和恢复机会。

## 知识关系图

```text
[共享可变状态]
  ├─ 单步竞争 → [原子操作]
  ├─ 多步不变量 → [互斥锁]
  ├─ 有限资源 → [信号量]
  └─ 等待状态变化 → [条件变量]
                         ↓ 多资源获取
                    [等待图与死锁]
                         └─ 固定顺序 / 检测恢复 → [继续前进]
```

### 如何读图

先识别共享状态需要哪种同步语义，再观察同步后是否引入等待。正确性和活性是两条不同轴：锁可以修复竞态，却可能制造死锁。
