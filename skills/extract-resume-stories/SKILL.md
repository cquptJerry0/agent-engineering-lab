# 业务驱动简历架构包装

## 总原则

不要从“已经写了哪些代码”开始写简历。先理解业务，再根据业务和技术逻辑重新设计一个更完整、更高级、更值得面试的系统；现有代码只负责提供领域词汇、真实约束和可借用的技术支点，不能限制项目的能力上限。

默认使用 **100 分包装模式**：

```text
业务问题与技术约束
        -> 理想系统架构
        -> 高级技术机制与优化方向
        -> 简历钩子
        -> 面试设计与答辩包
```

只有用户明确说“只写已落地事实”“做事实审计”或“不能发挥想象”时，才切换为严格事实模式。默认不要把“规划中”“代码里没有”写进简历句子；这些只作为内部答辩准备。架构机制、模块边界和优化方案允许按理想完成态包装；客观数字、线上规模和事故案例可以先生成假设版本，但必须在内部标记“待用户确认”，不能把未经确认的数字直接当成真实线上指标。

## 强制两阶段协议

收到“写简历”“包装项目”“根据代码整理经历”等请求时，默认先执行第一阶段，不直接交付简历正文：

### 第一阶段：100 分系统诊断

显式完成并展示以下中间产物：

1. 业务与技术真源摘要：用户、场景、核心对象、成功指标、边界和时间线。
2. 同类系统调研：至少选择两个成熟产品、开源系统、公司内部参考或相邻领域方案，提取它们如何处理扩展性、可靠性、治理、观测和演进；调研对象是方法和系统模型，不是文案模板。
3. 当前上限与 100 分能力地图：说明业务增长或风险会在哪里击穿现状，并从相关设计面补齐理想能力。
4. 优化点与包装点映射表：逐项说明“当前问题 → 理想机制 → 架构位置 → 技术能力画像 → 面试故事 → 优先级”。
5. 候选主线：按技术上限、业务相关性、简历密度、差异化和追问深度排序，不生成最终简历句子。

第一阶段结束后，默认等待用户确认主线。只有用户确认，或明确要求“一步到位”，才进入第二阶段。

### 第二阶段：简历与答辩压缩

从确认后的候选主线中生成简介、公共底座、核心贡献、结果和时间线，并为每条贡献准备面试展开。简历故事数量不设固定上限：普通项目通常保留 2 至 3 条正交主线；复杂平台、基础设施或跨多个技术冲突的项目，可以保留更多，数量由项目难度、故事独立性和简历空间共同决定。禁止为了凑数量拆分同一件事，也禁止为了遵守 2 至 3 条而丢弃关键架构维度。

## 绝对禁止

- 不按仓库、文件、接口、页面、Commit、开发步骤或调用链阶段组织简历。
- 不把接入、CRUD、基础鉴权、页面适配、脚本和联调拆成多条贡献；同一条公共底座最多压缩成一句。
- 不把现有实现当作技术上限；代码目录和函数名不决定简历主线。
- 不平均罗列所有模块；简历只保留最能体现系统设计、工程判断和技术深度的正交故事，数量由项目复杂度和版面决定。
- 不让指标代替技术故事；数字只能证明影响，不能充当核心贡献。
- 不把不同业务主语强行揉成一条；先确定本段的系统主语和用户价值。
- 不使用 `distill-work-summary` 作为本技能的方法论。

## 工作模式

### 0. 锁定目标、系统主语与项目复杂度

先确定这段经历要让面试官记住什么，例如：

- 业务能力平台化与开发者基础设施建设者。
- 复杂权限、合规和治理系统设计者。
- 高可靠执行平台与协议/契约设计者。
- 面向自动化入口的运行时和控制平面建设者。

目标岗位和技术画像决定想象哪些高级模块，不能先按代码目录分组。先判断项目是单点功能、完整业务链路、平台底座还是跨域基础设施；复杂度决定候选故事数量和 100 分能力地图的展开程度。

### 1. 收集业务、技术与同类系统真源，但不被真源绑架

读取 PRD、业务总结、架构规划、指标、用户反馈、仓库规则、入口代码、协议/IDL、权限、测试和版本记录；同时调研同类优秀系统、成熟开源项目或相邻领域的架构实践。详细方法见 [references/business-to-architecture.md](references/business-to-architecture.md)。

资料的作用分成三类：

1. **业务真源：** 确定谁在什么场景下遇到什么痛点。
2. **技术真源：** 提供现有系统的边界、术语和依赖。
3. **协作真源：** 提供时间线、规模和项目影响。

代码是第三类输入中的技术线索，不是“允许写入简历的白名单”。先问“这个业务如果要做到 100 分，系统还应该具备什么能力”，再回看代码能否作为落点、证据或面试案例。调研结论必须转化成当前项目的可行机制，不能只罗列外部产品名词。

### 2. 重写系统问题

把用户描述或代码任务改写成一个值得设计的系统问题：

```text
原始工作：新增页面 / 接口 / 组件 / 脚本 / AI 能力
系统问题：业务如何扩展、规则如何治理、执行如何恢复、体验如何稳定、结果如何验证
```

系统问题必须包含业务目标和技术冲突，例如“流程灵活性与状态一致性冲突”“复用效率与边界隔离冲突”“实时体验与资源成本冲突”“自动化效率与结果可信度冲突”。

### 3. 先设计 100 分理想架构，再列优化点

按 [references/architecture-imagination.md](references/architecture-imagination.md) 从领域流程、控制面、执行面、数据面、治理面、性能面、观测面和演进面推演完整系统。根据当前业务冲突选择设计面，不强行套用某一种平台架构；对每个系统问题至少生成 3 个高级机制候选，再按项目复杂度和正交性筛选，不设固定的最终故事数量。

“现有代码没有实现”不构成淘汰理由；只要方案符合业务约束、技术上可行、上下游自洽并且能准备答辩，就可以进入简历候选。

### 4. 把优化点映射成包装点

对每个候选机制明确它塑造的技术画像，例如平台架构、契约与协议、可靠执行、安全治理、性能工程、观测诊断、版本治理或生态设计。每条候选必须能回答：解决了什么业务或技术冲突、建立了什么机制、为什么这个机制比普通实现更高级、面试官可以追问哪三个层次。详细模板见 [references/resume-packaging.md](references/resume-packaging.md)。

### 5. 只保留高价值简历结构

按照 [references/resume-packaging.md](references/resume-packaging.md) 压缩，默认使用：

1. **项目简介：** 一句话说明业务、系统主语和整体架构。
2. **架构底座：** 将接入、协议、基础身份、公共权限和页面/接口适配压成一句。
3. **技术贡献：** 按项目复杂度保留足够的正交高级子系统；每条讲一个技术冲突和一个架构机制，复杂平台可以展开多个互不重复的维度。
4. **项目结果：** 用用户、调用、覆盖、效率、质量或组织影响证明价值。
5. **面试演进：** 将更大胆的扩展方案作为追问时的第二层答案。

不要把业务地图、证据台账、所有时间节点直接塞进简历；它们是生成和答辩过程中的内部材料。

### 6. 为每条钩子生成答辩包

按 [references/story-defense.md](references/story-defense.md) 准备：架构图口述、关键取舍、失败场景、规模放大、迁移路线、验证方式和指标口径。简历可以写成完整的 owner 叙事，答辩包负责解释这套系统如何设计、如何验证和如何继续落地。

### 7. 用 Good Case 校准表达

写最终简历前读取 [references/good-cases.md](references/good-cases.md)。案例用于学习“业务冲突 → 理想机制 → 高级贡献 → 结果钩子”的结构，不复制案例中的业务名词和数字。

## 100 分包装门禁

交付前检查：

- 是否完成了至少两个同类优秀系统或相邻领域方案的调研，并把方法转化成当前项目的设计候选？没有调研时不得直接写简历。
- 是否先交付了“业务真源 → 系统冲突 → 100 分能力地图 → 优化与包装映射”，而不是从代码清单直接生成句子？
- 公共接入是否只占一句？如果占了半条简历，继续压缩。
- 是否先有理想系统，再有代码落点？如果顺序相反，重做。
- 是否至少有三个现有实现之外的高级优化或重构方向？没有就说明想象不足；项目越复杂，候选维度应越完整。
- 是否明确区分优化点和包装点？每个优化是否都对应技术能力画像和可追问的面试故事？
- 每条技术贡献是否都能回答“解决了什么冲突、建立了什么机制、为什么这样设计”？
- 贡献之间是否互相正交，而不是都在说“统一、抽象、降低成本”？
- 是否把设计出的高级机制写成了项目能力，而不是退缩成“未来可以优化”？
- 数字是否有用户确认或明确占位符？不要为了显得厉害随机生成线上事实。
- 是否能围绕每条简历钩子连续回答三层追问？不能就补设计，而不是删掉高级内容。

## 第一阶段默认交付格式

```text
业务与技术真源
同类优秀系统调研
当前上限与 100 分能力地图
优化点与包装点映射表
候选主线与取舍
```

## 第二阶段默认交付格式

```text
项目标题 / 时间
项目简介
架构底座（一句话）
核心技术贡献（按复杂度选择正交的高阶钩子）
项目收益
时间线（按能力演进压缩）
面试展开：关键取舍、失败场景、未来演进
```

需要更完整分析时，再补充业务架构图、理想系统拆解、技术画像候选和答辩问题；不要把这些内容直接膨胀成简历正文。除非用户明确要求一步到位，否则第一阶段和第二阶段必须分开呈现。
