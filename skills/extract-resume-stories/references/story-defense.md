# 通用高级简历故事答辩包

简历可以按完整 owner 故事表达，答辩包负责把想象出来的高级架构变成可解释、可验证的技术方案。不要把“代码里没有同名文件”当成放弃高级故事的理由。

## 30 秒总述

```text
我在 [业务] 中面对 [核心系统矛盾]，重新设计了 [系统边界/平台]。
整体分为 [公共底座] 和 [关键高级子系统]，通过 [关键机制] 解决 [业务增长/可靠性/治理/性能] 问题，最终以 [结果信号] 验证价值。
```

## 3 分钟展开

按照下面顺序讲，不要从文件和函数开始：

1. 业务为什么需要这个系统，旧流程的上限是什么。
2. 你重新定义了哪些边界，领域、控制、执行和数据如何分工。
3. 最重要的技术冲突有哪些，为什么选择当前模型；根据项目复杂度决定展开数量。
4. 失败、重试、权限撤销、数据不一致、版本漂移或人工兜底如何处理。
5. 如何用测试、PoC、压测、灰度、用户反馈或真实结果验证设计。
6. 如果规模再扩大十倍，下一步补什么机制。

## 跨领域追问

### 架构与领域

- 为什么这样划分领域边界？哪些对象属于同一状态机？
- 哪些规则放在控制面，哪些规则必须下沉到执行面？
- 新入口或新业务接入时，哪些契约必须稳定？

### 可靠性与一致性

- 如何保证重试不会造成重复写入？
- 任务中断、响应丢失或下游部分成功时如何恢复？
- 如何判断系统状态已经生效，回查和补偿在哪里发生？

### 性能与规模

- 十倍数据量、并发量或会话长度下，最先出现什么瓶颈？
- 为什么选择缓存、批处理、虚拟化、增量更新或异步化？
- 降级、限流、背压和成本边界怎么设？

### 安全与治理

- 身份、角色、资源和动作如何组合授权？
- 审批、审计、回收和策略版本怎么闭环？
- 如何避免自动化入口绕过人工流程或安全边界？

### 自动化与 AI

- 工具契约、运行时、任务状态和模型输出如何解耦？
- 如何做评估、回放、人工兜底和错误归因？
- 哪些能力属于平台底座，哪些能力属于业务玩法？

### 版本与生态

- 依赖、组件、SDK、规则或文档变更如何发现兼容风险？
- 如何灰度、回滚和迁移已有消费者？
- 如何控制扩展点，避免平台最终退化成不可治理的插件集合？

## 想象方案的内部验证

对每个高级机制补一份内部说明：目标、数据结构、关键接口、失败状态、迁移步骤、最小 PoC、压测/契约测试方法和结果口径。最终简历只保留钩子；用户要求事实审计时，再单独展示哪些是现有能力、哪些是设计验证和哪些是下一阶段方案。

可以生成模拟规模、压测指标和故障演练作为面试练习；进入最终简历的客观数字需要用户确认口径。
