# 从业务到系统架构

## 业务先行

先回答五个问题，不要先看目录树：

1. 谁在什么场景下使用这个系统？
2. 当前流程中最贵、最慢、最容易出错或最难扩展的环节是什么？
3. 核心业务对象、状态和动作是什么？
4. 哪些边界必须被保护：身份、租户、资源、环境、版本、内容安全还是数据一致性？
5. 成功之后，业务会多出什么能力，研发会少掉什么成本？

把“做了一个功能”改写成一个系统命题：

| 原始描述 | 系统命题 |
| --- | --- |
| 新增页面/流程 | 把用户目标建模为可观测、可恢复、可演进的业务状态机 |
| 新增开放接口/SDK/命令 | 建立稳定契约、统一入口和兼容演进机制 |
| 接入第三方服务/依赖 | 建立适配层、风险隔离、版本治理和验证门禁 |
| 加权限/合规规则 | 把身份、资源、动作、审批和审计拆成组合治理模型 |
| 写批处理/自动化脚本 | 建立任务编排、幂等、断点恢复和结果回查机制 |
| 做数据统计/监控 | 建立指标定义、事件模型、诊断闭环和反馈决策系统 |
| 调研 AI/自动化提效 | 建立受控运行时、工具契约、评估集和人机协作闭环 |

## 真源的正确作用

业务文档用于确认目标和边界；架构文档用于寻找系统分层；代码用于提取术语、现有依赖和技术支点；Commit/MR 用于了解演进节奏；指标用于证明影响。任何来源都不能限制理想架构的完整度。

如果资料不完整，先基于业务模式补全合理假设，再列出需要用户确认的关键变量。不要因为没有看到某个类、表、接口或任务，就断言系统不能拥有该能力。

## 同类系统调研

100 分包装不是凭空堆砌高级名词。先识别项目属于哪类系统，再选择至少两个成熟参照：同类商业产品、开源基础设施、公司内部平台或相邻领域的成熟方案均可。调研重点放在系统模型，不是复制简历措辞：

1. 它如何定义核心对象、入口和契约？
2. 它如何处理权限、资源边界、版本和兼容？
3. 它如何执行任务、处理失败、恢复状态和验证结果？
4. 它如何做日志、审计、回放、灰度、升级和生态扩展？

将调研结果整理为“参考机制 → 适用业务冲突 → 当前项目可迁移设计 → 不能照搬的边界”。如果无法访问外部资料，可以使用已知行业模型或仓库内的架构规划，但要明确哪些是参考假设，不能假装完成了事实调研。

第一阶段至少交付一张能力对照表：

| 业务维度 | 当前上限 | 参考系统的成熟机制 | 当前项目的 100 分设计 | 简历能力画像 |
| --- | --- | --- | --- | --- |
| 扩展 / 可靠 / 治理 / 观测 / 演进 | 现状瓶颈 | 参照模型 | 可行机制 | 技术主线 |

## 业务架构图

优先画总图，再决定哪些部分值得写进简历：

```text
业务入口 / 角色 / 目标
        |
        v
领域对象 / 状态 / 规则 / 工作流
        |
        v
契约与控制：配置、身份、权限、审批、版本、策略
        |
        v
执行与数据：任务、队列、存储、事件、缓存、回查
        |
        v
观测与演进：日志、指标、回放、灰度、迁移、反馈
```

## 技术画像映射

用业务问题选择技术画像，而不是用代码模块选择简历标题：

- 流程复杂、状态多、异常多：领域建模与可靠工作流能力。
- 多入口、持续扩展、多人复用：平台化、契约和版本工程能力。
- 资源、角色、合规要求复杂：安全治理与策略系统能力。
- 高并发、大数据、弱网或实时交互：性能、资源模型和可观测能力。
- 规则密集、人工操作多：编译期自动化、批处理和工程效率能力。
- AI/自动化探索：运行时边界、评估、可靠性和人机协同能力。

最后只选一个主画像和两至三个支撑画像，避免平均用力。
