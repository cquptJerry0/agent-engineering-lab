# 面试导向课程大纲设计

## 目标

把一套知识或能力要求编译成可以稳定授课、形成实践证据并用于面试答辩的课程。

课程设计必须同时满足：

```text
知识完整
  +
认知顺序合理
  +
每课可以实践
  +
面试可以上场
  +
长期授课不漂移
```

## 强制原则

1. 区分`知识总纲`和`课程目录`：总纲定义完整边界，课程目录定义课数、顺序和验收。
2. 先建立覆盖矩阵，再确定课数；不能先拍脑袋决定“做 30 课”再硬塞内容。
3. 一节课围绕一个可以独立推演、实验和答辩的核心问题，不围绕零散术语。
4. 每节课从思考题开始，以可上场的面试答辩结束。
5. 每节课必须有具体案例、ASCII 图(纯文本结构图)、正常实验和失败实验。
6. 面试导向不等于背题；必须能用机制、边界、代码、数据或执行证据接住追问。
7. 不用删减知识换取表面简洁；用章节分组、课程聚类和支线触发条件控制投入。
8. 框架、产品和题库是案例或验收素材，不能成为知识主干。
9. 不提前批量创建空课件；开讲一课时再生成对应课件。
10. 较难英文第一次出现时写成`英文(精简通俗注释)`。

## 任务路由

先判断输入状态：

| 输入状态 | 处理方式 |
|---|---|
| 已有稳定知识总纲 | 直接设计课程架构和覆盖矩阵 |
| 只有零散资料或多套目录 | 先使用“知识体系调研与总纲设计” Skill（内部标识：`architecture-research`）合订知识主干 |
| 已有课程但结构混乱 | 审计覆盖、重复、课时粒度和防漂移机制 |
| 只需要写某一节课 | 使用本 Skill 的单课合同，不重做完整课程 |
| 只有题库或岗位描述 | 反推能力域，但必须补充原理与实践来源 |
| 只要求背面试答案 | 升级为“机制 + 案例 + 失败 + 证据”的课程，不只生成话术 |

## 工作流

### 第一步：读取现状

- 读取适用的仓库规则、知识总纲、资料、进度、题库和已有课程。
- 确认哪些文件拥有知识定义权，避免课程目录另建知识主干。
- 盘点用户目标、已有基础、目标岗位、时间预算和可用实践环境。
- 用户未提供时间预算时，先按产出驱动设计，不用固定时长限制课程。

### 第二步：提取能力域

将输入整理成三层：

```text
稳定能力域
  ↓
可独立掌握的核心问题
  ↓
具体知识点、案例和题目
```

核心问题必须能回答：

- 它解决什么真实问题？
- 最小工作机制是什么？
- 常见失败是什么？
- 如何通过实验或任务验证？
- 面试官会如何连续追问？

### 第三步：建立覆盖矩阵

先输出：

| 知识或能力单元 | 主归属课程 | 实践证据 | 面试验收 | 处理方式 |
|---|---|---|---|---|

处理方式只能是：

- 正文课完整覆盖。
- 与强相关知识合并讲授。
- 作为支线按条件插入。
- 已被另一课程完整覆盖。
- 暂不纳入，并明确理由。

不得使用“课程太长”作为删除核心知识的理由。

### 第四步：确定课程规模

课程数量由下面四个因素共同决定：

1. 认知依赖：后置课程是否依赖前置心智。
2. 问题完整性：一节课是否能形成完整案例和实验。
3. 上下文负担：是否在一节课中混入多个不同抽象层。
4. 验收成本：是否能在课末独立验证掌握。

一节课过大时拆分，一节课只有术语介绍时合并。

推荐结构：

```text
导学：先看完整系统或完整问题
基础章：建立必要原理和真实协议
机制章：掌握核心运行机制
组合章：处理复杂场景和系统协作
生产章：可靠性、安全、成本和治理
项目章：端到端整合、故障演练和答辩
```

结构可以随领域变化，不机械保留这些章节名称。

### 第五步：选择案例系统

优先使用一个贯穿课程的母案例，保持术语、角色和数据连续。

母案例必须具备：

- 明确用户和业务目标。
- 可观察输入和输出。
- 真实状态或数据变化。
- 可以主动制造失败。
- 能从简单版本逐步扩展。
- 可以产出面试项目证据。

不同主题需要替换案例时，说明替换原因，并保持核心机制可对照。

### 第六步：设计课程目录

每节课目录至少写明：

```text
课程标题
核心思考
知识主归属
具体案例
ASCII 图主题
最小正常实验
失败实验
面试目标
完成标准
```

详细格式见[课程架构](references/course-architecture.md)。

### 第七步：锁定单课合同

每节正式课必须包含：

```text
课程定位
开场思考
一句话心智
ASCII 图
具体案例
机制推演
最小正常实验
失败实验
框架或方案映射
面试攻防
课程验收
满分心智
仍未解决的问题
```

读取[单课模板](references/lesson-blueprint.md)获得完整字段和写法。

### 第八步：设计面试攻防

每课至少形成：

1. `30 秒回答`：核心判断 + 最小机制 + 一个关键边界。
2. `3 分钟回答`：问题、机制、ASCII 图、案例、失败、取舍和证据。
3. `三层追问`：原理追问、工程追问、项目追问。
4. `隐藏前提`：指出问题成立所需的约束，不盲目接受题设。
5. `现场证据`：代码、实验、指标、Trace、产物或复盘。

“吊打面试官”的标准是理解更完整、证据更真实、边界更清楚，不是使用攻击性话术。

### 第九步：评审后再批量落地

默认设置三道评审门：

1. 先确认课程目标、目标岗位和知识边界。
2. 再确认章节、课数和覆盖矩阵。
3. 再确认一节完整样课和课程模板。

用户明确要求一步到位时可以连续执行，但内部仍要完成三次检查。

### 第十步：建立防漂移机制

- 临时问题先归类为当前课、后续课、支线或前沿线索。
- 后续课问题只给最小定位，不提前展开整章。
- 新增课程必须证明现有课程无法承载该问题。
- 删除课程必须证明对应知识已有完整去向。
- 案例、框架和工具可以替换，核心问题与验收保持稳定。
- 每章结束后做覆盖复核、随机抽题和失败排障。

## 默认文件结构

```text
docs/course/
├── README.md          # 唯一课程入口和完整目录
├── lesson-template.md # 单课合同与验收规则
└── lessons/           # 开讲后逐课生成，不预建空文件
```

若项目使用中文文件名，可以改成：

```text
docs/课程/
├── README.md
├── 课程模板.md
└── 课件/
```

课程目录引用知识总纲和题库，不复制它们的完整定义。

## 质量验收

交付前读取[质量门禁](references/quality-gates.md)，并执行：

```bash
python3 scripts/validate_course.py <课程目录文件> --strict
```

至少人工确认：

- 所有核心知识都有课程或明确支线去向。
- 课程编号连续且没有重复。
- 每课只有一个主问题，但拥有完整案例和实验。
- 每课存在 ASCII 图主题、失败实验、面试目标和完成标准。
- 面试回答能落到真实机制与证据。
- 课程目录没有成为第二份知识总纲。
- 没有过拟合固定课数、框架、题库或单一项目。

## 资源读取规则

- 设计课程规模、章节和覆盖矩阵时读取[课程架构](references/course-architecture.md)。
- 编写或审查单节课时读取[单课模板](references/lesson-blueprint.md)。
- 交付前或用户要求评审课程质量时读取[质量门禁](references/quality-gates.md)。

## 禁止事项

- 不先定课数再倒推内容。
- 不把知识总纲中的每个条目机械拆成一课。
- 不按教材章节、文章来源或框架品牌直接生成课程。
- 不用纯理论讲解替代案例和实验。
- 不只设计正常 Demo，不设计失败路径。
- 不用题库决定完整知识边界。
- 不把 30 秒面试答案写成没有机制与边界的口号。
- 不批量生成大量空课件文件制造完成感。
