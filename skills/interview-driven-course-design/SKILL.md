# 自适应双轨课程设计

## 目标

把稳定知识边界和当前学习状态编译成一个高 ROI 的课程单元：

```text
知识总纲
  +
学习进度与薄弱点
  +
当前项目或面试目标
  ↓
当前 CU
  ├── 推导式理解
  └── 面试训练
```

课程不是知识真相源，也不是永久排期。它是面向当前学习者的生成视图。

## 强制原则

1. 知识总纲定义“应该知道什么”，学习进度定义“当前掌握到哪里”，CU 只回答“现在学什么”。
2. 默认只设计当前 CU，不预先锁死完整课数、永久分组和长期顺序。
3. 一个 CU 可以覆盖多个知识点，但必须共享中心问题、贯穿案例、连续状态和因果链。
4. 第一轨先学懂：`已有能力 → 暴露问题 → 引入机制 → 更新状态 → 下一问题`。
5. 第二轨后训练：从第一轨抽取题目，不另造知识结论。
6. 生成文档不等于掌握；只有复述、实验、排障和复核证据才能更新进度。
7. 框架、产品和题库是机制样本或验收素材，不能成为知识主干。
8. 公开班级、固定工期或明确排期场景可以设计完整目录，但必须标明它是暂定快照和重排条件。
9. 不提前批量创建空课件；开始一个 CU 时才创建对应双轨产物。
10. 较难英文第一次出现时写成`英文(精简通俗注释)`。

## 输入与真相源

优先读取：

| 输入 | 负责的问题 |
|---|---|
| 知识总纲 | 完整知识边界、依赖和掌握标准 |
| 学习进度 | 已掌握、薄弱点、遗忘和证据 |
| 当前目标 | 项目、面试、时间和环境约束 |
| 题库 | 真实问法、追问和题型 |
| 资料索引 | 机制来源、版本和待验证方向 |

若只有零散资料或多套冲突目录，先使用`architecture-research`建立稳定主干。

## 工作流

### 第一步：确认当前学习状态

- 读取适用的仓库规则。
- 找到唯一知识总纲和进度文档。
- 盘点当前目标、最近答错、实验失败、遗忘风险和可用环境。
- 已有课程只能作为历史生成结果，不自动继承其分组。

### 第二步：选择候选知识点

优先级：

1. 当前项目或面试马上需要，但理解不足。
2. 阻塞多个后续知识的基础机制。
3. 曾答错、只能背诵或实验失败。
4. 长时间未复核。
5. 尚未开始但暂时不阻塞后续。

每个候选知识点记录：

```text
主归属：
当前状态：
前置依赖：
选择原因：
需要的掌握证据：
```

### 第三步：聚合当前 CU

读取[课程架构](references/course-architecture.md)。

只有同时满足下面条件才合并：

- 共同回答一个中心问题。
- 可以使用同一个项目、用户目标和环境。
- 前一机制留下的问题会自然引出下一机制。
- 数据、状态或控制权可以连续演进。
- 能形成一条端到端 Trace(完整执行轨迹)。
- 一次学习可以完成理解、实验设计和复述。

出现两套独立状态模型、不同案例或两条无法统一的推导链时拆分。

### 第四步：设计链路学习

第一轨必须先给完整推导链，再展开项目版本：

```text
已有能力
  ↓
真实案例暴露问题
  ↓
解释现有机制为什么不够
  ↓
引入一个新机制
  ↓
输入、状态、控制权或输出发生变化
  ↓
制造正常与失败证据
  ↓
留下下一问题
```

每个中间机制都必须有因果作用。删除该机制后，后续版本应无法成立。

CU 与阶段标题必须采用名词化技术主题，例如`模型生成与 Tool Calling 原理`、`Verification Loop 与反馈修正`。标题用于回答“当前学习哪个技术块”，不能写成`为什么……`、`怎样……`、`如何……`类问题句。中心问题和阶段问题继续保留，但放在`中心问题`或`当前问题`字段中。

每个阶段不是单个知识点，也不能只是故事段落。它是围绕一个局部问题组织的知识点群，必须按下面的最小结构交付：

```text
本阶段知识点群
  ↓
当前问题与推导过程
  ↓
机制全解
  ↓
状态变化
  ↓
阶段结论与下一问题
```

`推导过程`负责说明知识为什么出现，`机制全解`负责把本阶段涉及的概念、组成、工作方式、边界和常见误区系统讲完整。两者不能互相替代。

详细合同见[单元蓝图](references/lesson-blueprint.md)。

### 第五步：设计面试学习

第二轨只在第一轨的结论稳定后生成。

每道题至少包含：

```text
完整题目和题型
一句话核心判断
启发式思考
30 秒回答
完整回答
必要的 ASCII 图
原理、工程和项目追问
实验、Trace、代码或真实请求证据
对应推导章节
```

换一种问法后仍应能从同一机制推导答案。若答案只能匹配题库原句，则课程设计不通过。

### 第六步：定义验收与写回

CU 设计必须明确：

- 理解验收：能否不看资料复述问题链。
- 图与状态验收：能否画出输入、状态、控制权和输出。
- 正常实验：什么证据证明机制工作。
- 失败实验：什么证据证明边界被理解。
- 实验可执行性：学习者是否知道准备什么、按什么步骤操作、应该看到什么。
- 自测验收：是否提供参考答案、判分点和常见错误。
- 图谱验收：是否使用中文节点和带语义的关系箭头。
- 面试验收：能否完成核心判断、短答、完整回答和连续追问。
- 进度写回：哪些证据允许升级到哪个状态。

生成 CU 本身不更新进度。

### 第七步：决定是否生成完整排期

默认停止在当前 CU。

只有用户明确要求以下场景时，才设计完整目录：

- 公开班级或团队统一授课。
- 已承诺的教学周期和交付日期。
- 需要评审整体预算、讲师或实验资源。
- 用户明确要求完整暂定计划。

完整目录必须标明：

```text
生成时间
适用人群
关键假设
暂定顺序
重排条件
每个 CU 的依赖和验收
```

完整排期仍不能成为第二份知识总纲。

## 推荐产物

```text
docs/课程/
├── README.md
└── CU-001-主题/
    ├── 推导式理解.md
    └── 面试训练.md
```

后续 CU 按真实生成顺序追加，不预建空目录。

## 质量验收

读取[质量门禁](references/quality-gates.md)，并执行：

```bash
python3 scripts/validate_course.py <课程入口或设计文件> --strict
```

若用户明确要求固定排期：

```bash
python3 scripts/validate_course.py <课程入口或设计文件> \
  --allow-scheduled-catalog --strict
```

## 禁止事项

- 不先定课数再倒推内容。
- 不把总纲中的每个知识点机械拆成一课。
- 不因总纲相邻就强行合并知识点。
- 不用纯理论章节替代贯穿项目和状态演进。
- 不把第一轨的 CU 或阶段标题写成面试问题或推导问句。
- 不在第一轨中混入完整面试答案。
- 不在第二轨中重新定义知识。
- 不把“看完文档”记录为已掌握。
- 不批量生成大量空课件制造完成感。
