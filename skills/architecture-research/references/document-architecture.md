# 研究型文档架构

## 目录

1. 唯一真相源
2. 总分结构
3. 多文档职责
4. 知识颗粒度
5. 去重规则
6. 迁移与完整性
7. 图表与正文

## 1. 唯一真相源

一套文档只能有一个知识主干。

```text
README
告诉读者从哪里开始

总纲
定义完整知识、架构和边界

方法
定义如何学习、研究或执行

进度
记录状态和证据

资料
记录来源和可信度

前沿
记录尚未稳定的方向
```

发生冲突时必须明确哪份文档拥有定义权。脑图、进度表、项目目录和案例都不能独立修改知识范围。

## 2. 总分结构

先用一张全景图和一条认知路径建立共同语境，再展开完整章节。

```text
全局判断
    ↓
系统分层或问题分类
    ↓
章节目标
    ↓
完整知识点
    ↓
边界、失败与验证
```

全景图负责看懂关系，不负责承载全部细节。总纲正文必须保留完整颗粒度。

每个一级章节只回答一个大问题。二级章节进一步拆机制，不按资料来源或框架品牌拆分。

## 3. 多文档职责

创建多文档前先输出职责表：

| 文档 | 唯一回答的问题 | 权威内容 | 不应该包含 |
|---|---|---|---|
| README | 从哪里开始 | 导航和入口 | 完整知识解释 |
| 总纲 | 应该知道什么 | 唯一知识定义 | 学习日志 |
| 方法 | 具体怎么做 | 工作流和质量标准 | 第二套知识树 |
| 进度 | 做到哪里 | 状态和证据链接 | 机制解释 |
| 资料 | 依据什么 | 来源、版本和证据 | 学习顺序 |
| 前沿 | 什么还不稳定 | 假设、争议和晋级条件 | 已确认主干 |

一个新文档必须回答：

- 它解决了哪份现有文档无法解决的问题？
- 删除它会丢失什么独立信息？
- 它是否会复制已有定义？

如果无法回答，不创建新文档。

## 4. 知识颗粒度

总纲中的核心章节至少包含：

```text
章节目标
核心心智
完整知识点
关键判断或概念边界
常见失败
最小实验或验证
第一轮掌握要求
与其他章节的关系
```

每个知识点至少能回答：

1. 它解决什么问题？
2. 它位于系统哪里？
3. 最小工作机制是什么？
4. 什么时候适用？
5. 常见失败是什么？
6. 如何验证真正掌握？

不要为了文档变短，把十个独立机制压成一个宽泛标题。

## 5. 去重规则

### 定义去重

同一概念只在主归属章节完整定义一次。

其他位置使用：

```text
一句定位 + 链接
```

不要再次复制机制、分类和失败边界。

### 章节去重

两个章节内容相似时，从下面四点区分：

- 控制权由谁持有。
- 状态由谁维护。
- 失败在哪里处理。
- 对外契约是什么。

如果四点都相同，考虑合并。

### 文档去重

- 总纲解释“是什么”。
- 方法解释“怎么学或怎么做”。
- 进度只记录“完成到哪里”。
- 资料只解释“依据什么”。

不要让每份文档都拥有“概念介绍”一列。

## 6. 迁移与完整性

重构现有文档时先建立迁移台账：

| 旧知识点 | 新主归属 | 处理方式 | 是否保留 | 原因 |
|---|---|---|---|---|

处理方式包括：

- 原样迁移。
- 重命名。
- 拆分。
- 合并。
- 降级为案例。
- 移入前沿。
- 删除。

删除必须给出理由，不能用“新结构更简洁”代替。

完成后检查：

- 旧知识点是否全部有去向。
- 新增知识点是否有来源。
- 总纲和进度是否能一一定位。
- README 是否能到达所有正式文档。
- 是否存在孤立文档。

## 7. 图表与正文

| 形式 | 负责表达 |
|---|---|
| 图 | 系统关系、包含关系、调用流和状态流 |
| 表格 | 分类、职责、对比、证据和取舍 |
| 正文 | 核心判断、原因、边界、失败和例子 |

图后不逐箭头复述。表格内容过长时，将判断移回正文。

一张图只回答一个问题。全景图不能同时承担调用链、学习顺序、文档导航和未来规划。
