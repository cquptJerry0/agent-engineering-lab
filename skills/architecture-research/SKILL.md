# 知识体系调研与总纲设计

## 目标

把分散资料重新编译成一套可解释、可验证、可维护的知识或架构体系。

不要按文章来源依次总结。先抽取问题、机制、证据和边界，再形成统一心智、文档职责与总分结构。

## 强制原则

1. 先设计研究，再执行研究。
2. 先合订知识架构，再设计文档。
3. 先让用户评审体系和样稿，再批量写正文。
4. 一个概念只有一个主归属和一处权威定义。
5. 官方资料、源码、论文和真实系统证据优先于课程与社交媒体。
6. 中文负责解释，英文只保留必要术语；较难术语第一次出现时写成`术语(精简通俗注释)`。
7. 不用删减知识点换取表面清爽；用层级、职责和引用消除混乱。
8. 不把推断、规划和宣传写成已落地事实。

## 任务路由

先判断任务属于哪一类：

| 类型 | 目标 | 默认交付 |
|---|---|---|
| 方向调研 | 判断某个领域应该怎么理解和建设 | 研究报告、问题地图、推荐方向 |
| 体系盘点 | 检查现有知识或架构是否完整、现代、重复 | 覆盖矩阵、缺口、重构建议 |
| 多资料合订 | 将多篇文章或多个项目统一成一个心智 | 概念归一表、统一架构、总纲 |
| 多文档重构 | 解决入口混乱、职责重叠和知识重复 | 文档职责表、迁移表、重构结果 |
| 正式方案写作 | 需求、目标和主要方案已经确定 | 转交`technical-document-writing` |

## 工作流

### 第一步：读取规则与现状

- 进入仓库后先读取适用的`AGENTS.md`、项目规则和业务背景。
- 盘点现有文档、目录、链接、版本、来源和未提交改动。
- 用户要求只调研时，不创建、修改或删除文件。

### 第二步：研究设计

读取[来源合订](references/source-synthesis.md)和[评审门禁](references/review-gates.md)。

先产出：

- 核心决策问题。
- 研究边界和非目标。
- 需要验证的关键假设。
- 来源类型与证据要求。
- 调研对象选择理由。
- 预期产物和风险。

默认停下让用户进行第一次评审。用户明确要求一步到位时可以继续，但仍需在内部完成研究设计。

### 第三步：标准化来源

为每份来源建立证据卡片，不按文章顺序写最终正文。

至少形成四个中间产物：

```text
问题地图：领域中有哪些稳定问题
概念归一表：同义词、近义词和真实差异
覆盖矩阵：每个问题有哪些来源和证据
冲突矩阵：来源在哪些结论上不一致
```

需要当前事实、最新项目状态或前沿方向时，必须联网核实发布日期、版本和官方来源。

### 第四步：建立统一架构

读取[文档架构](references/document-architecture.md)。

- 以问题和机制分组，不以文章、作者或框架分组。
- 将框架和开源项目降级为机制样本。
- 明确稳定主干、案例、支线和前沿雷达。
- 为每个概念指定唯一主归属。
- 建立旧内容到新结构的迁移映射，证明没有遗漏。

若需要多文档体系，先输出：

- 唯一主入口。
- 唯一知识主干。
- 每份文档只回答的问题。
- 文档之间的引用关系。
- 总纲一级结构和一个细颗粒度章节示例。

默认停下让用户进行第二次评审。

### 第五步：写一个完整样章

读取[中文表达](references/writing-quality.md)和[产物模板](references/output-patterns.md)。

样章必须展示：

- 总分结构。
- 完整知识颗粒度。
- 英文术语的通俗注释。
- 核心机制、边界、失败和验证。
- 图、表、正文的明确分工。

默认停下让用户进行第三次评审。先根据反馈修正结构和语言，再批量写剩余文档。

### 第六步：批量落地

- 先写唯一知识主干，再写方法、进度、资料、前沿等辅助文档。
- 辅助文档通过链接引用主干，不复制定义。
- README 只负责告诉读者从哪里开始。
- 每完成一份文档，检查它是否仍然只回答一个问题。

### 第七步：质量审计

先运行：

```bash
python3 "${CODEX_HOME:-$HOME/.codex}/skills/architecture-research/scripts/validate_doc_system.py" \
  <文档根目录> --entry README.md
```

再完成人工语义审计：

- 重要结论是否有原始来源。
- 原有知识点是否全部迁移或明确降级。
- 同一概念是否在多个文档重复定义。
- 每个分点是否能独立读懂。
- 较难英文是否在第一次出现时解释。
- 是否存在只有术语、没有问题和机制的段落。
- 总纲是否因追求简洁而缺斤少两。
- 推断、规划、案例和已落地事实是否区分清楚。

脚本只能检查结构问题，不能代替语义审计。

## 资源读取规则

- 合订多来源、处理证据冲突时读取[来源合订](references/source-synthesis.md)。
- 设计单文档或多文档职责时读取[文档架构](references/document-architecture.md)。
- 写正文、解释英文和检查可读性时读取[中文表达](references/writing-quality.md)。
- 需要暂停等待用户确认时读取[评审门禁](references/review-gates.md)。
- 需要输出研究设计、证据卡片、职责表或样章时读取[产物模板](references/output-patterns.md)。

## 下游交接

- 研究结论已经稳定，需要写正式技术方案：使用`technical-document-writing`。
- 需要拆成可执行工作包：使用`progressive-task-decomposition`。
- 需要绘制正式架构图：使用`tech-whiteboard`。
- 结构已固定，只需精修表达：使用`distill-work-summary`的文字级精修模式。

## 禁止事项

- 不按“资料一、资料二、资料三”组织最终架构。
- 不用框架功能列表代替问题分类。
- 不把推特、课程或泄漏材料作为唯一事实依据。
- 不在用户尚未评审架构时批量生成大量正文。
- 不为显得专业堆砌英文、缩写和框架名。
- 不用一页脑图替代完整知识总纲。
- 不让进度表、项目目录或案例文档另建一套知识主干。
