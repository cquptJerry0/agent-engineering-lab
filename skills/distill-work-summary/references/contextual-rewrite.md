# 文字级精修模式

用于结构已经固定，只需要优化文字表达、上下文承接、抽象总结、个人成长、技术难点或沉淀产出的场景。

## 核心原则

不要先改结构。先判断原文所在章节的职责，再判断这句话该保留事实、抽象能力，还是压缩解释。

改写时保持三件事：

- 不丢原句主干。
- 不复述前文项目。
- 不把总结写成空泛方法论。

## 改写顺序

### 1. 判断章节职责

- 背景：交代约束和原问题，不展开方案。
- 复杂度：说明为什么难，不证明能力。
- 核心难点：写风险、取舍和结果。
- 沉淀产出：写痛点和复用价值。
- 个人成长：写能力变化，不回放项目内容。

### 2. 判断抽象层级

- 太低：枚举项目、工具、字段、链路。
- 太高：只写方法论、判断力、体系化。
- 合适：用一句主判断承接成长，再用一句变化说明能力边界变宽。

### 3. 压缩语言

删除“提升明显、更加深入、逐步理解、这个点体现的是”等判断词。

优先保留具体动词：识别、拆分、下钻、区分、沉淀、降级、补偿。

避免第一人称和口语词。

## 个人成长写法

个人成长不是项目复述，也不是方法论口号。它要写“经过前文这些事后，处理问题的方式发生了什么变化”。

可参考这些句式，但不要机械套用：

- 复杂链路拆解更重视边界判断。处理需求时，不再只按页面、接口和操作步骤拆分，而是会先识别主链路、状态流转、一致性要求和副作用边界，判断哪些状态必须原子化，哪些动作可以补偿或降级。
- 对 Node.js 和中后台链路的理解更完整。问题定位不再停留在页面表现和接口返回，会继续下钻到服务分层、RPC、数据库事务、缓存、配置和部署环境，区分代码问题、配置缺口和环境依赖。
- 对 AI 提效的认知从使用工具推进到建设工具。面对高重复、强规则、可验证的研发流程，会进一步沉淀成 Skill、脚本或自动化流水线，让 AI 从单次辅助变成可复用的工程能力。

## 禁止写法

不要把成长写成项目索引：

```text
通过 TTP、i18n、Midscene、业务文档流水线，理解了……
```

不要把成长写成空泛方法论：

```text
形成了状态建模、风险治理、流程封装能力。
```

不要把成长写成态度：

```text
意识更强、理解更深、认知更克制。
```

## 典型改写

### 假转折改成约束变化

原文：

```text
这次需求的目标不仅仅是页面新增一个“预发布”状态，更是重构面板发布控制面：ROW 侧提交候选版本，TTP 侧可信人员审批，审批通过后再晋升正式版本。
```

改写：

```text
TTP 合规要求改变了面板发布的控制边界。ROW 侧只能提交候选版本，TTP 侧可信人员完成审批后，候选版本才能晋升为正式版本。
```

### 解释型表达改成边界判断

原文：

```text
这块的关键是先区分主链路和增强能力：审批链路必须稳定完成，辅助能力失败时只能降级，不能把错误继续向上扩散。
```

改写：

```text
TTP 适配需要先拆清主链路和增强能力。审批入口、审批提交和版本晋升属于主链路，必须保持可用；列表补充信息、辅助配置读取等能力失败时允许降级，避免非核心依赖阻断审批流程。
```

### 成长总结改成能力变化

原文：

```text
对 AI 提效的认知从“使用工具”推进到“建设工具”。通过 midscence skill、TTP 依赖治理 Skill、i18n 发布 Skill、业务文档自动更新流水线等探索，逐步理解了 AI 的封装边界、输入输出约束、执行报告和可复用资产建设方式。
```

改写：

```text
对 AI 提效的认知从使用工具推进到建设工具。面对高重复、强规则、可验证的研发流程，会进一步沉淀成 Skill、脚本或自动化流水线，让 AI 从单次辅助变成可复用的工程能力。
```

## 输出检查

- 是否保留了原句想表达的主干。
- 是否结合了所在章节职责。
- 是否比原文更短、更准。
- 是否没有重复前文项目内容。
- 是否能看出能力变化，而不是只看到项目枚举。
