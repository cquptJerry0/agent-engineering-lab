# 工作总结语言风格规则

本文档是 `distill-work-summary` 的语言准入规则。写述职、晋升、复盘、项目总结时，先按这里校准表达，再组织正文。

## 核心判断

好的工作总结靠逻辑推动，不靠句式显得高级。目标是文章有逻辑、表达清晰、判断可追溯。

每一段都要能回答四个问题：

- 当时有什么约束。
- 约束带来了什么具体冲突。
- 采取了什么取舍。
- 这个取舍让结果发生了什么变化。

如果一段话只能读出态度、形容词或抽象价值，看不出冲突和取舍，就要重写。

## 禁用的假转折

以下句式会让文字很像 AI 生成，也经常掩盖逻辑断裂。默认禁用，只有在确实需要纠正误解时才允许使用。

- “不是 A，而是 B”
- “不只是 A，还是 B”
- “不仅 A，还 B”
- “从 A 到 B”
- “既要 A，也要 B”
- “本质上是”
- “核心在于”
- “闭环赋能”
- “体现了我的”
- “这说明了”

这些句式的问题在于，它们经常把两个结论硬接在一起，中间缺少真实的因果链。改写时不要找同义词替换，要补出约束、冲突和取舍。

## 客观叙述与克制表达

默认使用客观叙述，不使用第一人称承接动作。

禁用：

- 我
- 我们
- 本人
- 我的
- 我负责
- 我参与

推荐承接对象：

- 本次改造
- 该链路
- 方案
- 系统
- 页面
- 发布流程
- 审批模型
- 配置能力

同时避免口语化动词和情绪化判断。下列表达容易让文章显得随意或用力，应替换成更明确的工程表达。

| 少用 | 推荐 |
|-|-|
| 压在 | 集中在 |
| 吃透 | 系统理解 / 明确 |
| 搞清楚 | 明确 / 梳理 |
| 卡住 | 受阻于 / 依赖于 |
| 走通 | 验证通过 / 完成联调 |
| 踩坑 | 暴露问题 / 发现风险 |
| 拉齐 | 统一 / 对齐 |
| 补齐认知 | 建立判断 / 完善理解 |
| 用力推进 | 收敛问题 / 推动落地 |

改写时优先保留事实关系，减少主观感受。

## 句子改写方法

优先用因果链表达。

坏句：

```text
这个项目不是简单支持预发布，而是重构了发布链路。
```

改写：

```text
原链路默认改动会直接进入 ROW 生产环境，TTP 合规要求加入预发布校验后，发布动作需要先沉淀成可审计、可回滚的中间状态，再进入正式发布。
```

坏句：

```text
这个能力不只是提升效率，还是沉淀了团队复用能力。
```

改写：

```text
过去每次发布都要人工确认环境、权限和下游状态，容易在临上线时反复补配置。将这些检查固化成操作文档和验证清单后，新需求可以沿同一套步骤完成验收。
```

坏句：

```text
从功能交付走向链路治理。
```

改写：

```text
这次交付里，页面入口只是显性改动，真正容易出问题的是发布过程中产生的半成功状态。方案将核心写入、审批状态、副作用同步拆成不同边界处理，避免失败后留下无法判断归属的脏数据。
```

## 段落连通规则

段落之间要按信息推进，不要靠排比或转折硬连。

推荐顺序：

```text
背景约束 -> 具体冲突 -> 关键取舍 -> 结果变化
```

可接受的段落推进方式：

- 前一段讲外部约束，后一段讲约束进入系统后产生的冲突。
- 前一段讲冲突，后一段讲原方案无法覆盖的边界。
- 前一段讲取舍，后一段讲这个取舍带来的稳定性、可恢复性或复用价值。

需要重写的信号：

- 段落之间只靠“同时、此外、另外、因此”连接，但信息没有递进。
- 每段末尾都上升到“能力”“价值”“闭环”。
- 同一个观点在背景、复杂度、难点、产出里重复出现。
- 标题像口号，正文找不到具体风险或工程取舍。

## 外显结构去模板化

正文可以有统一的思考框架，但不能把框架露在表面。真正需要稳定的是内部逻辑，不是标题和段落格式齐刷刷。

默认禁用这些写法：

- 三个标题都写成同一种语法，例如“XXX 总结 XXX”“XXX 治理 XXX”“XXX 提升 XXX”。
- 每段都按“问题是什么、做了什么、结果是什么”三句铺开。
- 每段开头都写“在 XXX 背景下”。
- 每段结尾都拔高到“最终形成了 XXX 能力”。
- 每个标题都用冒号拆成“名词：解释”，导致阅读节奏像表格。

更好的做法是保留隐性链路，改变外显切入点。

内部逻辑保持一致：

```text
约束 -> 冲突 -> 取舍 -> 结果变化
```

外显写法要错开：

- 一段从脏状态切入，先写失败后会留下什么问题。
- 一段从模型变化切入，先写原来的抽象为什么不够。
- 一段从落地阻塞切入，先写真实环境依赖缺口。
- 一段可以短，只承担信息推进；另一段可以长，用来讲关键取舍。

坏例子：

```text
### 事务边界总结发布一致性
### 缓存治理总结 Diff 稳定性
### 环境落地总结 TTP 部署经验
```

改写：

```text
### 半成功状态要先被收进模型
### Diff 缓存失效来自对比目标变化
### TTP 落地受阻于环境依赖
```

坏例子：

```text
事务边界的问题是发布链路存在一致性风险。通过拆分事务内外动作解决问题。最终提升了系统稳定性。

缓存治理的问题是 Diff 结果可能不准确。通过调整缓存 key 解决问题。最终提升了对比准确性。

环境落地的问题是 TTP 依赖不完整。通过补齐配置解决问题。最终提升了交付确定性。
```

改写：

```text
发布链路最怕留下判断不了归属的数据。核心写入和审批状态必须一起成功，缓存清理、通知、同步这类副作用可以放到事务外处理。这样失败后至少能判断数据停在哪个阶段，后续补偿也有依据。

Diff 缓存失效不是单纯的缓存过期问题。预发布加入后，对比目标从“当前生产态”变成了“草稿、预发、生产之间的多态比较”，原来的 key 无法表达目标环境和版本关系，因此需要重新建模缓存维度。

TTP 落地受阻于环境依赖。代码路径验证前，需要先确认权限、机房配置、下游能力和验证账号是否齐全，否则联调问题会混合在一起，无法判断是代码问题还是环境缺口。
```

## 标题写法

标题要交代判断或风险，避免只放抽象名词。

可用：

- “预发布链路的风险在半成功状态”
- “Diff 缓存失效来自对比目标变化”
- “TTP 落地受阻于环境依赖”
- “审批状态需要成为数据模型的一部分”

少用：

- “事务一致性”
- “复杂度治理”
- “链路闭环”
- “能力沉淀”

标题不要为了显得有冲突而套假转折。真实冲突来自材料本身。

## 语气和颗粒度

写作要保持工程表达的清晰度和克制感。

- 多写具体对象：审批状态、缓存 key、事务边界、发布环境、权限配置、验证清单。
- 多写具体动作：重构、拆分、治理、收敛、落地、校准、兜底、沉淀。
- 少写抽象标签：成长、赋能、闭环、价值、能力、抓手、体系化。
- 少写弱动作：参与、支持、负责、推进、对接。
- 避免第一人称、口语词和情绪化判断。
- 信息型段落可以直接结束，不要每段都拔高。

## 交付前检查

写完后逐段检查：

- 是否能看出真实约束。
- 是否写清具体冲突。
- 是否说明关键取舍。
- 是否交代结果变化。
- 是否删除假转折和模板化递进。
- 是否用事实推出能力，避免直接喊能力。
- 是否去掉第一人称叙述。
- 是否把口语表达替换成明确的约束、动作和结果。

如果删掉一句“不是 A，而是 B”后段落失去主旨，说明主旨本来没有被写清，需要补逻辑，不要换一个句式继续包装。
