# 高浓度工作总结

## 目标

把项目经历从“做了什么”压缩成“识别了什么问题、解决了什么复杂度、沉淀了什么能力”。默认服务于述职、晋升、绩效、成长总结、复盘沉淀。

输出要满足三点：

- 信息密度高：少讲过程，多讲判断、风险、方案和结果。
- 颗粒度稳定：不要逐文件、逐接口罗列；只保留能证明能力的关键点。
- 不重复：背景、复杂度、难点、产出分别承担不同叙事职责。
- 不模板化：固定结构只作为内部检查表，正文要按材料关系自然组织。

## 语言风格优先级

语言描述是本 Skill 的高优先级规则。执行写作、改写、压缩前，先读取 `references/language-style.md`，并按其中的“假转折禁用”和“段落连通规则”检查正文。

如果正文出现模板化转折、机械递进、段落逻辑接不上，优先修语言和逻辑，再压缩篇幅。

如果用户明确要求结构不变、只改文字，或指出“个人成长不像总结”“表达和上下文不贴”“抽象不够/太抽象”，先读取 `references/contextual-rewrite.md`，按文字级精修模式处理。

## 工作流

1. 先收集材料
   - 读取用户给的文档、commit、PR、需求说明、复盘记录。
   - 如果是代码项目，优先看 diff 统计、核心文件、测试、部署脚本、文档沉淀。
   - 只把能支撑观点的证据带入总结，不堆原始信息。

2. 先判断项目类型
   - 先问：这段经历最值得讲的是技术攻坚、复杂交付、平台建设、工具提效、排障复盘，或晋升述职里的能力跃迁。
   - 只选一条主线，最多补一条副线。不要把所有叙事模型都套上。

3. 再定一句话定位
   - 内部句式：在「背景/约束」下，将「原问题」改造成「新能力」，并沉淀「复用价值」。
   - 输出时不一定照搬这个句式，可以改成更自然的项目定位。
   - 示例：TTP 合规要求改变了 Material 的发布模型，原来的 ROW 直发需要升级成 Draft -> Pre -> Prod 的双机房审批链路。

4. 组织正文
   - 用户给了大纲时优先遵守用户大纲。
   - 用户没给大纲时，用“背景、复杂度、核心难点、沉淀产出、总结”作为默认骨架。
   - 默认骨架不是外显模板，每一节的写法要随材料变化。
   - 技术、复杂度、产出不要互相复述：复杂度只讲“为什么难”，难点讲“怎么判断和落地”，产出讲“解决了什么痛点”。

5. 写完后压缩
   - 删除低价值过程、文件罗列、泛泛能力标签。
   - 合并重复表达。
   - 保留能说明判断力的脏状态、边界取舍、上线后果、复用资产。

## 信息筛选规则

保留：

- 能说明业务/合规/系统约束的背景。
- 能说明链路重构、跨系统协作、强一致边界、降级治理的复杂度。
- 能体现工程判断的难点，例如事务边界、缓存建模、权限模型、部署落地、可观测性、自动化。
- 能复用的沉淀，例如操作文档、学习文档、复盘文档、脚本、Skill、测试方案。

删除：

- 文件列表式描述。
- “支持了页面、接口、字段”这类低密度流水账。
- 重复表达同一个价值的段落。
- 不能证明能力的实现细节。
- 没有痛点支撑的“写了文档/做了工具”。

## 叙事适配

按项目类型选择叙事重心，不要强行五段式。

- 技术攻坚型：先写错误后果或脏状态，再写关键机制和取舍，最后落到稳定性、可恢复性或长期可维护性。
- 复杂交付型：先写约束和不可控因素，再写如何收敛边界、拆分链路、推进验收，最后写交付结果和协作资产。
- 平台/基础设施型：先写系统边界和规模问题，再写标准化能力、降级策略、观测和复用，少写单点功能。
- 工具/效率型：先写重复痛点和人工成本，再写规则化、自动化、验证闭环，最后写提效范围和减少反复。
- 复盘排障型：先写现象和影响面，再写错误假设、定位路径、根因链路，最后写防复发沉淀。
- 晋升/述职型：先写影响面，再写判断力和复杂问题处理，最后写能力跃迁。不要只堆项目清单。

一个项目可能同时包含多类，但正文必须有主心骨。例如“预发布链路”主线是复杂交付，技术攻坚只挑事务、缓存、TTP 落地三处讲透；Skill 和文档沉淀放到产出，不抢主线。

## 默认正文骨架

### 1. 背景

用 1 到 3 段回答：

- 外部约束是什么。
- 原链路的问题是什么。
- 这个需求实际要重构什么能力。

不要在背景里展开技术方案。

### 2. 需求复杂度

只写复杂度，不写执行过程。每一点用“复杂在什么 + 为什么难”表达。这里负责铺垫问题分量，不负责证明技术能力。

常用复杂度维度：

- 发布模型变化：一步上线变成两阶段或多阶段链路。
- 状态结构化：临时 UI 状态变成可审计、可恢复的数据模型。
- 配置粒度：不同业务线、地区、角色、面板策略不同。
- 跨机房/跨系统：存在同步延迟、版本冲突、权限边界。
- 前端状态组合：多环境、多角色、多状态需要统一表达。
- 真实环境落地：依赖、权限、配置、下游能力不完整。

### 3. 核心难点

只挑 3 点。先在内部想清三件事：

```text
现象/风险：不处理会出现什么脏状态、错误判断、协作失败或上线风险。
关键取舍：为什么这样拆边界、建模型、做降级或做自动化。
结果：这个设计让链路获得了什么确定性。
```

这三件事是写作前的思考框架，不要原样写成“风险、解决、能力体现”三个小标题。

外显写法要有变化：

- 一个难点可以从失败后果切入，例如“预发布链路的风险在半成功状态”。
- 一个难点可以从模型变化切入，例如“Diff 缓存问题暴露的是对比目标变了”。
- 一个难点可以从落地环境切入，例如“TTP 真正的难点是环境不完整”。

可以插少量伪代码或文本图，但只在能降低理解成本时使用：

```text
事务内：
write core data
write audit/approval state
commit

事务外：
clear cache
notify
sync side effects
```

好的难点要能说明识别并治理了某类风险，不能停留在“实现了某接口”。

### 4. 沉淀产出

按资产类型写，说明解决什么痛点。不要把普通功能点混进产出。

推荐表格列：

| 产出 | 解决的痛点 | 价值 |
|---|---|---|

产出类型优先选择：

- 部署链路学习文档
- 操作文档
- 问题解决/排查复盘文档
- 测试方案或验收文档
- 脚本
- Skill
- 监控看板或排障手册

Skill 类产出只讲痛点和价值，不讲内部完整实现。示例：

| `starling-i18n-release` Skill | Starling CLI 链路长且不好用；代码里存在多种翻译函数风格，容易混淆远端翻译更新和代码集成 | 将 i18n 问题先分类，再按固定流程执行发布和验证，减少多语言上线反复 |

### 5. 总结

用 2 到 3 个成长方向收束。总结只收束前文已经证明过的能力，不新增观点。

可收束的方向：

- 功能交付之外，是否形成了链路设计和边界判断。
- 问题修复之外，是否治理了一类系统风险。
- 单次经验之外，是否沉淀了团队可复用资产。

## 语言描述

重点是避免模板化、口语化和第一人称叙述。详细规则见 `references/language-style.md`，该 reference 优先于本节的简要提示。

- 不要让三个难点同构。一个讲边界，一个讲机制，一个讲落地，节奏自然会不同。
- 不要把“风险、解决、能力体现”当作正文小标题。它们只能作为脑内检查项。
- 禁用假转折和模板化递进，例如“这个点体现的是”“不是 A 而是 B”“不只是 A，还是 B”“从 X 到 Y”“本质上”“闭环赋能”。只有在真实纠偏时才允许保留。
- 禁用第一人称叙述，例如“我”“我们”“本人”“我的”。默认使用客观对象承接动作，例如“本次改造”“该链路”“方案”“系统”“审批模型”。
- 能力判断要由事实和取舍推出。先写具体脏状态、错误后果、限制条件，再呈现判断依据。
- 不要每段末尾都拔高。重要段落可以收束，信息型段落直接结束。
- 标题要有判断，不只放名词。例如“预发布链路的风险在半成功状态”优于“事务一致性：拆清强一致和副作用边界”。
- 表达以清晰、克制、可审计为准，避免“压在”“吃透”“卡住”“走通”“踩坑”“拉齐”等口语词。
- 表格用于归类，正文用于讲判断。不要全文表格化。

写作时优先使用具体动词：重构、拆分、治理、落地、收敛、沉淀、校准、兜底。少用弱表达：参与、支持、负责、推进、对接。

## 风格要求

- 用中文输出，技术名词、代码标识、路径保留英文。
- 多用短句，少用空泛形容词。
- 表格只用于高密度归类，不要全文表格化。
- 技术部分一次讲透，避免背景、复杂度、难点互相重复。
- 每段都要能回答“材料支撑了什么判断”，但不一定把这句话写出来。
- 不要写“参与、支持、负责”这种弱表达，优先写“重构、拆分、治理、沉淀、落地、收敛”。
- 默认采用客观叙述，避免第一人称、口语词和情绪化判断。

## 输出检查

交付前检查：

- 是否能用一句话说清项目本质。
- 是否删除了低价值流水账。
- 是否根据项目类型选择了叙事主线。
- 是否最多只有 3 个核心难点。
- 是否每个难点都有风险、取舍和结果。
- 是否三个难点的标题和段落节奏不完全一样。
- 是否沉淀产出都写了“解决的痛点”。
- 是否避免同一个内容在复杂度、难点、产出里重复出现。
- 是否出现了“这个点体现的是”等机械能力标签，如果有，尽量改成事实自然推出能力。
- 是否按 `references/language-style.md` 删除假转折、补齐段落之间的约束、冲突、取舍和结果变化。
- 是否避免外显结构同构：标题、段落开头、段落结尾不能齐刷刷复用同一种句法，但内部逻辑仍要能连成一条线。
- 是否去掉第一人称叙述。
- 是否把口语表达替换成明确的约束、动作和结果。
